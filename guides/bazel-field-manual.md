# Bazel Field Manual

Deep reference for getting the most out of Bazel 9: every recommendation, the model, flags, Bzlmod, BUILD files, language rules, platforms, testing, remote caching and execution, performance, GitLab CI, images and air-gap, writing rules, troubleshooting, adoption and a one-screen reference.

Versions as of 2026-10-16: Bazel 9.3.0 LTS; module versions from the Bazel Central Registry.

## 01 · Every recommendation, one page

*The whole manual compressed to decisions: what to pick, why, the positions worth arguing about, the one-way doors, and the order to do it in if you are starting today.*

Every recommendation this manual makes, in one table, with the reason. If you read nothing else, read this and the chapter for whichever line you're about to disagree with.

**Defaults are for when you have no reason to choose otherwise.** Where a line says "close call", the alternative is genuinely defensible and the tiebreaker is named.

#### The stack

| Decision | Pick | Why | Chapter |
|---|---|---|---|
| Launcher | **Bazelisk**, named `bazel`, plus a committed `.bazelversion` | Every laptop and runner runs exactly the version the repo was tested with; an upgrade is a one-line diff you can revert | 03 |
| Bazel version | **9.x LTS** (9.3.0 today) | LTS releases get three years of fixes. Try the next major with `USE_BAZEL_VERSION=10.0.0rc1` on a branch, never by editing `.bazelversion` on main first | 03, 05 |
| Dependency system | **Bzlmod only** | WORKSPACE is gone in Bazel 9. `MODULE.bazel` plus a committed lockfile is the only supported path | 05 |
| Lockfile policy | **`--lockfile_mode=update` locally, `error` in CI** | A dependency can only change through a reviewed `MODULE.bazel.lock` diff | 04, 05 |
| Flags | **Everything in a checked-in `.bazelrc`**, situational flags under named configs, secrets in a gitignored `user.bazelrc` | Different flags in different terminals discard the analysis cache and split the remote cache | 04 |
| Action environment | **`--incompatible_strict_action_env`** | Your shell's `PATH` stops leaking into cache keys, so two machines produce the same action hashes | 02, 04 |
| BUILD files | **Generated by Gazelle** (Go, Python, proto) with `# keep` for the exceptions | Hand-maintained `deps` lists drift within weeks; Gazelle reads the imports | 06 |
| Visibility | **Private by default**, widened per consumer | Visibility is the only architecture rule a build system can enforce on every commit | 06 |

| Test results | **JUnit from `bazel-testlogs`** into GitLab, BEP file or BES link per job | Failures in the MR widget, timings and cache hits one click away | 09, 12 |
| Release metadata | **`--stamp` only under `--config=release`** | Stamping in every build turns every commit into a cache miss for every stamped action | 13 |
| Offline builds | **`bazel vendor` or a URL-rewriting downloader config with `block *`**, plus a mirrored registry | Every download is hash-checked, so a mirror can't change content without the build failing | 13 |
| Formatting and lint | **buildifier** for Starlark, **rules_lint** for source | Lint runs as cached actions with the same toolchains CI uses | 03, 06 |
| Editor | **JetBrains Bazel plugin or VS Code Bazel extension**, plus gopls with `GOPACKAGESDRIVER` | Language servers that can't see generated code produce red squiggles nobody trusts | 03, 07 |

#### The positions worth arguing about

These are opinions, not consensus. Each comes with its reason so you can overrule it deliberately.

| Position | Reason |
|---|---|
| **`bazel clean` is a bug report.** | A correct Bazel build never needs it. If it fixes something, an action has an undeclared input or a non-hermetic tool, and the next person hits it too. Find it with chapter 15 before you move on |
| **Remote cache first; remote execution only after 95% cross-machine hit rates.** | Remote execution makes every hermeticity bug fail at once on machines with nothing installed. The cache alone delivers most of the speed-up with none of that risk |
| **No host toolchains, ever.** | A rule that finds `gcc`, `python3` or `node` on `PATH` produces outputs that depend on what each machine has installed. Two machines then never share a hit |
| **`genrule` is for one line.** | It is a shell string with no providers, no toolchain resolution and `/bin/bash` as a hidden dependency. At twenty lines, write a rule (chapter 14) |
| **Never `tags = ["no-sandbox"]` or `"local"` to make a build pass.** | You have hidden an undeclared input, not fixed it, and the target is now uncacheable |
| **Small targets, not tiny ones.** | One library per package gives fine invalidation without drowning analysis in thousands of targets. Per-file targets cost more in analysis than they save in execution |
| **Generated BUILD files are reviewed, not hand-edited.** | Run Gazelle in CI with `-mode=diff`. A stale BUILD file should fail the MR that made it stale |
| **Keep the native tools working.** | `go build`, `uv run` and `pnpm test` beside Bazel keep onboarding cheap, keep IDEs happy, and make leaving Bazel possible. Chapter 16 |
| **Lockfiles are code.** | `MODULE.bazel.lock`, `go.sum`, `requirements_lock.txt` and `pnpm-lock.yaml` are reviewed like source. Renovate bumps them; humans approve |
| **One output base per tool.** | Your IDE and your terminal sharing an output base with different flags will fight over the analysis cache all day. Give the IDE its own with `--output_base` |
| **Measure before you tune.** | Every command writes a profile. Opening it takes one minute; guessing at flags takes an afternoon. Chapter 11 |

#### One-way doors — decide these slowly

Most choices in this manual are reversible in an afternoon. These are not.

| Door | What it costs to change |
|---|---|
| **Adopting Bazel at all** | BUILD files in every directory, CI, IDE setup and onboarding all assume it. Leaving later is a project, unless you kept the native tools working (chapter 16) |
| **Package layout and target names** | Labels end up in BUILD files, scripts, CI, dashboards and other repos. Renaming a package rewrites every reference. `alias()` softens a move; it doesn't remove the cost |
| **The module name in `module(name = ...)`** | Once other repos depend on it, renaming breaks every consumer's `bazel_dep` |
| **Public rule and macro APIs** | Attributes of a published rule or macro are a contract. Removing or renaming one breaks every BUILD file that set it |
| **Letting untrusted jobs write the shared cache** | A poisoned action result is served to every machine until it is evicted. The fix is wiping the cache and rebuilding trust, and you rarely know which entry was bad |
| **Hard-coding canonical repo names (`@@rules_go+`)** | Canonical names are an implementation detail and changed format between Bazel 7 and 8. Code that depends on them breaks on upgrade |
| **Remote execution platform image** | Every action key includes the exec platform. Changing the worker image invalidates the whole remote cache at once. Plan it as a scheduled cold-cache day |
| **Mirroring strategy for an air-gapped site** | Vendored source trees, a mirrored registry and URL rewriting each shape how updates cross the gap. Switching means re-validating every bundle you've shipped |

#### If you are starting today, in order

1. Chapter 03 — Bazelisk, `.bazelversion`, aliases, buildifier. Ten minutes.
2. Chapter 02 — read the model once, properly. Every later chapter assumes it.
3. Chapter 05 — a `MODULE.bazel` with the rule sets you need and a committed lockfile.

## 02 · The model underneath

*Three phases and one cache key. Every surprise Bazel hands you, from a rebuild you didn't expect to a cache miss in CI, traces back to how an action is hashed.*

Everything else in this manual follows from a handful of ideas. Get them solid and Bazel stops being surprising. Leave them fuzzy and every cache miss looks like a bug in Bazel when it is really a bug in the build.

### 1. Bazel is a function from inputs to outputs, memoised

Bazel reads your BUILD files, turns them into a graph of **actions**, and runs the actions whose outputs you asked for. Each action is a command with a fully declared list of input files, output files, arguments and environment. Bazel hashes all of that into an **action key**. If it has seen the key before, it reuses the recorded outputs instead of running the command.

That is the whole product. Incremental builds, remote caching, remote execution, test result caching and "build only what changed in this merge request" are all the same memoisation, applied at different scopes.

Two consequences you will use constantly:

- **Correctness depends on declarations, not on what the command actually reads.** If a compiler reads a header nobody declared, Bazel doesn't know the action depends on it. Change the header and nothing rebuilds. The sandbox exists to turn that silent bug into a loud failure.
- **Anything that reaches the action key splits the cache.** A different `PATH`, a different flag, a different toolchain version or an absolute path containing your home directory all produce a different key. Two machines that should share outputs then don't.

### 2. Three phases, three graphs

Every `bazel build`, `test`, `run` or `query` goes through some or all of three phases. Knowing which phase you are in tells you which tool to reach for.

| Phase | Input | Work done | Output | Inspect with |
|---|---|---|---|---|
| **Loading** | `MODULE.bazel`, `BUILD.bazel`, `.bzl` files | Resolve modules, evaluate Starlark, expand macros, run `glob()` | Packages and unconfigured targets | `bazel query` |
| **Analysis** | Targets plus a configuration (platform, flags) | Run each rule's implementation function; providers flow from deps to dependants; actions are *declared*, not run | Configured targets and the action graph | `bazel cquery`, `bazel aquery` |
| **Execution** | The subset of the action graph needed for the requested outputs | Check the cache for each action key; run misses in a sandbox, a persistent worker or a remote executor | Files under `bazel-out/` | `--profile`, `--execution_log_json_file`, `-s` |

Since Bazel 7, analysis and execution are interleaved ("Skymeld"): execution of a target can start as soon as that target is analysed. The phases are still conceptually separate, and the profile still shows them as distinct lanes.

#### What lives where

- **Loading phase errors** are Starlark and BUILD-file problems: `name 'go_library' is not defined`, `no such package`, a `glob()` that matches nothing with `allow_empty = False`.
- **Analysis phase errors** are graph and rule problems: visibility violations, a dep that doesn't provide what the rule needs (`does not have mandatory providers`), no matching toolchain, a `select()` with no matching branch.
- **Execution phase errors** are command problems: a compiler error, a missing input inside the sandbox, a test failure, a timeout, a download failure.

> **Field note.** A slow *no-op* build (nothing changed, but `bazel build //...` still takes 40 seconds) is an analysis problem. The usual cause is that the flags changed since the last command, so Bazel discarded the analysis cache. A slow *real* build is an execution or cache problem. Look at the profile before deciding which one you have.

### 3. Skyframe: why the second build is fast

Bazel runs as a long-lived **server** (a JVM) per output base. The client you type into is a thin process that talks to it. The server keeps the loading and analysis results in memory in a graph called **Skyframe**, where every value (a package, a configured target, an action, a file's digest) records what it was computed from.

When you run the next command, Bazel asks the file system what changed, invalidates exactly the Skyframe nodes that depended on those files, and recomputes only those. That is why a one-line change to a leaf library re-analyses a few targets instead of the whole repo.

What breaks the in-memory graph:

| Event | Effect |
|---|---|
| A build option that affects configuration changed (`--compilation_mode`, `--platforms`, most `--define` and `--//flag` values) | `Build option --X has changed, discarding analysis cache`. Analysis restarts from scratch |
| A startup option changed (`--output_base`, `--host_jvm_args`) | The server restarts. Everything in memory is lost |
| `bazel shutdown`, an OOM kill, a reboot | Server gone. The on-disk action cache survives, so execution is still incremental |
| A `.bzl` file that many BUILD files load changed | Every package that loads it is reloaded and re-analysed. Big but correct |

> **Gotcha.** Your IDE plugin, a pre-commit hook and your terminal are three clients of the same server. If they pass different flags, they take turns throwing away each other's analysis cache. Chapter 04 covers keeping them aligned, and the escape hatch: a separate `--output_base` for the tool that must differ.

#### `--watchfs`

By default Bazel discovers changes by checking file metadata. With `--watchfs`, it subscribes to OS file-change notifications (inotify on Linux, FSEvents on macOS) and only checks what the OS reported. On large repos this cuts seconds off every incremental command. It is safe to enable in `.bazelrc` for developer machines.

### 4. Repos, packages, targets and labels

#### The containers

| Concept | Defined by | Example |
|---|---|---|
| **Main repo** | The directory containing `MODULE.bazel` (the workspace root) | `~/src/mono` |
| **External repo** | A module, or a repo created by a module extension or repo rule | `@rules_go`, `@pypi`, `@distroless_static` |
| **Package** | A directory with `BUILD` or `BUILD.bazel`, plus all subdirectories that don't have one | `//lib/auth` |
| **Target** | A rule instance, a source file or a generated file inside a package | `//lib/auth:auth`, `//lib/auth:token.go` |

A package's boundary is hard: `glob()` does not cross into a subpackage, a target can only list files from its own package directly in `srcs`, and visibility is checked per package.

#### Labels

```text
@repo//path/to/pkg:target
│     │            └── target name (defaults to the last path component)
│     └── package path, relative to the repo root
└── repo name as seen from the current repo (omit for the current repo)
```

| Written | Means |
|---|---|
| `//lib/auth:auth` | Target `auth` in package `lib/auth` of the main repo |
| `//lib/auth` | Same thing: the target named after the package |
| `:auth` | Target `auth` in the current package |
| `token.go` | Source file in the current package (only in BUILD files) |
| `@rules_go//go` | Target `go` in package `go` of the repo the main repo calls `rules_go` |
| `@@rules_go+//go` | Same target by its **canonical** name. Never write this by hand |
| `//lib/...` | Pattern: every target in every package under `lib/` |
| `//lib/auth:all` | Pattern: every rule target in one package |
| `//lib/auth:*` | Pattern: every target including files |

#### Apparent and canonical repo names

With Bzlmod, a module chooses how it refers to its dependencies (the **apparent name**, usually the module name, or `repo_name` in `bazel_dep`). Bazel internally gives each repo a unique **canonical name**. Since Bazel 8 canonical names use `+` as a separator, for example `@@rules_go+` for a module and `@@gazelle++go_deps+com_github_google_uuid` for a repo created by an extension. Bazel 7 used `~`.

> **Gotcha.** Anything that parses canonical names (scripts grepping `bazel-out`, hard-coded runfiles paths like `external/rules_go~/...`) broke in the 7→8 upgrade and will break again if the scheme changes. Use apparent names in BUILD files, and resolve runfiles through the runfiles libraries rather than string-building paths.

### 5. Visibility: architecture you can enforce

Every target has a `visibility` attribute that lists which packages may depend on it. The check runs at analysis time and fails the build.

| Value | Who can depend on it |
|---|---|
| `["//visibility:private"]` | Only targets in the same package (the default unless `package(default_visibility = ...)` says otherwise) |
| `["//visibility:public"]` | Everyone |
| `["//services/api:__pkg__"]` | Targets in exactly that package |
| `["//services:__subpackages__"]` | Targets in `services/` and every package below it |
| `["//teams/payments:allowed"]` | Anyone listed in a `package_group` named `allowed` |

```starlark
package_group(
    name = "auth_clients",
    packages = [
        "//services/api/...",
        "//services/gateway/...",
        "-//services/api/legacy/...",   # exclusions start with -
    ],
)
```

Since Bazel 8, a target defined inside a symbolic macro is also checked against the macro's own location, so macros can no longer leak private targets into a caller's package. Legacy macros don't have this protection.

> **Field note.** Visibility is the cheapest architecture-enforcement tool you will ever get. Making `//lib/db` visible only to `//services/...` and `//lib/repo/...` turns "the web handler talks to the database directly" from a code-review argument into a build failure.

### 6. Rules, providers and the analysis contract

A **rule** is a Starlark function that receives its attributes (with dependencies already analysed) and returns **providers**. A provider is a typed struct that a dependency exposes to its dependants.

```text
go_library(//lib/log)   ──returns──▶  GoInfo, DefaultInfo
        │
        ▼ (deps)
go_library(//lib/auth)  ──reads GoInfo of //lib/log, declares a compile action,
                          returns its own GoInfo
        │
        ▼ (embed)
go_binary(//services/api) ──reads GoInfo of everything, declares a link action
```

Rules never see each other's internals, only providers. That is what keeps them composable: `oci_image` doesn't care that its layer came from `pkg_tar` wrapping a `go_binary`, only that it got files through `DefaultInfo`.

| Provider | Carries |
|---|---|
| `DefaultInfo` | `files` (what `bazel build` materialises), `runfiles`, `executable` |
| `OutputGroupInfo` | Named extra output sets, built with `--output_groups=name` |
| `CcInfo` | Headers, compile flags, libraries to link |
| `PyInfo` | Transitive Python sources, import paths |
| `JavaInfo` | Compile and runtime jars |
| `GoInfo` (rules_go) | Archive data for compiling and linking |
| `InstrumentedFilesInfo` | Which files coverage should instrument |
| `TestEnvironmentInfo` | Env vars a test rule adds |

```bash
# what a target actually returns
bazel cquery //lib/auth --output=starlark --starlark:expr='providers(target)'
```

### 7. Actions, keys and the two caches

An **action** is the unit of execution and caching. Each one has a **mnemonic** (`GoCompilePkg`, `CppCompile`, `PythonZipper`, `OCIImage`), a command line, declared inputs, declared outputs and execution requirements.

#### What goes into the action key

| Ingredient | Example that changes the key |
|---|---|
| Command line (argv) | Any flag that the rule passes through, `-O2` vs `-O0` |
| Environment variables set for the action | `PATH` when `--incompatible_strict_action_env` is off; any `--action_env` |
| Digests of every input file | One byte of one source, header, tool binary or SDK |
| Output paths | Configuration hash in `bazel-out/k8-fastbuild/...` |
| Execution platform properties | `exec_properties` such as the container image |
| Execution info | Tags like `no-remote` |

Things that **don't** go in the key: timestamps of inputs, the machine's hostname, your username. Unless they reach the command line or environment, which non-hermetic toolchains often make happen.

#### Local and remote caches

```text
action key ──▶ Action Cache (AC) ──▶ list of output digests + exit code
                                         │
                                         ▼
                      Content-Addressable Storage (CAS): digest ──▶ bytes
```

| Cache | Where | Survives | Notes |
|---|---|---|---|
| In-memory Skyframe | Bazel server | Until the server stops or flags change | Loading and analysis only |
| On-disk action cache | `$(bazel info output_base)/action_cache` | `bazel shutdown`; not `bazel clean` | Per output base. Tracks what is in `bazel-out` |
| Disk cache (`--disk_cache=DIR`) | Any directory | `bazel clean`, new clones | AC + CAS on local disk. Shared across workspaces on one machine |
| Remote cache (`--remote_cache=URL`) | A server speaking the Remote Execution API | Everything | Shared across machines. Chapter 10 |

> **Note.** Test results are cached the same way. A test action's key includes the test binary and all its runtime data, so `(cached) PASSED` means "this exact test, with these exact inputs, passed before". If the test reads something undeclared, the cached pass is a lie.

### 8. Hermeticity and the sandbox

A **hermetic** action reads only its declared inputs and depends on nothing about the machine it runs on. Hermeticity is what makes caching safe and remote execution possible.

Bazel enforces it with execution **strategies**:

| Strategy | What it does | Where it's used |
|---|---|---|
| `linux-sandbox` | Runs the action in Linux namespaces, with only declared inputs mounted (symlinked) into a fresh exec root, and no network by default | Default on Linux |
| `darwin-sandbox` | `sandbox-exec` profile on macOS | Default on macOS |
| `processwrapper-sandbox` | Fresh symlink tree of declared inputs, but no namespace isolation | Fallback where namespaces aren't available (some containers) |
| `worker` | Hands the request to a long-lived persistent worker process (javac, tsc, some Go tooling) | Rules that support it; big speedups for JVM compilers |
| `remote` | Sends the action to a remote executor | With `--remote_executor` |
| `local` / `standalone` | Runs directly in the exec root with no isolation | Debugging, or actions tagged `local`/`no-sandbox` |
| `dynamic` | Races local and remote for the same action, takes the first | Large remote-execution setups |

```bash
# which strategy ran each action
bazel build //app --execution_log_json_file=/tmp/exec.json
jq -r 'select(.runner) | .runner' /tmp/exec.json | sort | uniq -c

# force a strategy for one mnemonic, or everything
bazel build //app --strategy=GoCompilePkg=local
bazel build //app --spawn_strategy=local      # test whether the sandbox is the problem
```

#### What the sandbox does and doesn't catch

| Leak | Caught by the sandbox? |
|---|---|
| Reading an undeclared source file from the repo | Yes: it isn't mounted |
| Writing to an undeclared output | Yes: the output is discarded or the action fails |
| Using the network | Yes on `linux-sandbox` (no network unless `requires-network`) |
| Reading `/usr/bin/gcc`, `/usr/lib`, `/etc` | **No.** System paths are visible read-only so tools can run |
| Reading the environment (`PATH`, `HOME`) | Partly. `--incompatible_strict_action_env` fixes `PATH` |
| Timestamps, random seeds, hostnames in output | No. That's reproducibility, not isolation |

> **Gotcha.** The Linux sandbox still exposes the host's system directories. A rule that finds `python3` or `gcc` on the host builds fine in the sandbox and fails on a remote worker that doesn't have it, and two developers with different distro versions never share cache hits. Hermetic toolchains (chapter 08) close that gap; the sandbox alone does not.

### 9. Configurations: target and exec

A **configuration** is the full set of build options that affect how a target is analysed: the target platform, compilation mode, feature flags, `--//my:setting` values. The same target analysed under two configurations becomes two configured targets with different output paths.

Every build has at least two:

| Configuration | Built for | Typical members |
|---|---|---|
| **Target** | The platform in `--platforms` (defaults to the host) | Your binaries, libraries, tests, images |
| **Exec** | The execution platform the actions run on | Compilers, code generators, protoc, any `cfg = "exec"` dependency |

```bash
bazel config                     # every configuration this server has seen, with short hashes
bazel config 0a1b2c3 4d5e6f7     # diff two configurations' options
bazel cquery 'deps(//app)'       # each result is shown with its configuration hash
```

Output paths encode the configuration: `bazel-out/k8-fastbuild/bin/...` for the target configuration on Linux x86_64, `bazel-out/k8-opt-exec-<hash>/bin/...` for tools. A **transition** (chapter 08) changes the configuration partway down the graph, for example to build an image's binary for `linux/arm64` while the rest of the build stays on the host platform.

> **Field note.** "Why is this library being compiled twice?" Usually because it's both a dependency of your binary (target configuration) and of a code generator (exec configuration). That is correct, and `bazel cquery 'somepath(//app, //lib/x)'` shows you which path pulls in which copy.

### 10. Runfiles

A binary or test often needs files at runtime: data files, other binaries, the Python interpreter, shared libraries. Bazel collects them into a **runfiles tree** next to the executable: `bazel-bin/app/server.runfiles/`.

| You declare | It ends up |
|---|---|
| `data = ["testdata/config.yaml"]` | `server.runfiles/_main/app/testdata/config.yaml` |
| `data = ["@pypi//certifi"]` or a dep from another repo | Under that repo's directory in the runfiles tree |
| A binary in `data` | Its own runfiles merged in |

`_main` is the runfiles directory name for the main repository under Bzlmod.

Read runfiles through the language's runfiles library, never by guessing paths:

```python
# Python: rules_python's runfiles library
from python.runfiles import Runfiles

r = Runfiles.Create()
path = r.Rlocation("_main/app/testdata/config.yaml")
```

```go
// Go: rules_go's runfiles package
import "github.com/bazelbuild/rules_go/go/runfiles"

path, err := runfiles.Rlocation("_main/app/testdata/config.yaml")
```

> **Gotcha.** `bazel run` executes from inside the runfiles tree, not from your repo. A tool that writes files relative to the current directory writes them somewhere under `bazel-out`. Tools that need the repo read `$BUILD_WORKSPACE_DIRECTORY` (set by `bazel run`) and `cd` there first. Gazelle and buildifier already do this.

### 11. The output base, on disk

Each workspace gets an **output base**, by default under `~/.cache/bazel/_bazel_$USER/<md5 of workspace path>/`. One Bazel server runs per output base.

```text
~/.cache/bazel/_bazel_you/
├── install/<hash>/            # unpacked Bazel binary, shared by all workspaces
├── cache/repos/v1/            # repository cache: downloaded archives by sha256 (shared)
└── 3f2a…/                     # output base for one workspace
    ├── server/                # server pid, logs (java.log)
    ├── action_cache/          # on-disk action cache
    ├── external/              # fetched external repos
    ├── execroot/_main/        # the exec root: symlink forest where actions run
    │   └── bazel-out/
    │       ├── k8-fastbuild/bin/       # outputs: target configuration
    │       ├── k8-fastbuild/testlogs/  # test.log, test.xml
    │       └── k8-opt-exec-…/bin/      # tools: exec configuration
    └── command.profile.gz     # trace profile of the last command
```

| Path | How to get it | Use |
|---|---|---|
| Workspace | `bazel info workspace` | Repo root |
| Output base | `bazel info output_base` | Everything per workspace |
| Exec root | `bazel info execution_root` | Reproduce an action by hand |
| `bazel-bin` | `bazel info bazel-bin` | Outputs for the current configuration |
| Test logs | `bazel info bazel-testlogs` | `test.log`, `test.xml` |
| Repository cache | `bazel info repository_cache` | Downloaded archives, shared across workspaces |
| Server log | `$(bazel info output_base)/java.log` | Why the server died |

The `bazel-bin`, `bazel-out`, `bazel-testlogs` and `bazel-<reponame>` symlinks in the workspace root are conveniences that point here. They follow the configuration of the last command, which is why `bazel-bin` sometimes looks empty after a build with different `--platforms`. Use `bazel cquery //t --output=files` with the same flags to find outputs reliably.

> **Gotcha.** `bazel clean --expunge` deletes the whole output base: fetched external repos, the action cache and every output. The default repository cache lives outside it (under `cache/repos/`), so archives survive, but extracted repos and toolchains do not. Keep `--repository_cache` and `--disk_cache` in directories you choose (chapter 04), and an expunge costs you one rebuild from cache instead of a full re-download over a slow or air-gapped link.

### 12. Commands and what they do

| Command | Phases | Notes |
|---|---|---|
| `bazel build` | Loading, analysis, execution | Builds the requested targets' default outputs |
| `bazel test` | All three, then runs tests | Inherits all `build` options |
| `bazel run` | All three, then executes one binary | Inherits `build`; one target only; args after `--` |
| `bazel coverage` | Like `test` with instrumentation | Inherits `test` |
| `bazel query` | Loading only | Fast, configuration-blind |
| `bazel cquery` | Loading + analysis | Configuration-aware |
| `bazel aquery` | Loading + analysis | Shows actions; nothing executes |
| `bazel fetch` | Fetches external repos | Use before going offline |
| `bazel vendor` | Fetches into a vendor directory | Offline builds, chapter 13 |
| `bazel mod` | Module resolution | `graph`, `explain`, `tidy`, `show_repo` |
| `bazel info` | None | Paths and server state |
| `bazel clean` | None | Deletes outputs; `--expunge` deletes the output base |
| `bazel shutdown` | None | Stops the server |
| `bazel analyze-profile` | None | Summarises a trace profile |

### The words that trip people up

| Term | What it actually is |
|---|---|
| **Workspace** | The directory tree rooted at `MODULE.bazel`. Not the same as the deleted `WORKSPACE` file |
| **Module** | A versioned unit of dependency with its own `MODULE.bazel`. Every external dependency is a module or a repo made by one |
| **Repository (repo)** | A directory tree Bazel can load packages from. Modules are repos; extensions create more repos |
| **Package** | A directory with a BUILD file. Not a language package, not a module |
| **Target** | Anything a label names: a rule instance, a source file, a generated file |
| **Rule** | The Starlark definition (`go_library`). A rule *target* is one use of it |
| **Macro** | A function that creates targets during loading. Leaves no trace in the analysed graph |
| **Aspect** | A function that walks the dependency graph during analysis and adds actions or providers to each node it visits |
| **Provider** | Typed data a target exposes to the targets that depend on it |
| **Action** | One command with declared inputs and outputs. The unit of caching |
| **Spawn** | The execution of an action's command on some strategy. Logs and flags often say "spawn" |
| **Mnemonic** | The short name of an action type, used in profiles, `aquery` and `--strategy` |
| **Configuration** | The set of options a target is analysed under |
| **Exec platform** | Where actions run. **Target platform** is what the outputs are for. **Host platform** is the machine Bazel runs on |
| **Toolchain** | A rule-specific bundle of tools, selected by matching platform constraints |
| **Runfiles** | The tree of files a binary or test needs at runtime |
| **Output base** | Per-workspace directory with the server, external repos and outputs |
| **Exec root** | The symlink forest under the output base where local actions run |
| **Stamping** | Embedding build metadata (git commit, version) in outputs, only under `--stamp` |

### The model in one paragraph

You describe targets in BUILD files. Bazel loads them, analyses them under a configuration into a graph of actions, and hashes each action's command, environment and input digests into a key. Actions whose keys it has seen before, in memory, on disk or in a shared cache, are not run; their outputs are fetched. Everything else runs in a sandbox that hides undeclared inputs. Labels name everything, visibility limits who may depend on what, and providers are the only thing a target exposes. When something is wrong you are asking one of three questions: *does the graph say what I think it says* (`query`, `cquery`), *is the action what I think it is* (`aquery`, `-s`, `--sandbox_debug`), or *is the key what I think it is* (execution log, `--explain`).


## 03 · Toolbelt and daily bazel

*Bazelisk, the shell setup, buildifier and buildozer, watch mode, editor integration, the daily commands organised by what you want to know, and the map of the ecosystem.*

Bazel is the engine. The day-to-day speed comes from the tools around it: a launcher that pins the version, a formatter, a bulk editor, a watcher, an editor that understands the graph, and a handful of shell functions you will type a hundred times a week.

### Bazelisk: the only way to install Bazel

Bazelisk is a small Go binary that reads the version a repo asks for, downloads that Bazel release once, caches it, and runs it. Install Bazelisk, name it `bazel`, and never install Bazel itself.

```bash
# Linux: release binary (Fedora has no official package)
mkdir -p ~/.local/bin
curl -fsSLo ~/.local/bin/bazel \
  https://github.com/bazelbuild/bazelisk/releases/latest/download/bazelisk-linux-amd64
chmod +x ~/.local/bin/bazel

# macOS
brew install bazelisk

# anywhere with Go
go install github.com/bazelbuild/bazelisk@latest   # binary is named bazelisk; symlink it to bazel

bazel version          # first run downloads the pinned release
```

#### How Bazelisk picks a version

In order, first match wins:

| Source | Example | Use |
|---|---|---|
| `USE_BAZEL_VERSION` env var | `USE_BAZEL_VERSION=10.0.0rc1 bazel build //...` | One-off: try the next major |
| `.bazeliskrc` in the workspace, then in `$HOME` | `USE_BAZEL_VERSION=9.3.0` | Rare; prefer `.bazelversion` |
| `.bazelversion` in the workspace root | `9.3.0` | **The normal pin. Commit it.** |
| Nothing found | | Latest release. Never rely on this |

Special values: `latest`, `latest-1` (one release back), `last_green` (newest commit that passed CI upstream), `last_rc`, and a fork prefix such as `myorg/9.3.0`.

#### Environment variables worth knowing

| Variable | Does |
|---|---|
| `USE_BAZEL_VERSION` | Overrides the version for one command |
| `BAZELISK_BASE_URL` | Where to download Bazel from. Point it at an internal mirror with the same path layout as GitHub releases (`<base>/<version>/bazel-<version>-<os>-<arch>`) |
| `BAZELISK_HOME` | Cache directory (default `~/.cache/bazelisk`) |
| `BAZELISK_SKIP_WRAPPER` | Don't run a `tools/bazel` wrapper script in the repo |
| `BAZELISK_GITHUB_TOKEN` | Avoid GitHub API rate limits when resolving `latest` |

> **Field note.** If the repo contains an executable `tools/bazel`, Bazelisk runs it instead of Bazel, passing the real binary in `$BAZEL_REAL`. Teams use it to inject flags, check prerequisites or log usage. It is also a surprise when you don't know it's there: `ls tools/bazel` is the first thing to check when Bazel behaves differently in one repo.

#### Air-gapped runners

```bash
# mirror one release into an internal artefact store, same layout as GitHub
V=9.3.0
for f in bazel-$V-linux-x86_64 bazel-$V-linux-x86_64.sha256 bazel-$V-linux-arm64; do
  curl -fsSLO "https://github.com/bazelbuild/bazel/releases/download/$V/$f"
done
# upload to https://artifacts.internal/bazel/$V/ then on the runners:
export BAZELISK_BASE_URL=https://artifacts.internal/bazel
```

Or bake the exact binary into the CI image at `/usr/local/bin/bazel` and skip Bazelisk on runners entirely. Developers keep Bazelisk; both read the same `.bazelversion`.

#### Completion

#### Functions that earn their keep

```zsh
# targets that use this file directly: bwho //lib/auth:token.go
bwho(){ bazel query "rdeps(//..., $1, 1)" --output=label_kind; }

# why does A depend on B: bwhy //app:server @pypi//requests
bwhy(){ bazel query "somepath($1, $2)" --output=label; }

# every path between two targets, as an SVG
bpaths(){ bazel query "allpaths($1, $2)" --notool_deps --noimplicit_deps --output=graph \
  | dot -Tsvg > /tmp/paths.svg && xdg-open /tmp/paths.svg; }

# where are the outputs: bout //app:server
bout(){ bazel cquery "$1" --output=files 2>/dev/null; }

# open a test log: btlog //lib/auth:auth_test
btlog(){ local p=${1#//}; p=${p/://}; ${PAGER:-less} "$(bazel info bazel-testlogs)/$p/test.log"; }

# which package owns this file: bpkg lib/auth/token.go
bpkg(){ bazel query "$1" --output=package 2>/dev/null; }

# tidy everything generated
btidy(){ bazel run //:gazelle && bazel mod tidy && buildifier -r -lint=fix .; }

# rule kinds in the repo, counted
bkinds(){ bazel query 'kind(".*rule", //...)' --output=label_kind | cut -d' ' -f1 | sort | uniq -c | sort -rn; }

# rerun a test until it fails (flake hunting)
bflake(){ bazel test "$1" --runs_per_test="${2:-100}" --test_output=errors --nocache_test_results; }

# copy a built binary out of bazel-bin: bcp //cmd/tool ~/bin/tool
bcp(){ bazel build "$1" && cp -f "$(bazel cquery "$1" --output=files | head -1)" "$2"; }
```

> **Gotcha.** `bazel query path/to/file.go` only resolves when `path/to` is itself a package. For a file in a subdirectory that has no BUILD file, use the full label (`//path:to/file.go`) or `bazel query 'kind("source file", //path/...)' | grep file.go`.

### buildifier: format and lint Starlark

buildifier formats BUILD, `.bzl` and `MODULE.bazel` files into one canonical style and lints them for common mistakes.

```bash
go install github.com/bazelbuild/buildtools/buildifier@latest

buildifier -r .                          # format everything in place
buildifier -r -mode=check .              # CI: exit non-zero if anything would change
buildifier -r -lint=warn .               # report lint warnings
buildifier -r -lint=fix .                # apply the fixable ones (adds missing load()s, sorts deps)
buildifier -lint=warn -warnings=all path/BUILD.bazel
buildifier --help | sed -n '/warnings/,$p'   # list every warning category
```

Keep it versioned inside the repo so every developer and CI job runs the same version:

```starlark
# MODULE.bazel
bazel_dep(name = "buildifier_prebuilt", version = "10.1.0", dev_dependency = True)
```

```bash
bazel run @buildifier_prebuilt//:buildifier -- -r -lint=fix .
```

Useful lint categories: `native-cc`, `native-java`, `native-py`, `native-proto` and `native-android` flag native rules used without a `load()`, which is exactly the Bazel 9 migration. `load` flags unused loads. `unsorted-dict-items` and `list-append` are style. `uninitialized` and `return-value` catch real Starlark bugs in `.bzl` files.

### buildozer: edit hundreds of BUILD files in one command

buildozer applies commands to targets selected by label patterns. It edits files in place and keeps formatting intact.

```bash
go install github.com/bazelbuild/buildtools/buildozer@latest
```

Syntax: `buildozer 'command args' LABEL_PATTERN...`. In the pattern, `%kind` selects targets by rule kind, `*` every target, and `__pkg__` the package itself (for `package()` and `load()` edits).

| Task | Command |
|---|---|
| Add a dep to every `go_library` under a tree | `buildozer 'add deps //lib/log' //services/...:%go_library` |
| Remove a dep everywhere | `buildozer 'remove deps //lib/oldlog' //...:*` |
| Replace one dep with another | `buildozer 'replace deps //lib/oldlog //lib/log' //...:*` |
| Set an attribute | `buildozer 'set size medium' //...:%py_test` |
| Set a list attribute | `buildozer 'set tags manual integration' //e2e/...:*` |
| Tighten visibility | `buildozer 'set visibility //visibility:private' //internal/...:*` |
| Add a missing load | `buildozer 'new_load @rules_cc//cc:cc_library.bzl cc_library' //third_party/...:__pkg__` |
| Rename an attribute | `buildozer 'rename copts cxxopts' //lib/...:%cc_library` |
| Rename a target | `buildozer 'set name new_name' //pkg:old`, then `replace deps` in its users |
| Create a new target | `buildozer 'new go_test auth_test' //lib/auth:__pkg__` |
| Copy an attribute from another target | `buildozer 'copy deps //lib/auth:auth' //lib/auth:auth_test` |
| Print attributes (read only) | `buildozer 'print label kind srcs' //lib/...:*` |
| Comment an attribute | `buildozer 'comment deps Needed for the codec ABI' //lib/codec` |

Commands can be chained with `|` inside one argument, and many can be fed from a file:

```bash
buildozer 'add tags requires-network|set size large' //e2e/...:%go_test

# commands.txt: one "command|label" per line
cat > /tmp/commands.txt <<'EOF'
add deps //lib/log|//services/api:api_lib
set visibility //services:__subpackages__|//lib/auth:auth
EOF
buildozer -f /tmp/commands.txt
```

> **Gotcha.** buildozer exits `3` when it ran fine but changed nothing, which fails `set -e` scripts. Treat `0` and `3` as success: `buildozer ... || [ $? -eq 3 ]`.

### ibazel: watch mode

ibazel watches the source files that a target's graph depends on and reruns the command when any of them change.

```bash
go install github.com/bazelbuild/bazel-watcher/cmd/ibazel@latest

ibazel build //lib/...                 # rebuild on save
ibazel test //lib/auth:auth_test       # rerun tests on save
ibazel run //services/api -- --port 8080   # restart the server on save
```

ibazel queries the graph to decide which files to watch, so a new file only gets watched once a BUILD file includes it. For servers, rules can opt into live reload through ibazel's notification protocol (`tags = ["ibazel_notify_changes"]`), where the running process is told to reload instead of being restarted.

> **Field note.** Tilt can drive Bazel too: a `local_resource` that runs `bazel run //services/api:load` and a `k8s_yaml` that deploys it. Use ibazel for the "one service on my laptop" loop and Tilt when the service must run inside a kind cluster with its neighbours.

### Editors

Language servers need to know how Bazel sees the code: which files are in which target, where generated files live, which external repos supply which imports. Each language solves that differently.

| Language | Tool | Setup |
|---|---|---|
| All (JetBrains IDEs) | JetBrains' **Bazel** plugin (IntelliJ IDEA, GoLand, PyCharm, CLion) | Open the repo; import a project view of the directories you work in. The newer JetBrains-maintained plugin replaced the older Google "Bazel for IntelliJ" plugin |
| All (VS Code) | **Bazel** extension (`BazelBuild.vscode-bazel`) | Syntax, buildifier on save, target code lenses. Language features come from each language's server below |
| Go | gopls with `GOPACKAGESDRIVER` | rules_go ships a packages driver; see below |
| C / C++ | clangd with `compile_commands.json` | Generate the file with a compile-commands extractor such as `hedronvision/bazel-compile-commands-extractor` |
| Python | Pyright / basedpyright | Point `extraPaths` at `bazel-bin` and the external pip repos, or run the IDE inside a virtualenv built from the same lock |
| TypeScript | tsserver | rules_ts outputs live in `bazel-bin`; set `rootDirs` in `tsconfig.json` to include `bazel-bin` |
| Starlark | starpls, or the Bazel plugins above | Completion and go-to-definition in BUILD and `.bzl` files |

#### gopls through Bazel

```bash
# tools/gopackagesdriver.sh (chmod +x)
#!/usr/bin/env bash
exec bazel run -- @rules_go//go/tools/gopackagesdriver "${@}"
```

```json
{
  "go.toolsEnvVars": {
    "GOPACKAGESDRIVER": "${workspaceFolder}/tools/gopackagesdriver.sh"
  },
  "gopls": {
    "build.directoryFilters": ["-bazel-bin", "-bazel-out", "-bazel-testlogs", "-bazel-mono"]
  }
}
```

gopls itself still runs on a host Go install. If you want the editor to use the exact SDK the build uses, set `go.goroot` to the SDK directory under the output base; find it with `ls "$(bazel info output_base)/external" | grep go_sdk` rather than guessing, because the directory name is a canonical repo name.

> **Gotcha.** Excluding the `bazel-*` symlinks from every editor's file watcher is not optional on a large repo. They point into the output base, which contains every external repo and every output. An editor that indexes them burns CPU for minutes and finds three copies of every symbol.

#### Give the IDE its own output base

An IDE that runs Bazel with its own flags (aspects, output groups) shares the server with your terminal unless told otherwise. Each switch then discards the analysis cache. Most plugins let you set startup flags; give them `--output_base=$HOME/.cache/bazel-ide/<repo>`. You lose the shared in-memory graph but keep the shared disk and remote caches.

### Daily bazel, by intent

#### "What is in this repo?"

```bash
bazel query //...                                   # every target
bazel query 'kind(".*_binary", //...)'              # every binary
bazel query 'tests(//...)'                          # every test
bazel query 'kind(rule, //services/...)' --output=label_kind
bazel query //lib/auth:all --output=build           # the BUILD file after macro expansion
bazel query 'attr(visibility, "//visibility:public", //lib/...)'   # public API of lib/
bazel mod graph --depth=1                           # direct external dependencies
bazel query 'kind(".*", @pypi//...)' | head          # what an external repo offers
```

#### "Build or run this"

```bash
bazel build //services/api
bazel build //services/...                          # a subtree
bazel build -- //... -//experimental/...            # everything except a subtree
bazel build //... --keep_going                      # report all failures, not the first
bazel run //services/api -- --port 8080             # args after --
bazel run --run_under='strace -f' //tools/thing     # wrap the binary
bazel run --script_path=/tmp/run_api.sh //services/api   # write a launcher script, don't run
```

`bazel run` holds the server lock while the binary runs. `--script_path` writes a shell script that runs the binary with the right runfiles, then releases the lock, so you can keep building while it runs.

#### "Where did it go?"

```bash
bazel cquery //services/api --output=files                  # output paths
bazel cquery //services/api:image --output=files            # an OCI layout directory
bazel build //services/api --output_groups=+_validation     # extra output groups a rule defines
ls -l bazel-bin/services/api/                               # convenience symlink (last config)
```

#### "What will it run?"

```bash
bazel aquery //services/api --output=text           # every action: argv, inputs, outputs
bazel aquery 'mnemonic("GoLink", //services/api)'   # just the link
bazel build //services/api -s                       # print each command as it runs
```

#### "What state is Bazel in?"

```bash
bazel info                         # everything
bazel info release                 # the actual version running
bazel info output_base
bazel info used-heap-size-after-gc
bazel info server_pid
bazel config                       # configurations seen by this server
```

#### "Clean up"

```bash
bazel shutdown                     # stop the server, free its memory
bazel clean                        # delete outputs; keep fetched repos
bazel clean --expunge              # delete the whole output base
bazel clean --async                # move it aside and delete in the background
du -sh ~/.cache/bazel ~/.cache/bazel-disk   # what the caches cost you
```

> **Note.** `bazel clean` should never be needed for correctness. If a clean fixes a build, some action is non-hermetic: chapter 15 shows how to find it. Keep using clean for disk space, not for "it's acting weird".

## 04 · .bazelrc and the flags that matter

*Flags are where Bazel's speed and correctness live. One checked-in file, named configs for the situational ones, and a reference for the flags you will actually set.*

Most of Bazel's behaviour, and nearly all of its performance, is set by flags. Typed flags drift: five developers end up with five slightly different builds, and none of them share a cache. The fix is boring and complete: every flag lives in a checked-in `.bazelrc`, situational flags are grouped under named configs, and personal settings go in an ignored file.

### How rc files are found and read

Bazel reads rc files in this order. Later files and the command line override earlier ones.

| Order | File | Skip it with | Put here |
|---|---|---|---|
| 1 | System: `/etc/bazel.bazelrc` | `--nosystem_rc` | CI image settings: cache endpoints, runner resources, output roots |
| 2 | Workspace: `%workspace%/.bazelrc` | `--noworkspace_rc` | Everything the team shares. Reviewed like code |
| 3 | Home: `~/.bazelrc` | `--nohome_rc` | Personal defaults for every repo (cache paths) |
| 4 | `--bazelrc=FILE` (startup flag, repeatable) | | One-off experiments; CI variants |
| 5 | The command line | | Last wins |

`--ignore_all_rc_files` skips all of them, which is the quickest way to tell whether a problem comes from configuration or from the code.

```bash
bazel --nohome_rc build //app            # is it my ~/.bazelrc?
bazel --ignore_all_rc_files build //app  # is it any rc file at all?
bazel build //app --announce_rc          # print every rc line that applied, with its source
```

> **Note.** `--nosystem_rc`, `--noworkspace_rc`, `--nohome_rc`, `--bazelrc` and `--ignore_all_rc_files` are **startup** options: they go before the command (`bazel --nohome_rc build`), not after it.

### rc file syntax

Each line is `COMMAND[:CONFIG] FLAGS...`.

```text
# comment lines start with #
startup --host_jvm_args=-Xmx8g          # startup options (before the command)
common  --announce_rc                   # every command that accepts the flag
build   --verbose_failures              # build and every command that inherits from it
test    --test_output=errors            # test and coverage
query   --keep_going                    # just query
build:ci --keep_going                   # only with --config=ci
import  %workspace%/tools/bazel/remote.bazelrc        # must exist
try-import %workspace%/user.bazelrc                   # fine if missing
```

| Element | Meaning |
|---|---|
| `startup` | Options for the Bazel server. Changing one restarts the server |
| `common` | Applies to every command. Since Bazel 7, a `common` flag that a command doesn't support is silently ignored for that command, so it's safe to put shared flags there |
| `always` | Like `common`, but fails commands that don't support the flag. Rarely what you want |
| `build`, `test`, `run`, `query`, `cquery`, `aquery`, `fetch`, `mod`, `coverage`, `info`... | Applies to that command and to commands that inherit from it (table below) |
| `:name` suffix | Only applies with `--config=name`. Configs can include other configs |
| `import PATH` | Read another rc file; error if it doesn't exist |
| `try-import PATH` | Read another rc file if it exists |
| `%workspace%` | Expands to the workspace root. Use it for every repo-relative path |

A `#` starts a comment anywhere on a line, not only at the start, and a `\` at the end of a line continues it on the next.

```text
build --keep_going \
      --verbose_failures     # one logical line, two flags, trailing comment
```

> **Version-sensitive.** Bazel's development branch also accepts `try-import-if-bazel-version >=10.0.0 %workspace%/tools/bazel10.bazelrc` (operators `<`, `<=`, `>`, `>=`, `==`, `!=`, `~`), which lets one repo carry flags for two Bazel majors during an upgrade. It is in the client's rc parser on master; check that your release has it before relying on it (an unknown directive is a parse error).

#### Quoting and whitespace

rc lines are split on whitespace with shell-like quoting. A value with spaces must be quoted inside the file:

```text
build --remote_header="Authorization=Bearer abc123"     # one flag
build --remote_header=Authorization=Bearer abc123       # wrong: two arguments, the second is a target pattern
build --copt=-DGREETING=\"hello\"                       # escaped quotes reach the compiler
```

`~` in a value is expanded only at the start of a path value for flags that take paths (`--disk_cache=~/.cache/bazel-disk`). When in doubt, use an absolute path or `%workspace%`.

#### Platform-specific configs

With `common --enable_platform_specific_config`, Bazel automatically applies `build:linux`, `build:macos`, `build:windows`, `build:freebsd` or `build:openbsd` lines that match the host OS.

```text
common --enable_platform_specific_config
build:linux --sandbox_tmpfs_path=/tmp
build:macos --macos_minimum_os=13.0
build:windows --enable_runfiles
```

#### Configs that include configs

```text
build:cache   --remote_cache=grpcs://bazel-cache.internal
build:ci      --config=cache
build:ci      --remote_upload_local_results
build:release --config=ci
build:release --compilation_mode=opt --stamp
```

`--config=release` expands in place: `ci` (which expands `cache`), then the `release` lines. Expansion is in the position where `--config` appears, so a flag typed after `--config=x` on the command line overrides what `x` set.

### Command inheritance

A flag set for a command also applies to the commands that inherit from it.

| Command | Inherits options from |
|---|---|
| `build` | (base for most commands) |
| `test` | `build` |
| `run` | `build` |
| `coverage` | `test` (and so `build`) |
| `aquery`, `cquery` | `build` |
| `query` | none (its own options only) |
| `fetch`, `vendor`, `mod` | their own options plus `common` |
| `info`, `clean`, `shutdown`, `version` | their own options plus `common` |

Two practical consequences:

- Put build options under `build`, not `test`, so `bazel build` and `bazel test` use **the same configuration**. A flag that is only under `test` changes the configuration hash, and `bazel test` rebuilds everything `bazel build` just built.
- `cquery` and `aquery` inherit `build` options, so they see the same configuration your builds use. `query` doesn't, because it has no configuration.

> **Gotcha.** `test --compilation_mode=dbg` (or any configuration-affecting flag under `test`) silently doubles your build: `bazel build //...` produces `fastbuild` outputs and `bazel test //...` produces `dbg` outputs, each with its own cache entries. Configuration flags belong under `build`. Test-only flags (`--test_output`, `--test_timeout`, `--test_env`) are safe under `test` because they don't change how things are compiled.

### A full team .bazelrc, annotated

```text
# =============================================================================
# .bazelrc: shared by everyone. Personal settings go in user.bazelrc (ignored).
# =============================================================================

# --- every command -----------------------------------------------------------

build:cache --remote_cache=grpcs://bazel-cache.internal
build:cache --remote_cache_compression
build:cache --remote_timeout=60
build --remote_download_toplevel            # Build without the Bytes; default since 7
build --noremote_upload_local_results       # laptops read, CI writes

# --- tests ---------------------------------------------------------------------
test --test_output=errors
test --test_summary=terse
test --test_verbose_timeout_warnings
test --test_env=LANG=C.UTF-8

# --- per OS --------------------------------------------------------------------
build:linux --sandbox_tmpfs_path=/tmp       # private empty /tmp per action

# --- CI ------------------------------------------------------------------------
build:ci --config=cache

```


> **Gotcha.** Never commit credentials to `.bazelrc`. Remote-cache keys belong in `user.bazelrc` on laptops and in a CI variable written to a temp rc file (or `/etc/bazel.bazelrc`) on runners. `--announce_rc` prints rc lines, so a key in a committed rc file also ends up in every CI log.

### Flag reference by category

These are the flags that matter in practice. `bazel help build` lists every one, and `bazel help flags-as-proto` dumps them all in machine-readable form.

#### Correctness and hermeticity

| Flag | Default | Does |
|---|---|---|
| `--incompatible_strict_action_env` | off | Actions get a fixed minimal `PATH` instead of your shell's. Biggest single hermeticity win |
| `--action_env=NAME` / `NAME=value` | | Pass an env var into every action. Each one splits the cache; use sparingly |
| `--host_action_env` | | Same, for exec-configuration actions |
| `--sandbox_default_allow_network` | on | Turn off to deny network in the sandbox unless a target is tagged `requires-network` |
| `--sandbox_tmpfs_path=/tmp` | | Mount an empty tmpfs at that path per action (Linux) |
| `--sandbox_add_mount_pair=SRC[:DST]` | | Expose an extra host path in the sandbox. Breaks hermeticity; last resort |
| `--sandbox_writable_path` | | Make a host path writable inside the sandbox |
| `--spawn_strategy=` | auto | Global strategy order, e.g. `remote,worker,sandboxed,local` |
| `--strategy=MNEMONIC=strategy` | | Strategy for one action type |
| `--incompatible_default_to_explicit_init_py` | off | Python rules stop creating empty `__init__.py` files |

#### Caching

| Flag | Does |
|---|---|
| `--disk_cache=DIR` | Local AC + CAS outside the output base. Survives `bazel clean` and new clones |
| `--experimental_disk_cache_gc_max_size=SIZE` | Cap the disk cache (7.4+). Also `..._gc_max_age`. Name may have lost `experimental_` on your version: `bazel help build \| grep disk_cache` |
| `--repository_cache=DIR` | Downloaded archives by sha256. Share across workspaces |
| `--noremote_accept_cached` | Don't read from the remote cache (debugging) |
| `--remote_upload_local_results` | Upload locally run results to the remote cache (default on; turn off on laptops) |
| `--remote_download_toplevel` | Download only top-level outputs (default since 7) |
| `--remote_download_minimal` | Download nothing unless needed (CI jobs that only test) |
| `--remote_download_all` | Download everything (old behaviour; needed by tools that read `bazel-out` directly) |
| `--remote_download_regex=REGEX` | Also download outputs matching a regex (e.g. `.*\.jar$` for an IDE) |
| `--nocache_test_results` (`-t-`) | Run tests even when cached |

#### Remote

| Flag | Does |
|---|---|
| `--remote_cache=URL` | `grpc://`, `grpcs://`, `http://`, `https://`, or `unix:` |
| `--remote_executor=URL` | Remote execution endpoint (implies a cache at the same endpoint unless `--remote_cache` is set) |
| `--remote_instance_name=NAME` | Instance / namespace on the server |
| `--remote_header=K=V` | Extra header on every request (auth). Also `--remote_cache_header`, `--remote_exec_header` |
| `--remote_timeout=SECONDS` | Per-RPC timeout |
| `--remote_cache_compression` | zstd-compress blobs; the server must support it |
| `--remote_local_fallback` | Run locally if remote execution fails |
| `--remote_max_connections=N` | Connection pool size |
| `--tls_certificate=FILE` | CA certificate for a private TLS endpoint |
| `--tls_client_certificate`, `--tls_client_key` | mTLS to the cache |
| `--credential_helper=HOST=PATH` | External program that supplies auth headers per host (better than static headers) |
| `--bes_backend=URL`, `--bes_results_url=URL` | Stream Build Event Protocol to a server; print a results link |
| `--bes_upload_mode=fully_async` | Don't block the build on BES uploads |
| `--build_metadata=K=V` | Tag the invocation (`ROLE=CI`, `COMMIT_SHA=...`) for result UIs |

#### Tests

| Flag | Does |
|---|---|
| `--test_output=errors\|streamed\|all\|summary` | How much test output reaches the terminal. `streamed` runs tests serially |
| `--test_summary=terse\|short\|detailed` | End-of-run summary |
| `--test_filter=PATTERN` | Passed to the test framework (`TESTBRIDGE_TEST_ONLY`) |
| `--test_arg=ARG` | Extra argument to every test binary |
| `--test_env=NAME[=value]` | Env var for tests; splits the test cache by its value |
| `--test_tag_filters=a,-b` | Run tests with tag `a`, skip tag `b` |
| `--test_size_filters=small,medium` | Filter by size |
| `--test_timeout=60,300,900,3600` | Override timeouts per size, or one value for all |
| `--runs_per_test=N` | Run each test N times (flake hunting) |
| `--flaky_test_attempts=N` | Retry failing tests up to N times; reported as FLAKY |
| `--test_sharding_strategy=explicit\|disabled` | Honour or ignore `shard_count` |
| `--build_tests_only` | With `//...`, build only test targets and their deps |
| `--test_verbose_timeout_warnings` | Warn when a test is far below its timeout |
| `--test_tmpdir=DIR` | Where `$TEST_TMPDIR` points (see version note) |

> **Version-sensitive.** In Bazel 10, a `--test_tmpdir` set in `.bazelrc` resets to the default exec-root temp directory instead of `_tmp` in the workspace (from the 10.0.0rc1 release notes). Check tests that rely on a fixed path before upgrading.

#### Output and progress

| Flag | Does |
|---|---|
| `--color=yes\|no\|auto`, `--curses=yes\|no` | Terminal UI. CI: `--color=yes --curses=no` |
| `--show_progress_rate_limit=SECONDS` | Throttle progress lines (CI logs) |
| `--show_timestamps` | Timestamps on messages |
| `--output_groups=+name` | Also build a named output group |
| `--symlink_prefix=PREFIX` | Change (or with `/`, suppress) the `bazel-*` convenience symlinks |

| `--build_event_json_file=FILE` | Write the Build Event Protocol as JSON lines |
| `--build_event_binary_file=FILE` | Same, binary protobuf |

#### Debugging

| Flag | Does |
|---|---|
| `-s` / `--subcommands` | Print every command as it runs (`=pretty_print` for readability) |
| `--verbose_failures` | Full command line of failing actions |
| `--sandbox_debug` | Keep sandbox directories and print their paths on failure |
| `--explain=FILE` + `--verbose_explanations` | Why each action re-ran |
| `--execution_log_json_file=FILE` | Every spawn with inputs, outputs, env and runner, as JSON (slow; debugging) |
| `--execution_log_compact_file=FILE` | Same information, compact binary format (7.1+); convert with Bazel's execlog tool |
| `--toolchain_resolution_debug=REGEX` | Explain toolchain selection for matching toolchain types |
| `--profile=FILE` | Write the trace profile somewhere specific (one is written by default) |
| `--experimental_profile_include_target_label` | Target labels on profile entries |
| `--noslim_profile` | Keep every event in the profile |
| `--memory_profile=FILE` | Heap usage per phase |
| `--keep_going` (`-k`) | Continue after errors; report them all |
| `--nobuild` | Load and analyse only; execute nothing |

#### Resources

| Flag | Does |
|---|---|
| `--jobs=N` (`-j`) | Concurrent actions. Locally defaults to the CPU count; with remote execution set it to 100–500 |
| `--local_resources=cpu=N` | CPU Bazel may use locally. Accepts `HOST_CPUS*.75` |
| `--local_resources=memory=MB` | RAM Bazel may use locally. Accepts `HOST_RAM*.6` |
| `--local_test_jobs=N` | Concurrent local tests (default: same as jobs) |
| `--worker_max_instances=N` | Persistent workers per mnemonic |
| `--discard_analysis_cache` | Drop analysis data once execution starts. Lower peak memory, slower next build |
| `--nokeep_state_after_build` | Discard in-memory state after the command. CI only |

> **Version-sensitive.** `--local_resources=cpu=` and `--local_resources=memory=` replaced the older `--local_cpu_resources` and `--local_ram_resources` flags. If an old rc file uses those, `bazel help build | grep local_` shows what your version accepts.

#### Startup options

These go before the command and restart the server when they change.

| Option | Does |
|---|---|
| `--output_base=DIR` | Per-workspace state directory. A second output base means a second, independent server |
| `--output_user_root=DIR` | Parent of all output bases and the install base. Point CI at a persistent volume |
| `--host_jvm_args=-Xmx12g` | JVM heap for the server. Raise it for large repos |
| `--max_idle_secs=N` | Server shuts down after N idle seconds (default 3 hours) |
| `--batch` | No server; one-shot JVM. Slower, used in some hermetic CI setups |
| `--bazelrc=FILE` | Additional rc file |
| `--nohome_rc`, `--noworkspace_rc`, `--nosystem_rc`, `--ignore_all_rc_files` | Skip rc files |
| `--unlimit_coredumps` | Allow core dumps from the server |

> **Gotcha.** Two clients with different startup options against the same output base fight: the second one restarts the server, killing the first one's command. CI jobs that set `--host_jvm_args` differently from a pre-warm step lose their warm server every time. Put startup options in one place per environment.

### Reading what actually applied

```bash
# every rc line that applied, in order, with its file
bazel build //app --announce_rc 2>&1 | grep -E '^INFO: (Reading|Found)'

# the effective option values for this command (canonical form)
bazel build //app --nobuild --announce_rc
bazel info --show_make_env | head        # make variables visible to genrules

# what a configuration contains
bazel config                               # list configurations this server has seen
bazel config 0a1b2c3                       # all options in one, by short hash
bazel config 0a1b2c3 4d5e6f7               # diff two

# every flag Bazel knows, as data (tooling, linting rc files)
bazel help flags-as-proto | base64 -d > /tmp/flags.pb
```

`bazel help flags-as-proto` prints a base64-encoded `FlagCollection` protobuf: every flag's name, type, documentation, which commands accept it and whether it's deprecated. IDE plugins use it for rc-file completion; you can use it to fail CI when a committed `.bazelrc` uses a flag your Bazel version no longer has.

`bazel config` with two hashes is the quickest way to answer "why is this target built twice": the diff names the option that differs between the two copies.

### Keeping the IDE, scripts and terminal aligned

The in-memory analysis cache survives only while every client uses the same configuration-affecting flags. Each time a different set of flags arrives, Bazel prints:

```text
INFO: Build option --compilation_mode has changed, discarding analysis cache.
```

and the next no-op build costs a full analysis.

| Rule | Why |
|---|---|
| All shared flags in `.bazelrc`, none in scripts | A script that adds `--copt=-g` changes the configuration |
| Scripts that need different flags use `--config=NAME` | The difference is named and reviewed |
| Tools that must differ get their own `--output_base` | A separate server with its own cache; the disk and remote caches are still shared |
| IDE plugins point at the same `.bazelrc` | Most do by default; check the plugin's "additional flags" setting is empty |
| CI uses `--config=ci`, and `ci` only adds non-configuration flags where possible | `--keep_going`, `--color`, BES and upload flags don't change action keys |

```bash
# a pre-commit hook that doesn't disturb your terminal's server
bazel --output_base="$HOME/.cache/bazel-hooks/$(basename "$PWD")" run //:format.check
```

> **Field note.** When "the build is slow" turns out to be "the analysis cache is discarded every other command", the fix takes minutes and pays forever. Grep your terminal history for `discarding analysis cache` before you look at anything else.

### rc-file hygiene checklist

- [ ] `.bazelrc` is committed; `user.bazelrc` is in `.gitignore` and loaded with `try-import` at the end.
- [ ] `common --announce_rc` is on, so every log shows its configuration.
- [ ] Configuration-affecting flags are under `build`, never under `test` only.
- [ ] Every repo-relative path uses `%workspace%`.
- [ ] No credentials in committed files.
- [ ] `--config=ci` exists and CI uses nothing else on the command line except targets.
- [ ] Every flag with `experimental_` in its name has a comment saying why and on which version it was checked.
- [ ] CI fails if a committed rc file uses an unknown flag. Any cheap command with `--config=ci` does it, for example `bazel build --nobuild --config=ci //:gazelle`, because unknown flags are errors.


## 05 · Bzlmod and dependencies

*MODULE.bazel in depth: version resolution, extensions, the lockfile, overrides, private registries, Renovate, and the migrations from WORKSPACE and from Bazel 8 to 9.*

Bazel 9 has one dependency system: Bzlmod. `MODULE.bazel` names the modules you depend on, Bazel resolves one version of each with minimal version selection, module extensions turn language lockfiles into repos, and the result is pinned in `MODULE.bazel.lock`. `WORKSPACE` support is gone, not deprecated.

### The pieces

| Piece | What it is | Where |
|---|---|---|
| **Module** | A project with a name, a version and a `MODULE.bazel` | Your repo is the **root module**; every `bazel_dep` is another |
| **Registry** | An index of modules and versions: metadata, `MODULE.bazel` files, source URLs and patches | Bazel Central Registry (`bcr.bazel.build`) by default; your own mirror or private registry |
| **Module extension** | Starlark that runs after resolution and creates repos from tags modules declare | `go_deps`, `pip`, `npm`, `oci`, `go_sdk`, `llvm` |
| **Repo rule** | A Starlark function that creates one external repo (download, extract, generate BUILD files) | `http_archive`, `git_repository`, rules' own |
| **Lockfile** | `MODULE.bazel.lock`: resolved versions, registry file hashes, extension results | Committed next to `MODULE.bazel` |

```text
MODULE.bazel ──▶ registry lookups ──▶ dependency graph ──▶ MVS: one version per module
      │                                                          │
      └── use_extension tags ───────────────▶ extensions run ◀───┘
                                                   │
                                     MODULE.bazel.lock  +  repos (fetched lazily)
```

### MODULE.bazel directives

#### `module()`

```starlark
module(
    name = "acme_mono",
    version = "0.0.0",                       # irrelevant for a root module that nobody depends on
    compatibility_level = 1,                 # bump only on breaking changes for consumers
    bazel_compatibility = [">=9.0.0"],       # fail early on older Bazel
)
```

Only meaningful for a module others depend on. The root module's `name` is used as its apparent repo name inside its own BUILD files (`@acme_mono//...` also works, `//...` is normal).

#### `bazel_dep()`

```starlark
bazel_dep(name = "rules_go", version = "0.64.2")
bazel_dep(name = "gazelle", version = "0.54.0", repo_name = "bazel_gazelle")   # keep an old apparent name
bazel_dep(name = "buildifier_prebuilt", version = "10.1.0", dev_dependency = True)
bazel_dep(name = "protobuf", version = "...", max_compatibility_level = 2)
```

| Attribute | Does |
|---|---|
| `name`, `version` | The module and the minimum version you need |
| `repo_name` | The apparent name your BUILD files use. Defaults to `name`. Useful while migrating from WORKSPACE names such as `io_bazel_rules_go` |
| `dev_dependency = True` | Only applies when this module is the root. Your tools and test deps don't become your consumers' deps |
| `max_compatibility_level` | Accept a dependency across compatibility levels during a migration |

#### `use_extension()` and `use_repo()`

```starlark
go_deps = use_extension("@gazelle//:extensions.bzl", "go_deps")
go_deps.from_file(go_mod = "//:go.mod")
go_deps.module_override(path = "github.com/foo/bar", patches = ["//third_party:bar.patch"])
use_repo(go_deps, "com_github_google_uuid", "org_golang_x_sync", uuid = "com_github_google_uuid")
```

- `use_extension` returns a proxy; calling methods on it records **tags** for that extension.
- An extension sees the tags from **every** module in the graph that uses it, which is how `go_deps` merges Go dependencies across modules.
- `use_repo` makes the extension's repos visible to the current module, optionally under another name (`uuid = ...`). Repos not listed are invisible to your BUILD files.
- `use_extension(..., dev_dependency = True)` makes all its tags dev-only.

> **Field note.** Don't maintain `use_repo` lists by hand. `bazel mod tidy` rewrites them to exactly the repos the extension says you use (extensions report that through `extension_metadata`), and formats `MODULE.bazel` as a side effect.

#### `use_repo_rule()`

For a one-off archive that isn't a module:

```starlark
http_archive = use_repo_rule("@bazel_tools//tools/build_defs/repo:http.bzl", "http_archive")
http_file = use_repo_rule("@bazel_tools//tools/build_defs/repo:http.bzl", "http_file")

http_archive(
    name = "pgv_src",
    urls = ["https://github.com/bufbuild/protoc-gen-validate/archive/refs/tags/v1.2.1.tar.gz"],
    integrity = "sha256-REPLACE_WITH_SRI_HASH",
    strip_prefix = "protoc-gen-validate-1.2.1",
    build_file = "//third_party:pgv.BUILD",
)

http_file(
    name = "kubectl_linux_amd64",
    urls = ["https://dl.k8s.io/release/v1.34.1/bin/linux/amd64/kubectl"],
    sha256 = "REPLACE_WITH_SHA256",
    executable = True,
)
```

Every download needs a hash (`sha256` or SRI `integrity`). Without one, Bazel downloads it every time the repo is re-fetched, prints a warning with the hash it saw, and the repository cache can't serve it.

#### `register_toolchains()` and `register_execution_platforms()`

```starlark
register_toolchains("@llvm_toolchain//:all")
register_toolchains("//toolchains:all", dev_dependency = True)
register_execution_platforms("//platforms:rbe", dev_dependency = True)
```

Toolchains registered by the root module take priority over those registered by dependencies. Chapter 08 covers resolution.

#### `include()`

```starlark
# MODULE.bazel
module(name = "acme_mono")
include("//tools/deps:go.MODULE.bazel")
include("//tools/deps:python.MODULE.bazel")
include("//tools/deps:images.MODULE.bazel")
```

Splits a long `MODULE.bazel` into segments owned by different teams (pair it with `CODEOWNERS`). The included files must end in `.MODULE.bazel`. `include()` is available since Bazel 7.2 and is meant for the root module; a module published to a registry generally can't use it, because consumers fetch only its `MODULE.bazel`.

#### `override_repo()` and `inject_repo()`

```starlark
# replace a repo an extension creates with one of your own
go_deps = use_extension("@gazelle//:extensions.bzl", "go_deps")
override_repo(go_deps, com_github_foo_bar = "my_patched_bar")

# make one of your repos visible inside an extension
inject_repo(some_ext, "my_config_repo")
```

> **Version-sensitive.** `override_repo` and `inject_repo` arrived with Bazel 8. On older versions the only way to replace an extension's repo was an extension-specific override tag (`go_deps.module_override`, `pip.override`...). Those still work and are usually clearer.

### Version resolution

#### Minimal version selection

Each module states the **minimum** version of each dependency it needs. Bazel picks, for each module, the **highest** of those minimums. Nothing newer than someone asked for is ever selected, and there is no range syntax.

```text
acme_mono      needs rules_go 0.60.0, rules_python 2.4.2
rules_oci      needs rules_go 0.62.0   (hypothetical)
gazelle        needs rules_go 0.64.2
                          ──────────▶  selected: rules_go 0.64.2
```

| Consequence | What to do |
|---|---|
| Your `bazel_dep` version is a floor, not a pin | A transitive dep can raise it. `bazel mod explain rules_go` shows who did |
| Upgrades are explicit: nothing moves until a `MODULE.bazel` somewhere asks | Renovate (below) is the "somewhere" for your root module |
| A dependency's bump can silently raise a version you rely on | `common --check_direct_dependencies=error` fails when the resolved version of a direct dep differs from what you wrote |

#### Compatibility levels

A module's `compatibility_level` marks breaking changes. Two versions with different levels can't be resolved into one; the build fails with a compatibility-level error. Fix it by upgrading the module that pins the old level, or temporarily with `max_compatibility_level` or `multiple_version_override`.

#### Yanked versions

Registries can **yank** a version (for a security or correctness bug). Selecting a yanked version is an error that names the reason. `--allow_yanked_versions=module@version` lets you proceed while you upgrade.

### Overrides

Overrides only take effect in the **root** module. A dependency's overrides are ignored, which keeps the graph predictable.

| Override | Use | Example |
|---|---|---|
| `single_version_override` | Pin a version, switch registry, or patch | Carry a fix until upstream releases it |
| `multiple_version_override` | Let several versions coexist | Two compatibility levels during a long migration. Rare |
| `archive_override` | Source from a URL + integrity hash | A fork published as a tarball |
| `git_override` | Source from a Git commit | Testing an unreleased fix |
| `local_path_override` | Source from a local directory | Developing a rule set beside its consumer |

```starlark
single_version_override(
    module_name = "rules_go",
    version = "0.64.2",
    patches = ["//third_party/patches:rules_go-cgo-fix.patch"],
    patch_strip = 1,
)

git_override(
    module_name = "rules_oci",
    remote = "https://github.com/bazel-contrib/rules_oci.git",
    commit = "0123456789abcdef0123456789abcdef01234567",
)

archive_override(
    module_name = "acme_rules",
    urls = ["https://artifacts.internal/acme_rules/acme_rules-1.4.0.tar.gz"],
    integrity = "sha256-REPLACE",
    strip_prefix = "acme_rules-1.4.0",
)

local_path_override(module_name = "acme_rules", path = "../acme_rules")
```

> **Gotcha.** `git_override` and `local_path_override` modules aren't in the registry, so their versions don't participate in MVS: whatever is at that commit or path wins. A `local_path_override` committed by accident makes everyone else's build fail with a missing directory. Keep local overrides in a `.MODULE.bazel` segment you don't commit, or in `user.bazelrc` via `--override_module=acme_rules=../acme_rules`.

`--override_module=NAME=PATH` and `--override_repository=NAME=PATH` are the command-line equivalents for local development, and they don't touch `MODULE.bazel`.

### The lockfile

`MODULE.bazel.lock` records the resolved graph, the hash of every registry file Bazel read, and the output of each module extension (with the inputs it depended on). It makes builds reproducible and lets Bazel skip resolution and extension evaluation when nothing changed.

| `--lockfile_mode` | Behaviour | Use |
|---|---|---|
| `update` (default) | Use the lockfile; rewrite it when inputs change | Developer machines |
| `refresh` | Like `update`, but also re-check mutable registry data (yanked versions) | Occasionally, or in a scheduled job |
| `error` | Fail if the lockfile is missing or out of date | **CI** |
| `off` | Ignore it entirely | Debugging only |

```bash
bazel mod deps --lockfile_mode=update      # regenerate the lockfile without building
git diff --stat MODULE.bazel.lock          # review what moved
```

> **Gotcha.** The lockfile contains extension results, which can depend on the host (an extension that detects the OS, for example). Extensions declare that through `extension_metadata` and the lockfile stores per-platform entries. If two developers on Linux and macOS keep rewriting the lockfile at each other, an extension in the graph isn't declaring its OS dependence properly; `git diff` on the lockfile names it.

Resolve lockfile merge conflicts by taking either side and regenerating: `git checkout --theirs MODULE.bazel.lock && bazel mod deps --lockfile_mode=update`. Never hand-merge it.

### Registries

#### The Bazel Central Registry

[registry.bazel.build](https://registry.bazel.build/) is the browsable front end. The data is a Git repo, `bazelbuild/bazel-central-registry`, served at `https://bcr.bazel.build`. Every module version is reviewed and tested on a presubmit matrix before it's merged.

#### Registry layout

A registry is a directory tree served over HTTPS or read from disk:

```text
registry/
├── bazel_registry.json                 # optional: mirrors, module_base_path for local_path sources
└── modules/
    └── acme_rules/
        ├── metadata.json               # versions, maintainers, yanked_versions
        └── 1.4.0/
            ├── MODULE.bazel            # exactly the module's MODULE.bazel at that version
            ├── source.json             # where to get the source: url + integrity + strip_prefix
            ├── patches/                # optional patches applied after download
            │   └── fix-visibility.patch
            └── presubmit.yml           # BCR CI config (ignored by Bazel itself)
```

```json
{
  "url": "https://artifacts.internal/acme_rules/acme_rules-1.4.0.tar.gz",
  "integrity": "sha256-REPLACE",
  "strip_prefix": "acme_rules-1.4.0",
  "patches": { "fix-visibility.patch": "sha256-REPLACE" },
  "patch_strip": 1
}
```

#### Private and mirrored registries

```text
# .bazelrc: order matters. The first registry that has a module wins.
common --registry=https://bazel-registry.internal/
common --registry=https://bcr.bazel.build/
```

- Setting `--registry` replaces the default, so list the BCR explicitly if you still want it.
- A private registry is the clean way to share internal rule sets across repos: tag a release, add `modules/acme_rules/<version>/`, consumers write a normal `bazel_dep`.
- For an air-gapped site, mirror the whole BCR Git repo and serve it internally, then point `--registry` only at the mirror. Module sources still come from the URLs in `source.json`, so pair the mirror with URL rewriting (`--downloader_config`) or `bazel vendor` (chapter 13).
- A registry on local disk works too: `common --registry=file:///opt/bazel-registry`.

> **Version-sensitive.** `%workspace%` inside `--registry=file://...` (a registry checked into the repo) is supported in recent releases. If your version rejects it, use an absolute path from `/etc/bazel.bazelrc` or `user.bazelrc`.

### `bazel mod`: inspect and repair the graph

| Command | Answers |
|---|---|
| `bazel mod graph` | The whole resolved graph |
| `bazel mod graph --depth=1` | Direct dependencies only |
| `bazel mod graph --output=json` | Same, for scripts |
| `bazel mod deps rules_go` | One module's direct deps |
| `bazel mod explain rules_python` | Every module that asked for it, at which version, and which version won |
| `bazel mod path @rules_oci` / `all_paths` | How a module enters the graph |
| `bazel mod show_repo @pypi` | Where a repo comes from and its full definition |

```bash
bazel mod explain protobuf --verbose

# "what repos does go_deps give me, and which am I missing?"

```

### Writing a small module extension

When a tool isn't on the BCR and you want the same pinned binary on every platform, an extension with a tag class keeps `MODULE.bazel` declarative.

```starlark
# tools/binaries.bzl
load("@bazel_tools//tools/build_defs/repo:http.bzl", "http_file")

_binary = tag_class(attrs = {
    "name": attr.string(mandatory = True),
    "url": attr.string(mandatory = True),
    "sha256": attr.string(mandatory = True),
})

def _binaries_impl(module_ctx):
    for mod in module_ctx.modules:
        for b in mod.tags.binary:
            http_file(name = b.name, urls = [b.url], sha256 = b.sha256, executable = True)
    # results depend only on the tags: no need to store them in the lockfile
    return module_ctx.extension_metadata(reproducible = True)

binaries = module_extension(
    implementation = _binaries_impl,
    tag_classes = {"binary": _binary},
)
```

```starlark
# MODULE.bazel
binaries = use_extension("//tools:binaries.bzl", "binaries")
binaries.binary(
    name = "helm_linux_amd64",
    url = "https://get.helm.sh/helm-v3.19.0-linux-amd64.tar.gz",
    sha256 = "REPLACE",
)
use_repo(binaries, "helm_linux_amd64")
```

| `module_ctx` member | Use |
|---|---|
| `module_ctx.modules` | Every module that used the extension, root first; each has `.name`, `.version`, `.is_root`, `.tags` |
| `module_ctx.os` | Host OS and arch, for extensions that must differ by platform (declare it in metadata) |
| `module_ctx.download`, `.execute`, `.read`, `.path` | Like repository_ctx: fetch metadata, run a resolver |
| `module_ctx.extension_metadata(...)` | `reproducible = True` to keep results out of the lockfile; `root_module_direct_deps` / `..._dev_deps` so `bazel mod tidy` knows what to `use_repo` |

> **Field note.** Most of the time you don't need an extension: `use_repo_rule(http_file)` five times is fine. Write one when the same tags must be merged across several modules, or when the repos are computed from a lockfile (that is what `go_deps` and `pip.parse` are).

### Keeping dependencies current: Renovate

Renovate understands Bazel natively:

| Manager | Updates |
|---|---|
| `bazel-module` | `bazel_dep` versions in `MODULE.bazel` (and segments), `git_override` commits, `archive_override` URLs |
| `bazelisk` | The version in `.bazelversion` |
| `bazel` | Legacy WORKSPACE `http_archive` rules (irrelevant on Bazel 9) |

```json
{
  "extends": ["config:recommended"],
  "packageRules": [
    {
      "matchManagers": ["bazel-module"],
      "groupName": "bazel modules",
      "schedule": ["before 6am on monday"]
    },
    {
      "matchManagers": ["bazelisk"],
      "matchUpdateTypes": ["major"],
      "dependencyDashboardApproval": true
    }
  ],
  "postUpgradeTasks": {
    "commands": ["bazel mod deps --lockfile_mode=update", "bazel mod tidy"],
    "fileFilters": ["MODULE.bazel", "MODULE.bazel.lock"]
  }
}
```

> **Gotcha.** A Renovate MR that bumps `MODULE.bazel` without updating `MODULE.bazel.lock` fails CI under `--lockfile_mode=error`. `postUpgradeTasks` (above) needs Bazel on the Renovate runner and an allow-list entry for those commands in self-hosted Renovate. Without that, the alternative is a CI job on Renovate branches that regenerates and pushes the lockfile.

Go, Python and JS dependencies are updated through their own lockfiles (`go.mod`, `requirements.in`, `pnpm-lock.yaml`) by Renovate's normal managers. Bazel picks them up through the extensions; add `bazel mod tidy` and Gazelle to the post-upgrade step so `use_repo` lists and BUILD files follow.

### Migrating WORKSPACE to Bzlmod

Bazel 9 can't read `WORKSPACE` at all, so the migration happens on Bazel 8, where `--enable_workspace` still works and both systems can run side by side (`WORKSPACE.bzlmod` and the hybrid mode).

#### The order that works

1. **Upgrade to the newest Bazel 8** with your WORKSPACE build still green.
2. **Create `MODULE.bazel`** next to `WORKSPACE`. Leave `WORKSPACE` in place.
3. **Run the migration helper** from the BCR repo: `tools/migrate_to_bzlmod.py` in a checkout of `bazel-central-registry`, run from your workspace with the targets to build (its `--help` lists the flags). It tries a build, finds which repo is missing under Bzlmod, adds the `bazel_dep` or `use_repo_rule`, and repeats. It reports what it couldn't translate.
4. **Move rule sets first**: every `http_archive` for `rules_*` becomes a `bazel_dep`. Use `repo_name` to keep old apparent names (`io_bazel_rules_go`) until BUILD files are updated, then remove it.
5. **Move language deps to extensions**: `go_repository` macros to `go_deps.from_file`, `pip_parse` to `pip.parse`, `npm_translate_lock` to the `npm` extension.
6. **Leftover one-offs** become `use_repo_rule(http_archive)` or a small extension.
7. **Build with `--noenable_workspace`** until it's green. Then delete `WORKSPACE`, `WORKSPACE.bzlmod` and the `--enable_workspace` flag.
8. **Upgrade to Bazel 9.**

| WORKSPACE pattern | Bzlmod equivalent |
|---|---|
| `http_archive(name = "rules_go", ...)` + `go_rules_dependencies()` + `go_register_toolchains()` | `bazel_dep(name = "rules_go", ...)` + `go_sdk` extension |
| `gazelle_dependencies()` + `go_repository(...)` per dep | `go_deps.from_file(go_mod = "//:go.mod")` |
| `pip_parse(name = "pypi", ...)` + `install_deps()` | `pip.parse(hub_name = "pypi", ...)` + `use_repo(pip, "pypi")` |
| `container_pull` (rules_docker) | `oci.pull` (rules_oci) |
| `register_toolchains(...)` in WORKSPACE | `register_toolchains(...)` in MODULE.bazel |
| `bind()` | Gone. Use `alias` targets |
| `local_repository` | `local_path_override` (for modules) or `use_repo_rule(local_repository)` |
| A `*_deps()` macro from a rule set | Usually nothing: the module declares its own deps |

> **Gotcha.** Labels that hard-code WORKSPACE repo names break silently in `.bzl` and BUILD files that Bazel doesn't evaluate in your build (an unused macro, a script calling `bazel build @io_bazel_rules_go//...`). `grep -rn '@io_bazel_rules\|@bazel_gazelle\|@com_google_protobuf' --include='*.bzl' --include='BUILD*' --include='*.sh' .` before you delete `WORKSPACE`.

### Bazel 8 to 9

Bazel 9 is mostly the removal of things Bazel 8 deprecated. If you are clean on 8 with `--noenable_workspace` and explicit loads, 9 is a version bump.

| Change | Symptom on 9 | Fix |
|---|---|---|
| WORKSPACE removed | `WORKSPACE` ignored; external repos it defined are missing | Finish the migration above, on Bazel 8 |
| Language rules no longer autoloaded | `name 'cc_library' is not defined` (or `java_library`, `py_binary`, `sh_test`, `proto_library`...) | Add `load()` statements. `buildifier -r -lint=fix .` adds most of them; buildozer `new_load` does the rest |
| C++ rules live only in `rules_cc` | Same as above for `cc_*` | `bazel_dep(name = "rules_cc", version = "0.2.26")` and `load("@rules_cc//cc:cc_library.bzl", "cc_library")` |
| Native providers moved too | `name 'CcInfo' is not defined` in `.bzl` files | Load them from the rule set (`@rules_cc//cc/common:cc_info.bzl`) |

On Bazel 8, `--incompatible_autoload_externally` controlled which symbols were still loaded automatically; setting it to an empty value there reproduces Bazel 9's behaviour, so you can finish the load migration before upgrading.

#### Changes from Bazel 7 to 8 that bite during the same upgrade

| Change | Symptom | Fix |
|---|---|---|
| Canonical repo names use `+` instead of `~` | Scripts or runfiles paths with `rules_go~` break | Use apparent names and runfiles libraries; never parse canonical names |
| WORKSPACE disabled by default | External repos missing | `--enable_workspace` temporarily, then migrate |
| `glob()` that matches nothing is an error by default | `glob pattern '...' didn't match anything` | Fix the pattern, or `allow_empty = True` where empty is legitimate |
| Legacy external runfiles off by default | A test can't find a file under `external/...` in runfiles | Use the runfiles library (`Rlocation("repo/path")`) |

#### Rehearse the next upgrade

```bash
# run the next major against the whole repo without touching .bazelversion
USE_BAZEL_VERSION=10.0.0rc1 bazel build --nobuild //...    # loading + analysis only
USE_BAZEL_VERSION=10.0.0rc1 bazel test //...

# try every flag the next major will flip, on your current version
# (bazelisk reads the release's list of incompatible flags)
bazelisk --migrate build //...
```

`bazelisk --migrate` builds with each pending `--incompatible_*` flag one at a time and reports which ones break your repo. Run it in a scheduled CI job against the current LTS, and the next upgrade arrives as a list of known fixes.

> **Version-sensitive.** The 10.0.0rc1 notes list several `--incompatible_*` flags already flipped (for example `--incompatible_no_implicit_file_export` and `--incompatible_check_testonly_for_output_files`) and more scheduled for later. Read the release notes for each major you cross, and upgrade one major at a time.

### Dependency hygiene checklist

- [ ] `MODULE.bazel.lock` is committed and CI runs with `--lockfile_mode=error`.
- [ ] Every `http_archive` and `http_file` has an `integrity` or `sha256`.
- [ ] Tools and test-only modules are `dev_dependency = True`.
- [ ] `bazel mod tidy` leaves `MODULE.bazel` unchanged in CI.
- [ ] `common --check_direct_dependencies=error` (or `warning` while you clean up) catches silent transitive bumps.
- [ ] No `local_path_override` or `git_override` in the committed root module without a comment and an owner.
- [ ] Renovate updates `MODULE.bazel` and `.bazelversion`, and the lockfile follows in the same MR.
- [ ] A scheduled job runs `bazelisk --migrate` so the next major is a known list, not a surprise.


## 06 · BUILD files and Gazelle

*The dependency graph is the product. Package design, visibility, globs and their traps, and Gazelle doing the bookkeeping so nobody hand-edits deps.*

### Packages: the unit of everything

A package is a directory that contains a `BUILD.bazel` (or `BUILD`) file, plus every subdirectory below it that does not have one. Packages decide four things at once:

| What the package boundary controls | Consequence |
|---|---|
| **Label namespace** | `//lib/auth:token.go` only exists if `lib/auth` is a package. Move the BUILD file and every label to that file changes. |
| **Glob reach** | `glob()` never crosses into a subpackage. Add a BUILD file to a subdirectory and its files silently drop out of the parent's glob. |
| **Visibility** | `//visibility:private` means "this package". A smaller package is a tighter wall. |
| **Invalidation** | Loading re-evaluates a whole BUILD file when any file it globs changes. One BUILD file per directory keeps that cheap. |

Use `BUILD.bazel`, not `BUILD`. It never collides with a `build/` directory on case-insensitive filesystems (macOS, Windows), and editors can recognise it. Gazelle reads both and writes whichever you tell it with `# gazelle:build_file_name BUILD.bazel,BUILD`.

#### Granularity: how small is small enough

The rule is **one library target per directory, one directory per cohesive unit of code**. That matches Go's package model, Python's module layout and TypeScript projects, so Gazelle can generate it. It also means a change to one file only invalidates the targets that contain that file and their reverse dependencies.

| Shape | Effect | Verdict |
|---|---|---|
| One target for the whole repo (`//:everything`) | Every edit rebuilds and retests everything; no visibility at all | Never |
| One target per top-level service, globbing `**` | Coarse caching; tests can't run per module; cycles hidden inside one target | Migration stepping stone only |
| One target per directory | Fine-grained caching; Gazelle-friendly; visibility per directory | **Default** |
| One target per file (Gazelle `file` mode for Python or proto) | Finest caching; noisy BUILD files; larger analysis graph | When a directory has unrelated files and you can't split it |

> **Field note.** The fastest way to measure whether granularity is hurting you: change one leaf file and run `bazel test //... --explain=/tmp/x.txt --verbose_explanations`. Count how many actions re-ran. If a one-line change in a utility package reruns half the test suite, you have a dependency hub. `bazel query 'rdeps(//..., //lib/util)' | wc -l` will confirm it.

#### Breaking up a dependency hub

A "util" or "common" package that everything depends on makes every change to it a full rebuild. Split it by what callers actually import:

```bash
# who uses which file of the hub (Go example: a file per concern)
for f in $(bazel query 'labels(srcs, //lib/util)' --output=label); do
  echo "$f $(bazel query "rdeps(//..., $f, 1)" 2>/dev/null | wc -l)"
done | sort -k2 -n

# after splitting into //lib/util/strings, //lib/util/retry, ...:
# leave an alias so callers keep building, then migrate them with buildozer
```

```starlark
# lib/util/BUILD.bazel during the migration
alias(
    name = "util",
    actual = "//lib/util/retry",
    deprecation = "Depend on //lib/util/retry or //lib/util/strings directly.",
    visibility = ["//visibility:public"],
)
```

The `deprecation` attribute prints a warning on every build of a target that depends on it, which turns the migration into a visible to-do list instead of a wiki page.

### Visibility patterns

Visibility is the only architecture enforcement Bazel gives you for free. A dependency that violates it fails at analysis time, before anything compiles.

| Value | Who can depend on the target |
|---|---|
| `//visibility:private` | Targets in the same package (the default if nothing else is set) |
| `//visibility:public` | Everyone, including other modules |
| `//foo/bar:__pkg__` | Targets in package `//foo/bar` only |
| `//foo:__subpackages__` | `//foo` and every package below it |
| `//teams:payments` | Members of a `package_group` |

#### package_group for team or layer boundaries

```starlark
# teams/BUILD.bazel
package_group(
    name = "payments",
    packages = [
        "//services/payments/...",
        "//lib/billing/...",
        "-//lib/billing/experimental/...",   # exclusion
    ],
)

package_group(
    name = "platform",
    packages = ["//lib/...", "//tools/..."],
    includes = [":payments"],                # union with another group
)
```

```starlark
# lib/billing/ledger/BUILD.bazel
package(default_visibility = ["//teams:payments"])

go_library(
    name = "ledger",
    srcs = ["ledger.go"],
    importpath = "github.com/acme/mono/lib/billing/ledger",
)
```

`package(default_visibility = ...)` applies to every target in the package that doesn't set its own `visibility`. Set it to private in shared library packages, and widen per target. A package that defaults to public can never be narrowed later without fixing every consumer at once.

#### Layering rules that hold

```text
services/*   may depend on   lib/*         (lib targets list //services:__subpackages__)
lib/*        may depend on   lib/*         (within reason; avoid cycles)
lib/*        never depends on services/*   (services never widen to lib)
*/internal/* visible only to its parent    (//services/api:__subpackages__)
tools/*      visible to everything, cfg = exec only in practice
```

Encode the top line with visibility and check the third line in CI:

```bash
# fails the job if any lib target depends on a service
test -z "$(bazel query 'kind(".*_library", //lib/...) intersect rdeps(//lib/..., //services/...)' 2>/dev/null)"
```

> **Gotcha.** Visibility is checked on the **dependency edge**, not on the label you type. `bazel build //lib/billing/ledger` works for anyone. Only a target that lists it in `deps` (or `data`, `srcs`, any label attribute) is checked. Don't treat visibility as access control on who can build something.

#### testonly

```starlark
go_library(
    name = "fakes",
    srcs = ["fake_clock.go"],
    testonly = True,                 # only tests and other testonly targets may depend on this
    visibility = ["//visibility:public"],
)
```

`testonly = True` stops fake implementations and fixtures from leaking into production binaries. Tests are implicitly testonly. Any non-test target that depends on a testonly target fails at analysis time.

#### .bzl load visibility

A `.bzl` file can restrict who may `load()` it:

```starlark
# tools/internal/defs.bzl
visibility(["//tools/..."])          # only BUILD/.bzl files under //tools may load this
```

Use it for macros and helpers you intend to keep private to a tooling package, so nobody builds on an internal API you want to change.

### glob() in practice

```starlark
py_library(
    name = "worker",
    srcs = glob(
        ["worker/**/*.py"],
        exclude = [
            "worker/**/*_test.py",
            "worker/scratch/**",
        ],
    ),
)
```

| Behaviour | Detail |
|---|---|
| Scope | Matches files in this package only. Stops at any subdirectory with its own BUILD file. |
| Patterns | `*` matches within one path segment; `**` matches any number of segments. |
| Ordering | Results are sorted, so the label list is deterministic. |
| Generated files | Never matched. A glob only sees source files on disk. |
| Directories | Excluded by default (`exclude_directories = 1`). |
| Empty result | An error by default since Bazel 8 (`--incompatible_disallow_empty_glob`). Pass `allow_empty = True` where empty is legitimate. |

> **Version-sensitive.** Bazel 8 flipped `--incompatible_disallow_empty_glob` to true. A glob that matched nothing used to return `[]` silently; now the package fails to load. This is a common first error after an upgrade from 7. Fix the pattern, or add `allow_empty = True` only if empty really is valid.

> **Gotcha.** A glob that drops files is worse than one that fails. When someone adds a BUILD file to `worker/handlers/`, the parent's `worker/**/*.py` glob stops seeing `worker/handlers/*.py`. The build may still pass if nothing imported them through the parent target, and the files quietly stop being tested. Gazelle-generated explicit lists avoid this class of bug entirely.

#### When to glob and when to list

| Use `glob()` | Use explicit lists |
|---|---|
| Test data directories (`testdata/**`) | Source files of libraries (let Gazelle write them) |
| Static assets, templates, migrations | Anything a reviewer needs to see change in a diff |
| Vendored third-party trees with a hand-written BUILD file | Packages with mixed test and non-test files |

### The built-in rules you keep using

Since Bazel 9, language rules need a `load()`. These general rules remain built in and need no load.

#### filegroup

```starlark
filegroup(
    name = "migrations",
    srcs = glob(["migrations/*.sql"]),
    visibility = ["//services/api:__pkg__"],
)
```

A named set of files. It produces no actions. Use it to give other packages a stable label for data files, or to group outputs: `filegroup(name = "bins", srcs = [":api", ":worker"])` and then `bazel build //services:bins`.

`output_group` picks a named output group from a rule, for example the debug symbols or the type-checking output of a target: `filegroup(name = "api_debug", srcs = [":api"], output_group = "...")`. Group names depend on the rule; read them with `bazel cquery //x --output=starlark --starlark:expr='providers(target)'`.

#### alias

```starlark
alias(
    name = "db",
    actual = select({
        "//conditions:default": "//lib/db/postgres",
        "//tools/flags:sqlite": "//lib/db/sqlite",
    }),
)
```

An alias forwards everything to `actual`. Use it for stable public names, for moving targets without breaking consumers, and for picking an implementation with `select()`. Visibility is checked on the alias, then the alias must be able to see `actual`.

#### test_suite

```starlark
test_suite(
    name = "smoke",
    tags = ["smoke"],            # every test in THIS package tagged smoke
)

test_suite(
    name = "all_fast",
    tests = [
        "//lib/auth:auth_test",
        "//lib/billing:smoke",   # another suite: suites nest
    ],
)
```

`test_suite` with no `tests` attribute expands to every test in the package (filtered by `tags`). With `tests`, it expands to exactly those targets and suites. It does not accept wildcard patterns; for "everything under a path" use the command line (`bazel test //lib/...`) or tags with `--test_tag_filters`.

> **Gotcha.** `tests` takes labels, not target patterns: `"//lib/billing/..."` in that list fails to load. Keep suites small and explicit, or drive selection with tags.

#### genrule

```starlark
genrule(
    name = "version_go",
    srcs = ["VERSION"],
    outs = ["version.go"],
    cmd = "printf 'package version\\n\\nconst Value = \"%s\"\\n' \"$$(cat $<)\" > $@",
)

genrule(
    name = "schema_json",
    srcs = ["schema.yaml"],
    outs = ["schema.json"],
    tools = ["//tools/yaml2json"],          # built for the exec platform
    cmd = "$(execpath //tools/yaml2json) $< > $@",
)
```

| Make variable | Expands to |
|---|---|
| `$<` | The single input (only when `srcs` has one file) |
| `$@` | The single output (only when `outs` has one file) |
| `$(SRCS)`, `$(OUTS)` | All inputs, all outputs, space-separated |
| `$(execpath LABEL)` | Path of one file, valid inside the action's working directory |
| `$(execpaths LABEL)` | Same, for a label with several files |
| `$(rootpath LABEL)` | Runfiles-relative path, for use at run time (in `args` of a binary or test) |
| `$(location LABEL)` | Older alias; prefer `execpath` in `cmd` and `rootpath` in `args` |
| `$(RULEDIR)` | The output directory of this package |
| `$$` | A literal `$` for the shell |

A genrule is a shell string with no providers and no toolchain resolution. It is fine for a one-line transformation. As soon as it grows options, multiple outputs that depend on inputs, or needs to run a tool per platform, write a rule or use `run_binary` from aspect_bazel_lib, which runs a tool with declared args and no shell. Writing a real rule is covered in the rules and macros chapter.

```starlark
load("@aspect_bazel_lib//lib:run_binary.bzl", "run_binary")

run_binary(
    name = "schema_json",
    srcs = ["schema.yaml"],
    outs = ["schema.json"],
    tool = "//tools/yaml2json",
    args = ["$(execpath schema.yaml)", "$(execpath schema.json)"],
)
```

#### exports_files

A source file can be used by another package only if its package exports it.

```starlark
exports_files(
    ["openapi.yaml"],
    visibility = ["//services:__subpackages__"],
)
```

> **Version-sensitive.** Bazel 10 flips `--incompatible_no_implicit_file_export`. Today, a source file that a rule in its own package uses is implicitly visible to others in some cases; from 10.0, referencing another package's source file needs an explicit `exports_files` (or a `filegroup`). Add them now and test with `--incompatible_no_implicit_file_export` on 9.x to find the gaps before the upgrade.

### Tags

Tags are strings in a `tags` list. Most are free-form labels you filter on; a few change how Bazel executes the target.

| Tag | Effect |
|---|---|
| `manual` | Excluded from wildcard patterns (`//...`, `:all`, `:*`). Still builds when named explicitly. |
| `exclusive` | Test runs with nothing else in parallel. |
| `requires-network` | The sandbox allows network for this action. |
| `no-sandbox` | Action runs without a sandbox. Avoid; it hides undeclared inputs. |
| `no-remote` | Never executed remotely and never cached remotely. |
| `no-remote-exec` | May use the remote cache, but runs locally. |
| `no-remote-cache` | May execute remotely, but results are not cached remotely. |
| `no-cache` | Never cached, locally or remotely. |
| `local` | Runs locally, unsandboxed, uncached. The heaviest hammer. |
| `external` | Test is never cached and always reruns. |
| `cpu:N` | Test reserves N CPUs from the local scheduler. |

Free-form tags (`integration`, `smoke`, `e2e`, `slow`) drive selection: `bazel test //... --test_tag_filters=-e2e` and `bazel build //... --build_tag_filters=-gpu`.

> **Gotcha.** Execution tags on a test apply to the test action. They do not automatically apply to the actions that build the test's dependencies. If a code generator needs network, the tag belongs on the generator's target, not on the test that uses its output.

### A layout for a polyglot monorepo

```text
mono/
├── MODULE.bazel             # every external dep, one place
├── MODULE.bazel.lock
├── .bazelversion            # 9.3.0
├── .bazelrc                 # shared flags (see the .bazelrc chapter)
├── .bazelignore             # node_modules, build output of non-Bazel tools
├── BUILD.bazel              # gazelle target, root-level aliases, node_modules link
├── go.mod / go.sum          # Go deps, read by go_deps
├── requirements.in          # Python intent
├── requirements_lock.txt    # Python lock, read by pip.parse
├── package.json / pnpm-lock.yaml / pnpm-workspace.yaml
├── platforms/               # platform() definitions (see the platforms chapter)
├── tools/                   # macros, rules, tool binaries, workspace_status.sh
├── third_party/             # BUILD files for non-module archives, patches
├── proto/                   # .proto sources, one package per API
├── lib/
│   ├── go/...               # or lib/<domain> if domains span languages
│   ├── py/...
│   └── ts/...
└── services/
    ├── api/                 # one directory per deployable
    │   ├── BUILD.bazel      # binary, image, push
    │   └── internal/...
    └── worker/
```

Two layouts work: by language (`lib/go`, `lib/py`) or by domain (`lib/billing` with Go and Python inside). By domain keeps related code together and lets visibility follow team ownership; by language makes per-language tooling and Gazelle directives simpler. Pick one and keep it; mixing them is the hard version.

> **One-way door.** Directory layout becomes import paths. In Go the `importpath` follows `gazelle:prefix` plus the directory; in Python the `imports` attribute and the package path decide module names; in TypeScript it becomes path aliases. Moving `lib/` to `libs/` after a year rewrites every import in every language. Decide the top-level layout before the second team joins.

#### .bazelignore and REPO.bazel

`.bazelignore` lists directories Bazel must never treat as packages, one path per line relative to the repo root:

```text
node_modules
services/web/node_modules
.venv
target
```

Use it for directories other tools create (npm, cargo, virtualenvs). Without it, a stray `BUILD` file inside `node_modules` becomes a package and globs and wildcards behave strangely.

> **Version-sensitive.** Recent Bazel versions also accept `ignore_directories([...])` with glob patterns in a `REPO.bazel` file at the repo root. `.bazelignore` remains supported and is the portable choice; check `bazel help` and the release notes of your version before relying on `REPO.bazel`.

#### Convenience symlinks

`bazel-bin`, `bazel-out`, `bazel-testlogs` and `bazel-<repo>` at the root point into the output base. They are convenient and cause three problems: IDE indexers crawl them, `grep -r` finds every generated file twice, and tools that walk the tree (some linters, `find`) follow them.

```bash
# .gitignore
/bazel-*

# rename them out of the way, or turn them off
build --symlink_prefix=.bazel/            # .bazel/bin, .bazel/out, ...
build --experimental_convenience_symlinks=ignore   # don't create them at all
```

Turning them off is safe for scripts if they use `bazel info bazel-bin` or `bazel cquery --output=files` instead of hard-coded paths, which is the better habit anyway.

### Gazelle in depth

Gazelle reads your sources, figures out imports, and writes BUILD files. It owns `srcs`, `deps`, `embed`, `importpath` and the rule kinds it knows; it leaves everything else alone and merges into existing files.

#### Root setup with several languages

```starlark
# BUILD.bazel (repo root)
load("@gazelle//:def.bzl", "gazelle", "gazelle_binary")

gazelle_binary(
    name = "gazelle_bin",
    languages = [
        "@gazelle//language/proto",          # order matters: proto before go
        "@gazelle//language/go",
        "@rules_python_gazelle_plugin//python",
    ],
)

# gazelle:prefix github.com/acme/mono
# gazelle:build_file_name BUILD.bazel
# gazelle:go_naming_convention import
# gazelle:exclude third_party
# gazelle:exclude **/node_modules
# gazelle:python_extension enabled
# gazelle:python_root
gazelle(
    name = "gazelle",
    gazelle = ":gazelle_bin",
)
```

```starlark
# MODULE.bazel (excerpt)
bazel_dep(name = "gazelle", version = "0.54.0")
bazel_dep(name = "rules_python_gazelle_plugin", version = "2.4.2", dev_dependency = True)
```

The Python plugin also needs a mapping from import names to PyPI distributions (`import yaml` comes from `PyYAML`). rules_python_gazelle_plugin generates it as a `gazelle_python.yaml` manifest; its README has the two targets to add (`modules_mapping` and `gazelle_python_manifest`). Regenerate the manifest whenever `requirements_lock.txt` changes, and check it in CI with the manifest's test target.

#### Running it

| Command | Does |
|---|---|
| `bazel run //:gazelle` | Update every BUILD file (the `update` command is the default) |
| `bazel run //:gazelle -- update lib/auth services/api` | Only these directories (and below) |
| `bazel run //:gazelle -- fix` | Like update, plus migrations that may delete or rename things in existing rules |
| `bazel run //:gazelle -- -mode=diff` | Print a diff instead of writing files |
| `bazel run //:gazelle -- -mode=print lib/auth` | Print the generated file to stdout |
| `bazel run //:gazelle -- -repo_root=. -index=lazy` | Lazy indexing for large repos (check your Gazelle version supports it) |

`update` never applies changes that could break hand edits; `fix` does (renaming old rule kinds, removing deprecated attributes). Run `fix` once after a Gazelle or rules_go upgrade, review the diff, and use `update` day to day.

#### CI check

```yaml
gazelle:
  script:
    - bazel run //:gazelle -- -mode=diff > gazelle.diff || true
    - |
      if [ -s gazelle.diff ]; then
        cat gazelle.diff
        echo "BUILD files are stale: run 'bazel run //:gazelle' and commit." >&2
        exit 1
      fi
```

> **Gotcha.** Don't rely only on Gazelle's exit code in `-mode=diff`. Behaviour has varied across versions; testing for a non-empty diff, as above, works on all of them.

#### Directives you'll actually use

Directives are comments in a BUILD file. They apply to that directory and every subdirectory, until overridden lower down.

| Directive | Effect |
|---|---|
| `# gazelle:prefix github.com/acme/mono` | Go import path of this directory. Set once at the root; override in subtrees with a different module path. |
| `# gazelle:exclude PATH` | Skip a directory or glob (`**/testdata/generated`). |
| `# gazelle:ignore` | Don't touch this BUILD file at all. |
| `# gazelle:build_file_name BUILD.bazel,BUILD` | Which names to read; the first is used for new files. |
| `# gazelle:lang go,proto` | Only these languages in this subtree. |
| `# gazelle:go_naming_convention import` | Library targets named after the last import path component (`:auth`), not `:go_default_library`. |
| `# gazelle:resolve go github.com/acme/legacy //third_party/legacy` | Pin an import to a label when Gazelle can't find it (generated code, hand-written BUILD). Full form: `# gazelle:resolve SOURCE_LANG IMPORT_LANG IMPORT LABEL`. |
| `# gazelle:map_kind go_binary acme_go_binary //tools:go.bzl` | Generate your macro instead of the plain rule. Gazelle keeps managing its attributes. |
| `# gazelle:proto package` | One `proto_library` per directory (`file` for one per file, `disable` to turn proto off). |
| `# gazelle:proto_strip_import_prefix /proto` | Proto imports relative to `proto/`. |
| `# gazelle:python_root` | This directory is a Python import root (the equivalent of a `sys.path` entry). |
| `# gazelle:python_generation_mode package` | One `py_library` per directory (`file` or `project` are the alternatives). |
| `# gazelle:python_test_naming_convention $package_name$_test` | Name of generated test targets. |

#### Keeping hand edits

Gazelle merges. It owns the attributes it generates and removes entries it can no longer justify. To keep something it would delete, add `# keep`:

```starlark
go_library(
    name = "plugin",
    srcs = ["plugin.go"],
    importpath = "github.com/acme/mono/lib/plugin",
    deps = [
        "//lib/log",
        "//lib/plugin/registry",  # keep  (loaded via reflection, no import)
    ],
    x_defs = {"main.mode": "plugin"},   # not a Gazelle attribute; never touched
)
```

`# keep` on a single list entry keeps that entry. `# keep` on the attribute line (`deps = [  # keep`) keeps the whole attribute. `# keep` on the rule's opening line stops Gazelle merging into that rule at all. Use the narrowest one.

> **Field note.** A growing number of `# keep` comments is a signal, not a solution. Each one is a dependency Gazelle can't see: reflection, a plugin registry, a runtime `data` file. Prefer a `# gazelle:resolve` directive or a real import, so the dependency is visible to both Gazelle and the next person.

#### map_kind for house rules

```starlark
# tools/go.bzl
load("@rules_go//go:def.bzl", "go_binary")

def acme_go_binary(name, **kwargs):
    kwargs.setdefault("pure", "on")
    kwargs.setdefault("x_defs", {"main.version": "{STABLE_VERSION}"})
    go_binary(name = name, **kwargs)
```

```starlark
# BUILD.bazel (root)
# gazelle:map_kind go_binary acme_go_binary //tools:go.bzl
```

Gazelle now writes `acme_go_binary` with the right `load()` and keeps updating `srcs`, `embed` and `deps`. Every binary picks up the house defaults without anyone remembering them.

### buildozer: refactors across hundreds of files

buildozer edits BUILD files by command, without formatting churn. Syntax: `buildozer 'COMMAND ARGS' TARGET_PATTERN...`.

| Target pattern | Matches |
|---|---|
| `//lib/auth:auth` | One rule |
| `//lib/auth:*` | Every rule in the package |
| `//lib/...:*` | Every rule in every package below `lib` |
| `//lib/...:%go_library` | Every `go_library` below `lib` |
| `//lib/auth:__pkg__` | The package itself (for `package()` and loads) |

| Command | Example |
|---|---|
| `add ATTR VALUE...` | `buildozer 'add deps //lib/log' //services/...:%go_library` |
| `remove ATTR VALUE...` | `buildozer 'remove deps //lib/oldlog' //...:*` |
| `replace ATTR OLD NEW` | `buildozer 'replace deps //lib/util //lib/util/retry' //...:*` |
| `set ATTR VALUE` | `buildozer 'set size medium' //...:%py_test` |
| `remove ATTR` | `buildozer 'remove shard_count' //lib/...:%go_test` |
| `rename OLD NEW` | `buildozer 'rename srcs hdrs' //lib/codec:codec` |
| `new KIND NAME` | `buildozer 'new filegroup testdata' //lib/auth:__pkg__` |
| `new_load LABEL SYMBOL` | `buildozer 'new_load @rules_cc//cc:cc_library.bzl cc_library' //third_party/...:__pkg__` |
| `fix` | Older catch-all clean-up; prefer `buildifier -lint=fix` |
| `print ATTR...` | `buildozer 'print label size tags' //...:%go_test` (read-only) |
| `comment ATTR TEXT` | Add a comment to an attribute |

```bash
# several commands in one pass, from a file
cat > /tmp/cmds.txt <<'EOF'
replace deps //lib/util //lib/util/retry|//services/...:*
add tags integration|//services/api:api_test
EOF
buildozer -f /tmp/cmds.txt

# find every test without an explicit size, then set it
buildozer 'print label size' //...:%go_test | awk '$2 == "(missing)" {print $1}'
```

> **Gotcha.** buildozer exits with code 3 when it ran successfully but changed nothing. In a script with `set -e`, a re-run that finds nothing to do looks like a failure. Treat 3 as success: `buildozer ... || [ $? -eq 3 ]`.

#### buildifier: format and lint

```bash
buildifier -r .                          # format every BUILD, .bzl, MODULE.bazel
buildifier -r -lint=warn .               # report lint findings
buildifier -r -lint=fix .                # apply the safe fixes (adds missing loads)
buildifier -r -mode=check -lint=warn .   # CI: fail on unformatted files or warnings
```

`-lint=fix` adds `load()` statements for rules that Bazel 9 no longer autoloads (warnings in the `native-*` family: `native-cc`, `native-java`, `native-py`, `native-proto`, `native-sh`). It is the fastest single step in a Bazel 8 to 9 upgrade.

A `.buildifier.json` (or `-warnings=` flag) tunes which warnings apply:

```json
{
  "type": "auto",
  "lint": "warn",
  "warningsList": ["-module-docstring", "-function-docstring"]
}
```

### BUILD file review checklist

- [ ] Every rule has a `load()` from its rule set; no reliance on autoloading.
- [ ] Library visibility is narrower than public, and widening it is a deliberate change in the diff.
- [ ] Tests have an honest `size`; anything needing network says `requires-network`.
- [ ] Runtime files are in `data`, not read from a path outside the sandbox.
- [ ] No `glob()` for library sources that Gazelle could list.
- [ ] Every `# keep` has a reason in the comment.
- [ ] No `genrule` longer than one line; use `run_binary` or a rule.
- [ ] Gazelle and buildifier are clean (`-mode=diff`, `-mode=check`).

### Go

Go is the language Bazel fits best: Go's package model maps one-to-one onto Bazel packages, and Gazelle generates everything.

#### MODULE.bazel

```starlark
bazel_dep(name = "rules_go", version = "0.64.2")
bazel_dep(name = "gazelle", version = "0.54.0")

go_sdk = use_extension("@rules_go//go:extensions.bzl", "go_sdk")
go_sdk.from_file(go_mod = "//:go.mod")       # SDK version follows the `go` / `toolchain` line
# or pin explicitly:
# go_sdk.download(version = "1.26.2")

go_deps = use_extension("@gazelle//:extensions.bzl", "go_deps")
go_deps.from_file(go_mod = "//:go.mod")
use_repo(
    go_deps,
    "com_github_google_uuid",
    "org_golang_google_grpc",
    "org_golang_x_sync",
)
```

You never maintain the `use_repo` list by hand. After changing `go.mod`, run `bazel mod tidy` and it rewrites the list to exactly the modules your root module imports directly.

Repo names come from the import path: `github.com/google/uuid` becomes `@com_github_google_uuid`, and the package label is `@com_github_google_uuid//:uuid`. Sub-packages are `@org_golang_x_sync//errgroup`.

#### BUILD

```starlark
load("@rules_go//go:def.bzl", "go_binary", "go_library", "go_test")

go_library(
    name = "api_lib",
    srcs = ["main.go", "routes.go"],
    importpath = "github.com/acme/mono/services/api",
    visibility = ["//visibility:private"],
    deps = [
        "//lib/auth",
        "@org_golang_google_grpc//:grpc",
    ],
)

go_binary(
    name = "api",
    embed = [":api_lib"],
    pure = "on",
    x_defs = {
        "github.com/acme/mono/lib/version.Commit": "{STABLE_GIT_COMMIT}",
        "github.com/acme/mono/lib/version.Version": "{STABLE_VERSION}",
    },
    visibility = ["//visibility:public"],
)

go_test(
    name = "api_test",
    size = "small",
    srcs = ["routes_test.go"],
    embed = [":api_lib"],
    data = glob(["testdata/**"]),
)
```

| Attribute | What it does |
|---|---|
| `importpath` | The Go import path; Gazelle derives it from `gazelle:prefix` plus the directory |
| `embed` | Compile these libraries' sources into this target (how tests see unexported names) |
| `pure = "on"` | Disable cgo: static binary, no C toolchain needed, trivial base images |
| `x_defs` | `-X` linker flags. `{KEY}` values are filled from the workspace status file, but only with `--stamp` |
| `goos`, `goarch` | Force a target OS/arch for one binary (prefer `--platforms` for whole builds) |
| `race = "on"` | Build this test or binary with the race detector |
| `gc_goopts`, `gc_linkopts` | Extra compiler and linker flags |

#### Daily commands

```bash
bazel run //services/api -- --port=8080
bazel test //lib/...
bazel test //lib/auth:auth_test --test_arg=-test.run=TestVerify --test_arg=-test.v
bazel test //lib/... --@rules_go//go/config:race          # race detector for everything
bazel build //services/... --platforms=@rules_go//go/toolchain:linux_arm64

# the Go tool from the hermetic SDK, for go.mod work
```

#### go_deps overrides

Most Go modules build cleanly from generated BUILD files. When one doesn't, fix it in `MODULE.bazel`, not by forking it.

```starlark
# pass Gazelle directives into an external module's BUILD generation
go_deps.gazelle_override(
    path = "github.com/envoyproxy/protoc-gen-validate",
    directives = [
        "gazelle:proto disable",        # use the checked-in .pb.go files, don't regenerate
    ],
)

# patch an external module
go_deps.module_override(
    path = "github.com/example/broken",
    patches = ["//third_party/patches:broken-fix-build-tags.patch"],
    patch_strip = 1,
)
```

| Symptom | Override |
|---|---|
| A dependency ships `.pb.go` files and also `.proto` files; Gazelle generates conflicting `go_proto_library` targets | `gazelle_override` with `gazelle:proto disable` |
| Build tags or a generated file confuse Gazelle | `gazelle_override` with `gazelle:exclude` or `gazelle:build_tags` |
| A real bug in the upstream code or its BUILD files | `module_override` with a patch |
| A module already has good BUILD files (published Bazel module) | Prefer a `bazel_dep` on its BCR module over `go_deps` |

> **Field note.** Gazelle maintains a default set of overrides for popular modules that need them (the "default gazelle overrides" in the gazelle repo). If a well-known module fails, upgrade gazelle first; the fix may already be there.

#### Go traps

> **Gotcha.** `go test ./...` and `bazel test //...` can disagree. Go reads files on disk relative to the package; Bazel runs tests in the runfiles tree. A test that opens `../../testdata/x.json` passes with `go test` and fails under Bazel. Put files in `data` and open them relative to the test's own package directory, which is the working directory Bazel sets for Go tests.

> **Gotcha.** Generated `.go` files committed next to sources (mocks, `stringer` output) are picked up by Gazelle as sources. Either generate them with Bazel and exclude the committed copies, or commit them and don't generate. Doing both produces duplicate symbol errors.

### Python

Python under Bazel is workable and needs more care than Go. The language has no build step to hang dependency information on, so everything depends on the import path and the lockfile.

#### MODULE.bazel

```starlark
bazel_dep(name = "rules_python", version = "2.4.2")

python = use_extension("@rules_python//python/extensions:python.bzl", "python")
python.toolchain(
    python_version = "3.12",
    is_default = True,
)

pip = use_extension("@rules_python//python/extensions:pip.bzl", "pip")
pip.parse(
    hub_name = "pypi",
    python_version = "3.12",
    requirements_lock = "//:requirements_lock.txt",
)
use_repo(pip, "pypi")
```

The toolchain downloads a standalone CPython build, so the interpreter is identical on every machine and CI runner. `pip.parse` creates one hub repo (`@pypi`) with a target per distribution: `@pypi//requests`, `@pypi//pyyaml`. Names are normalised: lower case, `-` and `.` become `_`.

#### Locking requirements

The lock file must contain exact versions and hashes. Two ways to produce it:

```starlark
# BUILD.bazel (root): option 1, rules_python's pip-tools wrapper

    name = "requirements",
    src = "requirements.in",
    requirements_txt = "requirements_lock.txt",
)
```

```starlark
# BUILD.bazel (root): option 2, uv through rules_uv (much faster on big sets)
load("@rules_uv//uv:pip.bzl", "pip_compile")

pip_compile(
    name = "generate_requirements_txt",
    requirements_in = "requirements.in",
    requirements_txt = "requirements_lock.txt",
)
```

```bash

bazel test //:requirements_test               # option 1: fail if the lock is stale
bazel run //:generate_requirements_txt        # option 2
```

#### BUILD

```starlark
load("@rules_python//python:py_binary.bzl", "py_binary")
load("@rules_python//python:py_library.bzl", "py_library")
load("@rules_python//python:py_test.bzl", "py_test")

```

| Attribute | What it does |
|---|---|
| `imports` | Directories, relative to the package, added to `sys.path` for this target and everything that depends on it |
| `main` | The entry-point file of a binary or test |
| `data` | Runtime files, readable through the runfiles library |
| `python_version` | Pin a target to one of several registered interpreters |

#### The import path problem

Outside Bazel, you run from the repo root and Python finds packages relative to it. Inside Bazel, every target runs in a runfiles tree and only the repo root plus `imports` entries are on `sys.path`.

| You write | It works under Bazel when |
|---|---|
| `from lib.py.telemetry import tracer` | Nothing extra: the repo root is on `sys.path` by default |
| `from telemetry import tracer` | The library sets `imports = [".."]` (or Gazelle's `python_root` covers it) |
| `import worker` from a sibling test | The library sets `imports = ["."]` |

Pick one convention for the whole repo. Absolute imports from the repo root are the simplest under Bazel; per-project import roots (`# gazelle:python_root` in each project directory) match what most Python projects already look like.

```bash
# .bazelrc: stop Bazel creating empty __init__.py files everywhere
build --incompatible_default_to_explicit_init_py
```

> **Gotcha.** Without `--incompatible_default_to_explicit_init_py`, Bazel creates an empty `__init__.py` in every directory of the runfiles tree. That turns namespace packages into regular packages and two distributions sharing a namespace (`google.cloud.*`, company `acme.*` packages) shadow each other. Set the flag before you have many Python targets; turning it on later breaks every package that relied on the implicit files.

#### pytest

`py_test` runs `main` with the plain interpreter. To use pytest, give each test a small entry point:

```python
# tools/pytest/pytest_main.py
import os
import sys

import pytest

if __name__ == "__main__":
    args = ["-p", "no:cacheprovider", "--import-mode=importlib"]
    if os.environ.get("XML_OUTPUT_FILE"):
        args.append(f"--junitxml={os.environ['XML_OUTPUT_FILE']}")
    if os.environ.get("TESTBRIDGE_TEST_ONLY"):      # set by --test_filter
        args += ["-k", os.environ["TESTBRIDGE_TEST_ONLY"]]
    args += sys.argv[1:]
    sys.exit(pytest.main(args))
```

```starlark
# tools/pytest/defs.bzl
load("@rules_python//python:py_test.bzl", "py_test")

    py_test(
        name = name,
        srcs = srcs + ["//tools/pytest:pytest_main.py"],
        main = "//tools/pytest:pytest_main.py",
        args = args + ["$(rootpath %s)" % s for s in srcs],
        deps = deps + ["@pypi//pytest"],
        **kwargs
    )
```

```starlark
load("//tools/pytest:defs.bzl", "pytest_test")

pytest_test(
    name = "tasks_test",
    size = "small",
    srcs = ["tests/test_tasks.py"],
    deps = [":worker"],
)
```

`tools/pytest/BUILD.bazel` needs `exports_files(["pytest_main.py"])`. Map the macro with `# gazelle:map_kind py_test pytest_test //tools/pytest:defs.bzl` so Gazelle generates it. The `-p no:cacheprovider` flag stops pytest writing `.pytest_cache` into the read-only runfiles tree.

Editors want a virtualenv. Build it from the same lock so the editor and Bazel agree:

#### Python traps

> **Gotcha.** Packages with native extensions and no wheel for your platform are built from source by `pip.parse` at fetch time, with the host compiler. That is slow and not hermetic. Prefer versions that publish wheels for every platform you build for, and check with `pip download --only-binary=:all:`.

> **Gotcha.** Code that reads files with paths relative to `__file__` or the working directory works under `python main.py` and fails under Bazel. Use the runfiles library (`from python.runfiles import runfiles`, provided by `@rules_python//python/runfiles`) and declare the files in `data`.

Each npm package with binaries gets a generated `package_json.bzl` that exposes them as rules: `bin.NAME` runs the tool as a build action, and `bin.NAME_binary` and `bin.NAME_test` wrap it as a runnable binary or a test.

#### JS/TS traps

> **Gotcha.** If `node_modules` is not in `.bazelignore`, Bazel walks it as source and every `BUILD` file shipped inside a package becomes a package of yours. `verify_node_modules_ignored` in the extension catches this at fetch time; keep it on.

> **Gotcha.** `ts_project` checks that your `tsconfig.json` settings match its attributes (`declaration`, `composite`, `outDir`, `rootDir`). A mismatch is an analysis error, not a warning. Set the attribute on the rule and the option in the file to the same value, or let `ts_config` carry the file and remove duplicates from the rule.

> **Field note.** Lifecycle scripts (`postinstall`) don't run by default under rules_js. Packages that download binaries in `postinstall` (esbuild, sharp, playwright browsers) need either a platform-specific optional dependency (most modern ones ship this way) or an explicit `lifecycle_hooks` entry on `npm_translate_lock`. In an air-gap, prefer packages that ship binaries as optional dependencies.

### C and C++

C and C++ have no package manager to translate, and Bazel was built for them. The work is in making the toolchain hermetic.

#### MODULE.bazel with a hermetic clang

```starlark
bazel_dep(name = "rules_cc", version = "0.2.26")
bazel_dep(name = "toolchains_llvm", version = "1.11.3")

llvm = use_extension("@toolchains_llvm//toolchain/extensions:llvm.bzl", "llvm")
llvm.toolchain(
    llvm_version = "19.1.7",
)
use_repo(llvm, "llvm_toolchain")
register_toolchains("@llvm_toolchain//:all")
```

Bazel otherwise auto-detects a C++ toolchain from the host (`gcc` or `clang` on `PATH`, plus system headers). That works and is the single largest source of cache misses between machines. With toolchains_llvm, every machine compiles with the same downloaded clang.

| Option | Strength | Trade-off |
|---|---|---|
| `toolchains_llvm` | Real clang/LLVM, any version; sysroots for cross-compiling | Large download; you choose and supply sysroots for other targets |
| `hermetic_cc_toolchain` (4.3.0) | `zig cc` as the compiler; cross-compiles to many targets with no sysroot setup | Zig's libc and linker behaviour differ in edge cases from gcc/clang |
| Host auto-detection | Zero setup | Not hermetic; cache keys differ per machine |

#### BUILD

```starlark
load("@rules_cc//cc:cc_binary.bzl", "cc_binary")
load("@rules_cc//cc:cc_library.bzl", "cc_library")
load("@rules_cc//cc:cc_test.bzl", "cc_test")

cc_library(
    name = "klv",
    srcs = ["klv.cc"],
    hdrs = ["klv.h"],
    copts = ["-Wall", "-Wextra", "-Werror"],
    includes = ["."],                          # headers included as "klv.h" by dependants
    visibility = ["//visibility:public"],
)

cc_binary(
    name = "klv_dump",
    srcs = ["klv_dump.cc"],
    deps = [":klv"],
)

cc_test(
    name = "klv_test",
    size = "small",
    srcs = ["klv_test.cc"],
    deps = [
        ":klv",
        "@googletest//:gtest_main",
    ],
)
```

| Attribute | Meaning |
|---|---|
| `hdrs` | Public headers: dependants may include these |
| `srcs` | Sources and private headers |
| `includes` | Add directories to dependants' include path (use `strip_include_prefix` or `include_prefix` for cleaner control) |
| `copts` | Compiler flags for this target only |
| `defines` | `-D` flags that propagate to dependants; `local_defines` don't |
| `linkopts` | Linker flags that propagate to binaries |
| `linkstatic` | Prefer static linking of this library |

```bash
bazel build //lib/codec:klv_dump -c opt           # optimised
bazel build //lib/codec:klv_dump -c dbg           # debug info, no optimisation
bazel test //lib/codec:klv_test --config=asan     # define build:asan --copt=-fsanitize=address --linkopt=-fsanitize=address
```

Many C/C++ libraries are BCR modules with good BUILD files already: `googletest`, `abseil-cpp`, `zlib`, `boringssl`, `fmt`, `spdlog`. Prefer `bazel_dep` over hand-written BUILD files for archives.

#### compile_commands.json for clangd

clangd needs a compilation database. Bazel doesn't produce one natively. The common tool is Hedron's compile-commands extractor (`hedronvision/bazel-compile-commands-extractor`), which runs `aquery` and writes `compile_commands.json` at the repo root. It is not always on the BCR at a current version; add it with `git_override` pinned to a commit and run it with `bazel run @hedron_compile_commands//:refresh_all`. Check its README for the current module name and setup.

> **Gotcha.** `-Werror` in `copts` applies only to your targets, but a header-only dependency compiled into your translation units triggers warnings in your target. Add the dependency's include directory with `-isystem` (via `includes` on a wrapper library) or keep `-Werror` for CI only with a config.

For C++, `cc_proto_library` is in `@protobuf//bazel:cc_proto_library.bzl` and `cc_grpc_library` in `@grpc//bazel:cc_grpc_library.bzl`. For Java, `java_proto_library` is in `@protobuf//bazel:java_proto_library.bzl`.

> **Version-sensitive.** The proto rules moved from `@rules_proto` and native Bazel into the `protobuf` module (`@protobuf//bazel:...`), and rules_go's compiler labels have changed across releases (`go_grpc` versus newer `go_grpc_v2`). Let Gazelle write `go_proto_library` targets, and check the rules_go release notes before hand-editing compiler labels.

> **Field note.** Compiling `protoc` from source is often the slowest action in a cold build. Bazel 9 with recent protobuf releases can use a prebuilt `protoc` through toolchain resolution instead. The flags involved are new and still settling; check the protobuf release notes and the Bazel 9 release blog for the current setting before turning it on, and confirm with `bazel aquery 'mnemonic("GenProto", //proto/...)'` which `protoc` runs.

#### buf alongside Bazel

Many teams keep `buf lint` and `buf breaking` for API review and use Bazel only to generate and compile. That split works: `buf` reads the same `.proto` files, and Bazel doesn't need to know about it. Run `buf breaking --against '.git#branch=main'` in CI next to the Bazel jobs.

```starlark
load("@rules_shell//shell:sh_binary.bzl", "sh_binary")
```

## 08 · Platforms, toolchains and configuration

*Where an action runs and what it builds for are separate questions. Constraints, toolchain resolution, transitions, select and build settings, and how one command builds ARM on x86.*

### Three platforms in every build

Every build involves up to three platforms. On a laptop building for itself they are the same machine, which is why most people never think about them until cross-compilation or remote execution forces the issue.

| Platform | Question it answers | Set by |
|---|---|---|
| **Host** | Where is the Bazel client and server running? | Auto-detected; override with `--host_platform` |
| **Execution (exec)** | Where do actions (compilers, generators, tests) run? | First match from `--extra_execution_platforms`, then `register_execution_platforms()`, then the host |
| **Target** | What does the output run on? | `--platforms` (defaults to the host platform) |

An x86_64 laptop building an arm64 container image with remote execution has three different answers: host is the laptop, exec is the remote worker pool, target is linux/arm64.

### Constraints and platforms

A platform is nothing more than a named set of constraint values. Constraints come in settings (a dimension) and values (a point on it).

```starlark
# @platforms already defines the common ones:
#   @platforms//os:linux  @platforms//os:macos  @platforms//os:windows
#   @platforms//cpu:x86_64  @platforms//cpu:arm64 (alias: aarch64)

# your own dimension: platforms/BUILD.bazel
constraint_setting(
    name = "gpu",
    default_constraint_value = ":no_gpu",
)

constraint_value(name = "no_gpu", constraint_setting = ":gpu")
constraint_value(name = "cuda", constraint_setting = ":gpu")

platform(
    name = "linux_amd64",
    constraint_values = [
        "@platforms//os:linux",
        "@platforms//cpu:x86_64",
    ],
)

platform(
    name = "linux_arm64",
    constraint_values = [
        "@platforms//os:linux",
        "@platforms//cpu:arm64",
    ],
)

platform(
    name = "linux_amd64_cuda",
    parents = [":linux_amd64"],          # inherit, then add
    constraint_values = [":cuda"],
)

# a remote execution pool: same constraints plus where the worker runs
platform(
    name = "rbe_linux_amd64",
    parents = [":linux_amd64"],
    exec_properties = {
        "container-image": "docker://harbor.internal/build/rbe-ubuntu24@sha256:REPLACE",
        "OSFamily": "Linux",
    },
)
```

| `platform()` attribute | Use |
|---|---|
| `constraint_values` | The constraints this platform satisfies |
| `parents` | Inherit constraints and exec properties from another platform |
| `exec_properties` | Key/value pairs sent to the remote executor (container image, pool, OS). Keys depend on the backend |
| `flags` | Build flags applied when this platform is the target platform (recent Bazel; check `bazel help` on your version) |

> **Gotcha.** A platform with no constraint for a setting gets that setting's `default_constraint_value`, or nothing if there is no default. A `select()` on `@platforms//os:linux` then fails to match a platform that forgot to list an OS. Always give target platforms a full OS and CPU.

### Toolchain resolution, step by step

A rule that needs a compiler declares a **toolchain type**. Bazel then picks a concrete toolchain for each configured target.

```text
1. Collect candidate execution platforms, in order:
     --extra_execution_platforms        (flag, first)
     register_execution_platforms(...)  (MODULE.bazel, root module first)
     the host platform                  (last)
2. Collect candidate toolchains for each required type, in order:
     --extra_toolchains                 (flag, first)
     register_toolchains(...)           (MODULE.bazel, root module first, then deps)
3. For each execution platform in order:
     for each required toolchain type:
       take the first toolchain whose
         exec_compatible_with   is satisfied by this exec platform
         target_compatible_with is satisfied by the target platform
         target_settings        all match the current configuration
     if every required type found a toolchain: choose this exec platform, stop
4. If no exec platform satisfies every type: analysis error
   ("No matching toolchains found for types ...")
```

Two consequences follow from that order. **The first match wins**, so registration order matters: a broad toolchain registered early shadows a specific one registered later. And **one exec platform must satisfy all toolchain types of a target at once**; Bazel won't mix a compiler from one exec platform with a linker from another.

#### Registering

```starlark
# MODULE.bazel
register_execution_platforms("//platforms:rbe_linux_amd64")
register_toolchains(
    "//tools/toolchains:all",
    "@llvm_toolchain//:all",
)
```

`register_toolchains` and `register_execution_platforms` in a non-root module are honoured too, after the root module's. A `dev_dependency = True` argument limits a registration to when this module is the root.

#### Debugging the choice

```bash
# why this toolchain? (a regex matched against toolchain type labels)
bazel build //services/api --toolchain_resolution_debug='@rules_go//go:toolchain'
bazel build //lib/codec --toolchain_resolution_debug='@bazel_tools//tools/cpp:toolchain_type'
bazel build //x --toolchain_resolution_debug='.*'          # everything, noisy

# which toolchains are registered at all
bazel query 'kind(toolchain, @llvm_toolchain//...)'
```

The debug output prints each exec platform considered, each toolchain tried, and the reason it was rejected ("mismatching values: arm64"). Read it from the top; the first rejected candidate is usually the one you expected to win.

### Writing a toolchain

You write one when your repo has a tool that rules need, and the tool differs per platform: a formatter, a code generator distributed as binaries, an SDK.

```starlark
# tools/fmt/toolchain.bzl
FmtInfo = provider(
    doc = "A formatter binary for one exec platform.",
    fields = {"binary": "File: the formatter executable"},
)

def _fmt_toolchain_impl(ctx):
    return [platform_common.ToolchainInfo(
        fmt = FmtInfo(binary = ctx.executable.binary),
    )]

fmt_toolchain = rule(
    implementation = _fmt_toolchain_impl,
    attrs = {
        "binary": attr.label(
            executable = True,
            allow_single_file = True,
            cfg = "exec",
            mandatory = True,
        ),
    },
)
```

```starlark
# tools/fmt/BUILD.bazel
load(":toolchain.bzl", "fmt_toolchain")

toolchain_type(
    name = "toolchain_type",
    visibility = ["//visibility:public"],
)

fmt_toolchain(name = "fmt_linux_amd64_impl", binary = "@fmt_linux_amd64//:fmt")
fmt_toolchain(name = "fmt_macos_arm64_impl", binary = "@fmt_macos_arm64//:fmt")

toolchain(
    name = "fmt_linux_amd64",
    toolchain_type = ":toolchain_type",
    toolchain = ":fmt_linux_amd64_impl",
    exec_compatible_with = ["@platforms//os:linux", "@platforms//cpu:x86_64"],
    # no target_compatible_with: a formatter's output doesn't depend on the target
)

toolchain(
    name = "fmt_macos_arm64",
    toolchain_type = ":toolchain_type",
    toolchain = ":fmt_macos_arm64_impl",
    exec_compatible_with = ["@platforms//os:macos", "@platforms//cpu:arm64"],
)
```

```starlark
# consuming it in a rule
def _fmt_check_impl(ctx):
    fmt = ctx.toolchains["//tools/fmt:toolchain_type"].fmt
    out = ctx.actions.declare_file(ctx.label.name + ".ok")
    ctx.actions.run(
        executable = fmt.binary,
        arguments = ["--check", "--stamp-file", out.path] + [f.path for f in ctx.files.srcs],
        inputs = ctx.files.srcs,
        outputs = [out],
        mnemonic = "FmtCheck",
    )
    return [DefaultInfo(files = depset([out]))]

fmt_check = rule(
    implementation = _fmt_check_impl,
    attrs = {"srcs": attr.label_list(allow_files = True)},
    toolchains = ["//tools/fmt:toolchain_type"],
)
```

| `toolchain()` attribute | Meaning |
|---|---|
| `toolchain_type` | Which type this toolchain implements |
| `toolchain` | The target that returns `ToolchainInfo` |
| `exec_compatible_with` | Constraints the exec platform must have to run this toolchain |
| `target_compatible_with` | Constraints the target platform must have (a cross-compiler targeting arm64 sets these) |
| `target_settings` | `config_setting`s that must match (for example a "use the debug SDK" flag) |

The split between the `toolchain()` declaration and the implementation target matters: Bazel only analyses the implementation of the toolchain it selects. Downloading SDKs for every platform you register stays lazy.

> **Field note.** A toolchain type can be optional: declare it in the rule as `toolchains = [config_common.toolchain_type("//tools/fmt:toolchain_type", mandatory = False)]` and check `ctx.toolchains[...]` for `None`. Use it when a feature should degrade instead of failing on platforms without the tool.

### Exec versus target configuration

Every label attribute in a rule says which configuration its dependency is built in.

| Attribute setting | Dependency is built for | Use for |
|---|---|---|
| (default, `cfg = "target"`) | The target platform | Libraries you link, files you ship |
| `cfg = "exec"` | The chosen exec platform | Compilers, code generators, any tool the action runs |

```starlark
attrs = {
    "deps": attr.label_list(),                              # target
    "_generator": attr.label(
        default = "//tools/gen",
        executable = True,
        cfg = "exec",                                       # runs during the build
    ),
}
```

When you cross-compile for arm64 on x86_64, `//tools/gen` is built for x86_64 so it can run, and `deps` are built for arm64 so they can be linked. Getting this wrong produces an "exec format error" when an action tries to run an arm64 binary on an x86 worker, or an x86 library linked into an arm64 binary.

> **Gotcha.** The same target built in both configurations appears twice in the graph and is compiled twice. `bazel cquery 'deps(//x)'` shows both, with different configuration hashes. That is normal for tools and their libraries; it becomes a cost when a large library is accidentally a dependency of a tool.

### select() and config_setting

`select()` picks attribute values from the configuration. It is resolved during analysis, which is why `bazel query` (loading phase) shows all branches and `bazel cquery` shows the chosen one.

```starlark
load("@bazel_skylib//lib:selects.bzl", "selects")
load("@rules_cc//cc:cc_library.bzl", "cc_library")

config_setting(
    name = "linux_arm64",
    constraint_values = ["@platforms//os:linux", "@platforms//cpu:arm64"],
)

config_setting(
    name = "linux_amd64",
    constraint_values = ["@platforms//os:linux", "@platforms//cpu:x86_64"],
)

config_setting(
    name = "opt",
    values = {"compilation_mode": "opt"},              # matches -c opt
)

selects.config_setting_group(
    name = "linux_any",
    match_any = [":linux_arm64", ":linux_amd64"],
)

cc_library(
    name = "simd",
    srcs = ["simd_common.cc"] + select({
        ":linux_arm64": ["simd_neon.cc"],
        "@platforms//cpu:x86_64": ["simd_avx2.cc"],
        "//conditions:default": ["simd_scalar.cc"],
    }),
    copts = select({
        ":opt": ["-O3"],
        "//conditions:default": [],
    }),
)

# two keys, same value, without duplicating the list
cc_library(
    name = "io",
    srcs = selects.with_or({
        ("@platforms//os:linux", "@platforms//os:macos"): ["io_posix.cc"],
        "@platforms//os:windows": ["io_win.cc"],
    }),
)
```

| `config_setting` attribute | Matches on |
|---|---|
| `constraint_values` | The target platform's constraints |
| `values` | Built-in flags: `compilation_mode`, `cpu`, `define`, and others |
| `flag_values` | Starlark build settings (`//tools/flags:telemetry`) |

Rules for `select()`:

- A `constraint_value` label can be used directly as a select key; no `config_setting` needed.
- Exactly one key must match, or the most specific one if one is a strict specialisation of another. Two equally specific matches are an error.
- No match and no `//conditions:default` is an analysis error. Add `no_match_error = "..."` to make it readable.
- `select()` works on attribute values, not on rule kinds or target names. To choose between whole targets, put the `select()` in an `alias`.

### Build settings: your own flags

Build settings are typed flags defined in Starlark. They are part of the configuration, so they participate in caching and `select()` correctly, unlike `--define`.

```starlark
# tools/flags/BUILD.bazel
load("@bazel_skylib//rules:common_settings.bzl", "bool_flag", "string_flag")

bool_flag(
    name = "telemetry",
    build_setting_default = True,
    visibility = ["//visibility:public"],
)

string_flag(
    name = "db_backend",
    build_setting_default = "postgres",
    values = ["postgres", "sqlite"],
    visibility = ["//visibility:public"],
)

config_setting(name = "telemetry_off", flag_values = {":telemetry": "false"})
config_setting(name = "sqlite", flag_values = {":db_backend": "sqlite"})
```

```bash
bazel build //services/api --//tools/flags:telemetry=false
bazel build //services/api --//tools/flags:db_backend=sqlite
bazel build //services/api --no//tools/flags:telemetry     # boolean shorthand
```

```bash
# .bazelrc: name them so nobody types label paths
build --flag_alias=telemetry=//tools/flags:telemetry
build:embedded --telemetry=false --//tools/flags:db_backend=sqlite
```

> **Gotcha.** A `select()` that never matches its intended branch fails silently when there is a `//conditions:default`. After adding a build setting, prove the branch is taken: `bazel cquery 'deps(//services/api)' --//tools/flags:telemetry=false | grep telemetry` should change the answer. If it doesn't, the `config_setting` value or label is wrong.

> **Gotcha.** `--define=KEY=VALUE` still works and still shows up in old BUILD files. It is untyped, unscoped and every value changes the configuration of every target. Migrate to build settings, which only affect targets that read them.

### Transitions

A transition changes the configuration for part of the graph. Two kinds:

| Kind | Attached to | Effect |
|---|---|---|
| **Outgoing** (edge) | An attribute: `attr.label(cfg = my_transition)` | Dependencies through this attribute are built in the new configuration |
| **Incoming** (rule) | The rule: `rule(cfg = my_transition)` | The target itself is built in the new configuration |

#### The one you'll use: build this for another platform

```starlark
load("@aspect_bazel_lib//lib:transitions.bzl", "platform_transition_filegroup")

platform_transition_filegroup(
    name = "api_arm64",
    srcs = ["//services/api"],
    target_platform = "//platforms:linux_arm64",
)
```

`bazel build //services:api_arm64` produces the arm64 binary regardless of `--platforms`. This is how one build produces several architectures; the images chapter uses it for multi-arch images.

#### Writing one

```starlark
# tools/transitions.bzl
def _opt_impl(settings, attr):
    return {"//command_line_option:compilation_mode": "opt"}

opt_transition = transition(
    implementation = _opt_impl,
    inputs = [],
    outputs = ["//command_line_option:compilation_mode"],
)

def _opt_filegroup_impl(ctx):
    return [DefaultInfo(files = depset(transitive = [d[DefaultInfo].files for d in ctx.attr.srcs]))]

opt_filegroup = rule(
    implementation = _opt_filegroup_impl,
    attrs = {
        "srcs": attr.label_list(cfg = opt_transition),
    },
)
```

Built-in flags are addressed as `//command_line_option:NAME`; Starlark build settings by their label. A transition may also return a dict of dicts to split one dependency into several configurations (a "split transition"), which is how fat binaries for several CPUs are built.

> **Field note.** Older Bazel versions required rules using Starlark transitions to declare an `_allowlist_function_transition` attribute. Current versions don't. If you see an error naming that attribute, you are on an old Bazel or copying an old example.

> **Gotcha.** Every distinct output configuration is a separate copy of the affected subgraph: analysed again, built again, stored under a different `bazel-out/` directory. A transition that sets a flag to a slightly different value for each target can multiply build time. Keep transitions coarse (a few platform values, opt or not), and watch `bazel config` for an exploding list.

### target_compatible_with: skip what can't build

```starlark
go_binary(
    name = "systemd_notify",
    srcs = ["notify.go"],
    target_compatible_with = ["@platforms//os:linux"],
)

cc_library(
    name = "cuda_kernels",
    srcs = ["kernels.cc"],
    target_compatible_with = select({
        "//platforms:cuda": [],
        "//conditions:default": ["@platforms//:incompatible"],
    }),
)
```

| Behaviour | Detail |
|---|---|
| In wildcard builds (`//...`) | Incompatible targets are skipped with a note; the build succeeds |
| Requested explicitly | An error: "target is incompatible". `--skip_incompatible_explicit_targets` turns that into a skip as well |
| Propagation | A target that depends on an incompatible target is itself incompatible |
| `@platforms//:incompatible` | A constraint no platform has; selecting it makes a target incompatible everywhere outside the chosen branch |

This replaces the old pattern of `tags = ["manual"]` plus a separate CI job per platform. `bazel test //... --platforms=//platforms:linux_arm64` now tests everything that can run on arm64 and skips the rest, visibly.

### Inspecting configurations

```bash
bazel config                                 # every configuration this server has seen, with IDs
bazel config 3f2a9c1                         # options of one configuration (ID prefix is enough)
bazel config 3f2a9c1 8b04e7d                 # diff two configurations

bazel cquery //services/api                  # prints the target with its configuration ID
bazel cquery 'deps(//services/api)' --output=label_kind --platforms=//platforms:linux_arm64
bazel cquery //services/api --output=starlark \
  --starlark:expr='target.label'             # starlark access to configured targets
```

The diff is how you answer "why are there two copies of this library in `bazel-out`?" or "why did switching from the IDE to the terminal rebuild everything?": find the two configuration IDs in `cquery` output and diff them.

### Cross-compilation and multi-arch, by language

| Language | Command or setup | Notes |
|---|---|---|
| Go, `pure = "on"` | `--platforms=@rules_go//go/toolchain:linux_arm64` or your own platform | No extra setup; rules_go registers toolchains for every GOOS/GOARCH |
| Go with cgo | Hermetic C toolchain with a target sysroot | toolchains_llvm (sysroot) or hermetic_cc_toolchain (zig) |
| C/C++ | Register a toolchain with `target_compatible_with` for the target, plus a sysroot | toolchains_llvm accepts per-target sysroots in `llvm.sysroot(...)` |
| Python | Pure Python is platform-independent; wheels with native code must exist for the target | `pip.parse` can download wheels per target platform; check the rules_python docs for your version's multi-platform support |
| JS/TS | Platform-independent, except native npm packages | Native packages publish per-platform optional dependencies |
| Java | Platform-independent bytecode | Remote JDKs exist for each exec platform |
| Images | Base pulled with `platforms = [...]`, one `oci_image` built through a platform transition per architecture, joined by `oci_image_index` | See the images chapter |

#### One command, both architectures

```starlark
# services/api/BUILD.bazel
load("@aspect_bazel_lib//lib:transitions.bzl", "platform_transition_filegroup")

[
    platform_transition_filegroup(
        name = "api_" + arch,
        srcs = [":api"],
        target_platform = "//platforms:linux_" + arch,
    )
    for arch in ["amd64", "arm64"]
]

filegroup(name = "api_all_arch", srcs = [":api_amd64", ":api_arm64"])
```

```bash
bazel build //services/api:api_all_arch
bazel cquery //services/api:api_all_arch --output=files
```

> **Gotcha.** `--platforms` accepts a list, but only the first value is used for ordinary targets. Passing `--platforms=a,b` does not build twice. Use transitions, as above, to produce several architectures in one invocation.

### Remote execution: making the exec platform real

With remote execution, the exec platform must describe the worker accurately and every toolchain must be runnable there.

```text
# .bazelrc
build:rbe --extra_execution_platforms=//platforms:rbe_linux_amd64
build:rbe --host_platform=//platforms:rbe_linux_amd64
build:rbe --platforms=//platforms:linux_amd64
```

| Check | How |
|---|---|
| The exec platform is the remote one | `--toolchain_resolution_debug` shows `//platforms:rbe_linux_amd64` selected |
| No host tools leak into actions | `bazel aquery //x --output=text` shows no `/usr/bin/` or `/home/` paths |
| macOS laptops work with Linux workers | Toolchains with `exec_compatible_with = linux` resolve to the remote platform; local-only actions (`no-remote-exec`) still need a macOS toolchain |
| The container image matches `exec_properties` | Pin it by digest; a floating tag changes the environment without changing cache keys |

> **One-way door.** `exec_properties` such as the container image are part of the action key. Changing the worker image digest invalidates every remotely executed action at once: the next build is a cold build for everyone. Bump it deliberately, ideally right after a release and with the cache warmed by a main-branch build.

### Platform checklist

- [ ] Every target platform lists both an OS and a CPU constraint.
- [ ] Toolchains are hermetic (downloaded, pinned), registered in `MODULE.bazel`, and the specific ones are registered before the general ones.
- [ ] Tools are in `cfg = "exec"` attributes; shipped code is not.
- [ ] Custom flags are build settings, not `--define`, and each `select()` branch has been proven with a `cquery`.
- [ ] Platform-only targets use `target_compatible_with`, not `manual`.
- [ ] Multi-arch outputs come from transitions in one build, not from repeated `--platforms` invocations.
- [ ] `bazel config` shows a short, explainable list of configurations.


## 09 · Testing at scale

*A test is an action whose output is pass or fail, so unchanged tests never run. Sizes, the test environment, sharding, flakes, services, coverage and JUnit.*

### What a test target actually is

A test target is a rule whose name ends in `_test` and whose output is an executable. `bazel test` builds it, then runs it as a **test action**: a sandboxed process with a fixed environment, a timeout, a resource reservation and two outputs Bazel cares about, an exit code and an optional JUnit XML file. Exit code `0` is a pass; anything else is a fail.

Because the run is an action, it has an action key like any compile. If none of the test's inputs changed (binary, runfiles, `data`, env, flags that reach it), Bazel reports `(cached) PASSED` and does not run it again. That single property is why `bazel test //...` stays fast on a large repo, and why a test that reads anything it did not declare is the most expensive bug you can have: it passes from cache forever after the thing it secretly depends on has broken.

| Piece | Where it comes from | What it means for you |
|---|---|---|
| The binary | `srcs`, `deps`, `embed` | Changes rebuild and rerun the test |
| Runfiles | `data`, plus the runfiles of every dep | Files the test may read at runtime, laid out in a symlink tree |
| Environment | Bazel's fixed test env, `env` attribute, `--test_env` | Your shell's env does **not** leak in |
| Timeout | `size` or `timeout` attribute, `--test_timeout` | Exceeding it is a failure, reported as `TIMEOUT` |
| Resources | `size`, `tags` such as `cpu:4` | Used by Bazel's local scheduler, not a cgroup limit |
| Outputs | `test.log`, `test.xml`, `test.outputs/` | Under `bazel-testlogs/<package>/<name>/` |

> **Gotcha.** "Cached PASSED" is a statement about inputs, not about the world. A test that talks to a staging database, reads `$HOME/.config`, or calls the internet is cached on the first pass and never reruns. Either declare what it reads, or tag it `external` (never cached) and run it from a separate job.

### Sizes, timeouts and resources

`size` is one attribute doing two jobs: it sets the default timeout and the resources Bazel reserves when it schedules the test locally.

| `size` | Default `timeout` | Seconds | Reserved RAM (local) | Reserved CPU |
|---|---|---|---|---|
| `small` | `short` | 60 | 20 MB | 1 |
| `medium` (default) | `moderate` | 300 | 100 MB | 1 |
| `large` | `long` | 900 | 300 MB | 1 |
| `enormous` | `eternal` | 3600 | 800 MB | 1 |

You can set `timeout` separately when a test is light but slow, for example a small unit test that waits on a long retry loop:

```starlark
go_test(
    name = "backoff_test",
    size = "small",          # light on resources
    timeout = "moderate",    # but allowed 300 s
    srcs = ["backoff_test.go"],
    embed = [":backoff"],
)
```

Override the numbers for a whole run, for example on a slow shared runner:

```bash
# short,moderate,long,eternal in seconds
bazel test //... --test_timeout=120,600,1800,3600

# warn when a test is far inside its timeout and could be a size smaller
bazel test //... --test_verbose_timeout_warnings
```

A test that needs more cores than one says so with a tag. The reservation only affects how many tests Bazel runs in parallel; it does not cap the process.

```starlark
py_test(
    name = "train_test",
    size = "large",
    srcs = ["train_test.py"],
    tags = ["cpu:4"],        # reserve 4 CPUs when scheduling locally
    deps = [":model"],
)
```

> **Field note.** Set sizes honestly and turn on `--test_verbose_timeout_warnings` in CI for a week. The warnings tell you which `medium` tests finish in two seconds. Moving them to `small` changes nothing about correctness, but it lets the scheduler pack many more of them onto a runner.

### The test environment

Bazel runs each test with a known environment. Test frameworks wired up by the rule sets read these variables for you; when you write a test runner or a shell test, you read them directly.

| Variable | Set to | Use it for |
|---|---|---|
| `TEST_TMPDIR` | A private, writable, empty directory | Scratch files. `HOME` also points here |
| `TEST_UNDECLARED_OUTPUTS_DIR` | A writable directory collected after the run | Screenshots, traces, dumps you want to keep as artifacts |
| `TEST_UNDECLARED_OUTPUTS_ANNOTATIONS_DIR` | A writable directory | Short annotation files that tools surface beside results |
| `XML_OUTPUT_FILE` | Path the test may write JUnit XML to | Per-testcase results; if absent, Bazel writes a minimal XML itself |
| `TESTBRIDGE_TEST_ONLY` | Value of `--test_filter` | The framework's own filter (Go `-test.run`, pytest `-k`, gtest filter) |
| `TEST_SHARD_INDEX` / `TEST_TOTAL_SHARDS` | Shard number and count | Which slice of test cases this process runs |
| `TEST_SHARD_STATUS_FILE` | A path | The test touches it to confirm it understood sharding |
| `TEST_PREMATURE_EXIT_FILE` | A path | Frameworks create it at start and delete at clean exit, so an early `exit(0)` is caught |
| `TEST_SRCDIR`, `RUNFILES_DIR` | Runfiles root | Locating `data` files |
| `TEST_WORKSPACE` | Main repo's name in runfiles | Building runfiles paths by hand |
| `TEST_TARGET`, `TEST_SIZE`, `TEST_TIMEOUT` | The label, size and timeout | Logging, adapting behaviour to the budget |
| `TEST_RANDOM_SEED` | Varies per run with `--runs_per_test` | Seeding randomised tests reproducibly |

```bash
# pass a variable through explicitly; nothing else from your shell reaches the test
bazel test //lib/auth:auth_test --test_env=LOG_LEVEL=debug

# pass through the value from your shell (by name only)
bazel test //e2e:smoke_test --test_env=KUBECONFIG
```

```starlark
sh_test(
    name = "render_test",
    srcs = ["render_test.sh"],
    data = ["//deploy:manifest", "testdata/expected.yaml"],
    env = {"DIFF_CONTEXT": "3"},   # fixed env, part of the cache key
)
```

> **Gotcha.** `--test_env=NAME` without a value inherits from your shell, so it becomes part of the action key. A token or a timestamp passed that way means the test never caches and may differ between machines. Pass stable values only, or tag the test `external`.

#### Runfiles: reading data files the portable way

Runfiles are a symlink tree (or a manifest file on platforms without symlinks) next to the test binary. Never build paths relative to the source tree or the current directory; use your language's runfiles library, which handles Bzlmod's repo-name mapping for you.

| Language | Library | Typical call |
|---|---|---|
| Go | `@rules_go//go/runfiles` | `runfiles.Rlocation("_main/lib/auth/testdata/key.pem")` |
| Python | `@rules_python//python/runfiles` | `runfiles.Create().Rlocation("_main/lib/auth/testdata/key.pem")` |
| Shell | `@bazel_tools//tools/bash/runfiles` | `$(rlocation _main/lib/auth/testdata/key.pem)` |
| C++ | `@rules_cc//cc/runfiles` | `Runfiles::CreateForTest()->Rlocation(...)` |
| Java | `@bazel_tools//tools/java/runfiles` | `Runfiles.preload().unmapped().rlocation(...)` |

`_main` is the runfiles name of the main repository under Bzlmod. For files in external repos, the libraries translate apparent names (`@pypi`) to canonical ones, provided you pass the correct source repository, which the rule-set helpers do.

> **Version-sensitive.** The runfiles directory name of the main repo changed with Bzlmod (it is `_main`, not your old WORKSPACE name), and canonical names of external repos changed separator from `~` to `+` in Bazel 8. Code that hard-codes either breaks on upgrade. The runfiles libraries are the fix.

### Running, filtering and reading results

```bash
bazel test //...                                    # everything; unchanged tests come from cache
bazel test //lib/... --test_output=errors           # print logs of failing tests only
bazel test //lib/auth:auth_test --test_output=streamed   # live output; runs tests one at a time
bazel test //lib/auth:auth_test --test_filter='TestVerify'      # framework-level filter
bazel test //lib/auth:auth_test --test_arg=-test.v --test_arg=-test.count=1
bazel test //... --build_tests_only                 # skip building non-test targets matched by //...
bazel test //... --notest_keep_going                # stop at the first failing test
bazel test //lib/auth:auth_test --nocache_test_results   # rerun even if cached; short form -t-
bazel test //lib/auth:auth_test --cache_test_results=no  # same thing, explicit
```

#### Output and summary modes

| `--test_output` | Shows | Use when |
|---|---|---|
| `summary` (default) | Pass/fail per target only | Interactive runs where you'll open logs yourself |
| `errors` | Full log of each failing test | CI and most daily work. Put it in `.bazelrc` |
| `all` | Full log of every test | Rarely; huge on a real repo |
| `streamed` | Live stdout/stderr | Debugging one test. Forces sequential, uncached-feeling runs |

| `--test_summary` | Shows |
|---|---|
| `short` (default) | One line per test target that ran |
| `terse` | Only failures and a count. Good default for `.bazelrc` |
| `detailed` | Per-testcase pass/fail parsed from the XML |
| `testcase` | Per-testcase counts per target |
| `none` | Nothing |

#### Filters

```bash
bazel test //... --test_tag_filters=-integration,-e2e     # exclude by tag (leading -)
bazel test //... --test_tag_filters=smoke                 # only targets tagged smoke
bazel test //... --test_size_filters=small,medium
bazel test //... --test_timeout_filters=-eternal
bazel test //... --test_lang_filters=go,py                # by rule name prefix: go_test, py_test

# exclude a subtree with a target pattern; the -- stops flag parsing
bazel test -- //... -//e2e/...
```

Tag filters apply only to test targets. To keep a test out of `//...` entirely, tag it `manual`; to keep it in `//...` but skip it in the default CI job, tag it with a domain word (`integration`, `e2e`) and filter.

#### Where the results land

```text
bazel-testlogs/lib/auth/auth_test/
├── test.log            # combined stdout/stderr
├── test.xml            # JUnit XML: from the framework, or generated by Bazel
├── test.outputs/       # TEST_UNDECLARED_OUTPUTS_DIR, often zipped as outputs.zip
├── test.cache_status   # cache metadata
└── coverage.dat        # after bazel coverage
```

With sharding or `--runs_per_test`, each shard and run gets its own subdirectory (`shard_2_of_8/`, `run_3_of_50/`).

> **Version-sensitive.** Whether undeclared outputs are zipped into `outputs.zip` or left as a directory is controlled by `--zip_undeclared_test_outputs`, and its default has moved between releases. Check yours with `bazel help test | grep -A2 zip_undeclared` before writing a CI step that expects one shape.

### Flakes: hunt, quarantine, fix

A flaky test is one whose result changes without its inputs changing. Bazel gives you three tools for them: run it many times, retry it automatically, and isolate it.

#### Hunting

```bash
# run one test 200 times, in parallel, uncached
bazel test //lib/queue:consumer_test --runs_per_test=200 --jobs=32 --test_output=errors

# apply a run count only to targets matching a regex
bazel test //lib/... --runs_per_test='//lib/queue:.*@50'

# report "FLAKY" rather than "FAILED" when some runs pass
bazel test //lib/queue:consumer_test --runs_per_test=50 --runs_per_test_detects_flakes

# reproduce with the same seed the failing run had (read it from that run's test.log)
bazel test //lib/queue:consumer_test --test_env=TEST_RANDOM_SEED=1234
```

Common causes, in rough order of frequency:

| Cause | Tell-tale sign | Fix |
|---|---|---|
| Fixed ports | `address already in use` when tests run in parallel | Bind port 0 and read back the assigned port |
| Shared state outside `TEST_TMPDIR` | Fails only when run alongside another test | Write only under `TEST_TMPDIR` |
| Wall-clock timing | Fails on loaded runners, passes on laptops | Inject a clock; wait on conditions, not sleeps |
| Test order inside a target | Fails only with a particular `--test_filter` or shard split | Make each case set up its own state |
| Network or external service | Fails in bursts across many tests | Hermetic fake, or move to a tagged integration suite |
| Resource starvation | Timeouts under `--jobs` high | Honest `size`, a `cpu:N` tag, or `exclusive` |

#### Retrying and quarantining

```bash
# CI-wide: retry failures up to 2 times; reported as FLAKY if a retry passes
bazel test //... --flaky_test_attempts=2

# only for a known-bad area
bazel test //... --flaky_test_attempts='//legacy/.*@3'
```

```starlark
go_test(
    name = "consumer_test",
    srcs = ["consumer_test.go"],
    embed = [":queue"],
    flaky = True,               # retried up to 3 times by default
    tags = ["quarantine"],      # filterable: --test_tag_filters=-quarantine
)
```

> **Gotcha.** `flaky = True` is a permanent comment that nobody reads. Prefer a CI-wide `--flaky_test_attempts=2`, plus a dashboard (BES or the JUnit report) listing tests that needed a retry. Quarantine with a tag and an issue link in the BUILD file, and remove the tag when the issue closes.

### Sharding

Sharding splits one test target across several processes. Bazel sets `TEST_TOTAL_SHARDS` and `TEST_SHARD_INDEX`; the framework decides which test cases each shard runs. Go, gtest, JUnit and pytest (through rules_python's runner or a sharding plugin) understand the protocol; a plain shell test does not.

```starlark
go_test(
    name = "conformance_test",
    size = "large",
    srcs = ["conformance_test.go"],
    embed = [":parser"],
    shard_count = 8,
)
```

```bash
bazel test //lib/parser:conformance_test --test_sharding_strategy=explicit   # honour shard_count (default)
bazel test //lib/parser:conformance_test --test_sharding_strategy=disabled   # run unsharded, for debugging
```

The framework signals that it understood sharding by touching `TEST_SHARD_STATUS_FILE`. If it does not, Bazel runs every case in every shard and, depending on the release, warns or fails. Shards are separate actions, so each caches and retries on its own.

Shard a test when it is large and on the critical path. Splitting it into several smaller test targets is usually better, because each target then caches independently of the others.

### Tests that need the outside world

#### Tags that relax the rules

| Tag | Effect | Cost |
|---|---|---|
| `requires-network` | The sandbox allows network for this action | Results depend on the network; cache with care |
| `exclusive` | No other test runs at the same time | Serialises CI around it |
| `external` | Never cached; always reruns | Pays its full runtime every build |
| `no-remote-exec` | Executes locally, may still use the remote cache | Fine for tests needing host devices or sockets |
| `no-remote` | Neither executed nor cached remotely | Use when results must not be shared |
| `no-sandbox` | Runs without the sandbox | Hides undeclared inputs. Last resort |
| `local` | Local, unsandboxed, uncached | The heaviest hammer |
| `manual` | Excluded from `//...` and `:all` | Run only when named explicitly |

#### Pattern 1: test-scoped fixtures (preferred)

Start what the test needs inside the test, on random ports, writing under `TEST_TMPDIR`. Embedded or in-process versions exist for many services: a Postgres binary fetched as a Bazel dependency and started by the test, an in-memory Redis-compatible server, a fake S3 such as a MinIO binary in `data`. The test stays hermetic, runs in the sandbox, caches, and can run remotely.

```starlark
go_test(
    name = "store_integration_test",
    size = "medium",
    srcs = ["store_integration_test.go"],
    embed = [":store"],
    data = ["@postgres_bin//:bin"],     # a pinned binary, not the host's postgres
    env = {"PG_BIN": "$(rlocationpath @postgres_bin//:bin)"},
)
```

#### Pattern 2: a manual suite run by a dedicated job

When a test genuinely needs a cluster, a running stack or a GPU, keep it out of the default run and give it its own CI job.

```starlark
test_suite(
    name = "e2e",
    tags = ["manual"],                 # keep the suite itself out of //...
    tests = [
        "//e2e/ingest:klv_roundtrip_test",
        "//e2e/api:auth_flow_test",
    ],
)
```

```bash
bazel test //e2e:e2e --config=ci --test_env=APP_BASE_URL
```

#### Testcontainers and Docker inside the sandbox

Testcontainers-style tests talk to a Docker or Podman socket on the host. The Linux sandbox mounts most of the host read-only and blocks the network unless `requires-network` is set, so these tests usually need some combination of `requires-network`, `no-remote-exec` and either `no-sandbox` or an explicit writable path for the socket. They can never run on remote executors that lack a daemon.

```starlark
java_test(
    name = "kafka_it",
    size = "large",
    srcs = ["KafkaIT.java"],
    tags = [
        "requires-network",
        "no-remote-exec",
        "exclusive",        # containers compete for the same host resources
        "integration",
    ],
    deps = ["@maven//:org_testcontainers_kafka"],
)
```

> **Field note.** If more than a handful of tests need containers, that is a signal to move them to Pattern 2 and run them against one shared stack per job, rather than starting a dozen containers per test. Verify your exact tag combination on one test before you roll it out; socket permissions differ between Docker, rootless Podman and the CI image.

### `test_suite`

`test_suite` groups tests by label so a person or job can run them by one name. With no `tests` attribute, it collects every test in its package, filtered by its `tags`.

```starlark
# all tests in this package tagged "smoke"
test_suite(
    name = "smoke",
    tags = ["smoke"],
)

# an explicit list across packages
test_suite(
    name = "release_gate",
    tests = [
        "//services/api:api_test",
        "//services/worker:worker_test",
        "//lib/auth:auth_test",
    ],
)
```

A `test_suite` is resolved during loading, so `bazel query 'tests(//:release_gate)'` lists exactly what it will run.

### Coverage

```bash
bazel coverage //lib/... \
  --combined_report=lcov \
  --instrumentation_filter='^//lib[/:]'

# one combined lcov file
ls "$(bazel info output_path)/_coverage/_coverage_report.dat"

# per-test lcov files
find -L bazel-testlogs -name coverage.dat

# HTML for humans
genhtml --output coverage-html "$(bazel info output_path)/_coverage/_coverage_report.dat"
```

| Flag | Effect |
|---|---|
| `--instrumentation_filter=REGEX` | Which targets get instrumented. Defaults to the packages of the tests you ran, which is rarely what you want in a monorepo |
| `--instrument_test_targets` | Also instrument test code itself (off by default) |
| `--combined_report=lcov` | Merge per-test reports into one file |
| `--nocache_test_results` | Force a fresh run; coverage results are cached like test results |

Per-language notes:

| Language | Notes |
|---|---|
| Go | Works with rules_go out of the box; emits lcov through Bazel's coverage merger |
| Python | Needs coverage.py: set `configure_coverage_tool = True` on `python.toolchain(...)` in `MODULE.bazel` |
| C/C++ | gcc uses gcov; clang uses llvm-cov. Hermetic toolchains (toolchains_llvm) must ship the matching tools. Check the toolchain's docs for the flags it expects |
| Java | Built in (JaCoCo) |
| JS/TS | Depends on the test runner rule (Jest, Vitest, Mocha via rules_js); check that rule set's coverage docs |

> **Gotcha.** Coverage builds use different flags, so they have different action keys from normal test builds. Running `bazel coverage` and `bazel test` alternately on the same output base discards the analysis cache each time. Give coverage its own CI job, or its own `--output_base` locally.

### JUnit in GitLab

GitLab's test report reads JUnit XML. Bazel writes one `test.xml` per test target (per shard and per run), so collect them after the run, keeping the directory structure so names don't collide.

```yaml
test:
  script:
    - bazel test --config=ci //...
  after_script:
    - mkdir -p reports
    - find -L bazel-testlogs -name test.xml -exec cp --parents {} reports/ \; || true
  artifacts:
    when: always            # failing jobs are exactly when you want the report
    reports:
      junit: reports/**/test.xml
```

When a framework writes its own XML to `XML_OUTPUT_FILE`, GitLab shows per-testcase names and failure messages. When it doesn't, Bazel's generated XML has one testcase per target, which still shows pass/fail but not which case failed. Go (rules_go), pytest (via rules_python), JUnit and gtest all write proper XML.

### `--run_under`: wrap the test process

`--run_under` prefixes the test (or `bazel run` binary) with another command. The wrapper can be a label, which Bazel builds, or a host command.

```bash
bazel test //lib/codec:klv_test --run_under='gdb --args'                 # debugger
bazel test //lib/codec:klv_test --run_under='valgrind --error-exitcode=1' # memory errors
bazel test //lib/codec:klv_test --run_under='strace -f -o /tmp/st.txt'    # what does it touch
bazel test //lib/queue:consumer_test --run_under='timeout 30'             # tighter local limit
bazel test //lib/api:api_test --run_under=//tools/testing:with_fake_clock # your own wrapper target
```

`--run_under` changes the action key, so wrapped runs don't pollute the normal cache entries.

> **Note.** For interactive debugging, `bazel test --test_output=streamed --run_under='gdb --args'` gives you a live session. Add `--test_timeout=3600` or the test's own timeout will kill the debugger mid-session.

### Checklist for a healthy test tree

- Every test has an honest `size`, and `--test_verbose_timeout_warnings` runs in CI.
- No test reads outside its runfiles and `TEST_TMPDIR`; anything that must is tagged and filtered.
- Integration and end-to-end suites are `manual` or tag-filtered, with their own jobs.
- `--test_output=errors` and `--test_summary=terse` are in `.bazelrc`.
- Retries are CI-wide and visible, not `flaky = True` scattered through BUILD files.
- JUnit XML is collected with `when: always`.
- Coverage runs in its own job with an explicit `--instrumentation_filter`.


## 10 · Remote cache and execution

*Built once, for everyone. Disk and remote caches, standing up bazel-remote and Buildbarn, the trust model, measuring hit rates, and finding the action key that differs.*

### Two caches, one protocol

Bazel caches execution results at two levels, and both use the same two-table model from chapter 02: an **Action Cache** (AC) mapping an action key to the digests of its outputs, and a **Content-Addressable Store** (CAS) mapping each digest to bytes.

| Cache | Lives | Shared with | Set with |
|---|---|---|---|
| Disk cache | A directory on this machine | Every workspace and output base on the machine | `--disk_cache=PATH` |
| Remote cache | A server speaking the Remote Execution API (gRPC) or plain HTTP | Everyone pointed at it | `--remote_cache=URL` |
| Remote execution | A cluster that also runs actions | Everyone pointed at it | `--remote_executor=URL` |

You can use the disk and remote caches together. Bazel checks the disk cache first, then the remote one, and writes results to both (subject to the upload flags).

> **Note.** Neither cache is the output base. The output base (`bazel info output_base`) holds this workspace's in-memory graph state, external repos and the current outputs. Deleting it is a `bazel clean --expunge`; the disk and remote caches survive and make the next build fast again.

### The disk cache

```bash
# in ~/.bazelrc or the repo .bazelrc
build --disk_cache=~/.cache/bazel-disk
```

The disk cache is the cheapest speedup there is. Switching branches, running `bazel clean`, or working in two clones of the same repo all become mostly cache hits.

#### Keeping it bounded

Older Bazel releases never shrank the disk cache; it grew until you deleted it. Bazel 7.4 added built-in garbage collection, which runs while the server is idle.

```bash
build --experimental_disk_cache_gc_max_size=60G
build --experimental_disk_cache_gc_max_age=14d
```

> **Version-sensitive.** These flags were introduced with an `experimental_` prefix. Later releases may have dropped it. Confirm the exact names on your version with `bazel help build | grep disk_cache_gc` before committing them to `.bazelrc`. Without GC, a cron job deleting files older than N days by access time is a workable fallback.

### Remote cache protocols

| Scheme | Protocol | Notes |
|---|---|---|
| `grpc://`, `grpcs://` | Remote Execution API v2 over gRPC | The full protocol: batch reads, `FindMissingBlobs`, compression, remote execution. Prefer it |
| `http://`, `https://` | Simple HTTP GET/PUT of `/ac/KEY` and `/cas/DIGEST` | Works with any WebDAV-ish server or object store front end. No batching, no remote execution |
| `unix://` | gRPC over a Unix socket | A local cache proxy on the same host |

```bash
bazel build //... --remote_cache=grpcs://bazel-cache.internal
bazel build //... --remote_cache=https://bazel-cache.internal/cache
```

#### Flags that matter for a cache client

| Flag | Default | What it does |
|---|---|---|
| `--remote_cache=URL` | none | Enables the remote cache |
| `--remote_upload_local_results` | true | Write results of locally executed actions back to the cache |
| `--remote_accept_cached` | true | Read from the cache. Turn off to force a rebuild while still uploading |
| `--remote_instance_name=NAME` | empty | Namespaces the cache on servers that support it |
| `--remote_timeout=DURATION` | 60s | Per-call timeout. Raise for large blobs on slow links |
| `--remote_retries=N` | 5 | Retries on transient errors |
| `--remote_max_connections=N` | 100 | Concurrent connections to the backend |
| `--remote_cache_compression` | false | zstd-compress blobs over the wire, if the server supports it |
| `--remote_local_fallback` | false | With remote execution: run locally if the remote call fails |
| `--remote_header=K=V` | none | Extra header on every call; usually an auth token |
| `--remote_cache_header=K=V` | none | Header only for cache calls (when cache and executor differ) |
| `--credential_helper=[SCOPE=]PATH` | none | External program that returns headers per URL, so tokens never sit in an rc file |
| `--remote_proxy=URL` | none | Route remote calls through a proxy |

```bash
# laptops: read the shared cache, don't write to it
build --remote_cache=grpcs://bazel-cache.internal
build --noremote_upload_local_results

# CI on the default branch: read and write
build:ci --remote_upload_local_results
```

### Build without the Bytes

With a remote cache or executor, most intermediate outputs never need to land on your disk. Bazel only needs their digests to compute downstream keys. Build without the Bytes (BwoB) controls which outputs are downloaded.

| `--remote_download_outputs` | Downloads | Shorthand | Use when |
|---|---|---|---|
| `all` | Every output of every action | `--remote_download_all` | Tools that scan `bazel-out/` expect files there |
| `toplevel` (default since 7.0) | Outputs of the targets you asked for, plus what `bazel run` and tests need | `--remote_download_toplevel` | Daily work and CI |
| `minimal` | Almost nothing | `--remote_download_minimal` | CI jobs that only need pass/fail, or that push images from the cache |

```bash
# fetch only outputs matching a regex in addition to the mode's defaults
bazel build //app --remote_download_regex='.*\.(json|xml)$'
```

> **Gotcha.** BwoB assumes the cache still holds the blobs it skipped. If the server evicts a blob between Bazel learning its digest and needing it, the build fails with a lost-input error. Bazel can rerun the producing actions in this case ("rewinding"); Bazel 10.0 turns `--rewind_lost_inputs` on by default according to its release notes. On 9.x, size the cache so blobs live for at least a working day, and check `bazel help build | grep -E 'rewind|eviction'` for what your version offers.

### Standing up bazel-remote

[bazel-remote](https://github.com/buchgr/bazel-remote) is a single Go binary with a disk-backed LRU store. It speaks gRPC (REAPI cache subset) and HTTP, and runs happily in an air-gapped network. It is the right first shared cache.

```bash
docker run -d --name bazel-remote --restart=always \
  -u 1000:1000 \
  -v /srv/bazel-remote:/data \
  -v /etc/bazel-remote:/etc/bazel-remote:ro \
  -p 8080:8080 -p 9092:9092 \
  quay.io/bazel-remote/bazel-remote:latest \
    --dir=/data \
    --max_size=500 \
    --storage_mode=zstd \
    --tls_cert_file=/etc/bazel-remote/tls.crt \
    --tls_key_file=/etc/bazel-remote/tls.key \
    --htpasswd_file=/etc/bazel-remote/htpasswd \
    --enable_endpoint_metrics
```

| Flag | Meaning |
|---|---|
| `--dir` | Storage directory. Put it on fast local SSD, not network storage |
| `--max_size` | Cache size in GiB. LRU eviction above it |
| `--storage_mode=zstd` | Store blobs compressed; pairs with `--remote_cache_compression` on clients |
| `--port`, `--grpc_port` | HTTP (8080) and gRPC (9092) listeners |
| `--tls_cert_file`, `--tls_key_file` | Serve TLS |
| `--tls_ca_file` | Require client certificates signed by this CA (mTLS) |
| `--htpasswd_file` | Basic auth for both HTTP and gRPC |
| `--allow_unauthenticated_reads` | Anyone may read; only authenticated clients may write |
| `--enable_endpoint_metrics` | Prometheus metrics per endpoint |

> **Field note.** `--htpasswd_file` plus `--allow_unauthenticated_reads` gives you the trust model below with no extra moving parts: laptops and merge-request jobs read anonymously from inside the network, and only the CI credential on protected branches can write. Pin the image by digest in production and mirror it into your registry for the air-gap.

#### Pointing clients at it

```bash
# reads, anonymous
build:cache --remote_cache=grpcs://bazel-cache.internal:9092
build:cache --remote_cache_compression

# writes, CI only: basic auth in the URL from a masked CI variable
#   bazel test --config=ci --remote_cache=grpcs://ci:${BAZEL_CACHE_PASSWORD}@bazel-cache.internal:9092 //...
```

#### Sizing

| Repo profile | Start at | Then |
|---|---|---|
| A few services, one language | 100 GiB | Watch the eviction rate in metrics |
| Monorepo, several languages, daily CI on main | 500 GiB | Size so blobs survive at least 2–3 days of main-branch builds |
| Remote execution | 1–2 TiB, split CAS and AC | Follow the backend's own guidance |

Run it on a host close to the CI runners. Cache traffic is many small round trips, so latency matters more than bandwidth.

### Buildbarn for remote execution

[Buildbarn](https://github.com/buildbarn) is an open-source (Apache-2.0) implementation of the Remote Execution API, written in Go and designed to run on Kubernetes. It is made of separate services you compose:

| Component | Role |
|---|---|
| `bb-storage` as frontend | The endpoint Bazel talks to. Routes cache calls to storage and execution calls to the scheduler |
| `bb-storage` as storage | CAS and AC shards on local disk, often several replicas behind consistent hashing |
| `bb-scheduler` | Queues actions and hands them to workers by platform properties |
| `bb-worker` | Fetches inputs into a build directory, asks the runner to execute, uploads outputs |
| `bb-runner` | Runs the actual command inside the worker pod's container image |
| `bb-browser` | Web UI for inspecting actions, inputs, outputs and failures by digest |

```text
bazel ──grpcs──▶ frontend ──▶ storage (CAS + AC shards)
                     │
                     └──────▶ scheduler ──▶ worker + runner pods (per platform image)
                                               │
                                               └──▶ storage
```

The [bb-deployments](https://github.com/buildbarn/bb-deployments) repository has working Kubernetes manifests and Jsonnet configuration. Start from those rather than writing configuration from scratch; the config schema is large and changes between releases.

The Bazel side is short:

```bash
build:rbe --remote_executor=grpcs://bb-frontend.internal
build:rbe --remote_instance_name=main
build:rbe --extra_execution_platforms=//platforms:rbe
build:rbe --host_platform=//platforms:rbe
build:rbe --jobs=200
build:rbe --remote_timeout=3600
build:rbe --remote_local_fallback
```

The platform (chapter 08) carries `exec_properties`, such as the container image the runner uses. The scheduler matches those properties against what each worker pool advertises.

> **One-way door.** Remote execution is reversible technically, but organisationally it is a service with an on-call. Workers, storage shards and images need upgrades, capacity planning and incident response. Get the remote cache hit rate above 95% across machines first; most teams find that a cache alone delivers most of the speedup without the cluster.

#### Rolling remote execution out gradually

```bash
# only Go compiles and links remotely; everything else stays local
build:rbe-go --config=cache
build:rbe-go --remote_executor=grpcs://bb-frontend.internal
build:rbe-go --spawn_strategy=local
build:rbe-go --strategy=GoCompilePkg=remote --strategy=GoLink=remote
```

Watch the failures that remote execution exposes: tools read from `/usr/bin`, absolute paths, actions that write outside their outputs, tests needing devices. Each is a hermeticity bug that was already costing you cache hits.

### The cache trust model

A remote cache is a code-execution channel: whoever can write to the AC decides what output a given action key produces for everyone else. Treat write access like push access to the default branch.

| Writer | Allowed to write? | Why |
|---|---|---|
| CI on protected branches (main, release) | Yes | Code is reviewed; runners are trusted |
| CI on merge requests from the same project | Usually read-only | The code isn't reviewed yet; a malicious MR could poison keys others will hit |
| CI on forks | Read-only, or no access | Untrusted code |
| Developer laptops | Read-only | Laptops are non-hermetic in ways you can't see; uploads spread their quirks |
| Remote execution workers | Yes, by design | The service writes results it computed itself |

```yaml
# .gitlab-ci.yml: write credential only on protected branches
.cache-write:
  rules:
    - if: $CI_COMMIT_REF_PROTECTED == "true"
  variables:
    BAZEL_CACHE_FLAGS: "--remote_upload_local_results"

.cache-read:
  variables:
    BAZEL_CACHE_FLAGS: "--noremote_upload_local_results"
```

> **Gotcha.** A read-only token that the server doesn't enforce is not read-only. Enforce it on the server (bazel-remote's `--allow_unauthenticated_reads` with a write password only CI has, or per-token permissions in a commercial backend), not only with the client flag.

### Measuring the hit rate

Every build ends with a process summary:

```text
INFO: 2,431 processes: 2,380 remote cache hit, 37 internal, 14 linux-sandbox.
```

- `remote cache hit` and `disk cache hit`: served from cache.
- `internal`: Bazel's own bookkeeping actions (symlinks, runfiles trees). Not cacheable, normal.
- `linux-sandbox`, `processwrapper-sandbox`, `worker`, `local`: ran locally.
- `remote`: ran on a remote executor.

The meaningful test is a **no-change rerun on a different machine**. Build on CI, then build the same commit on a clean runner or laptop with the cache. On a hermetic repo, nearly every non-internal process should be a hit.

### Finding non-hermetic action keys

When two machines miss each other's results, their action keys differ. The execution log records the key inputs of every spawn, so diffing two logs shows what differs.

```bash
# machine A (or a clean output base)
bazel clean
bazel build //app --execution_log_json_file=/tmp/exec_a.json

# machine B
bazel clean
bazel build //app --execution_log_json_file=/tmp/exec_b.json

# compare; sort keys so ordering noise disappears
diff <(jq -S . /tmp/exec_a.json) <(jq -S . /tmp/exec_b.json) | less
```

| Log | Flag | Notes |
|---|---|---|
| Compact | `--execution_log_compact_file=PATH` | Small, fast to write. Default choice for CI. Convert to JSON with the execlog converter in the Bazel source tree (`src/tools/execlog`) |
| JSON | `--execution_log_json_file=PATH` | Human-readable; slower and much larger. Fine for a one-off debug |
| Binary | `--execution_log_binary_file=PATH` | Protobuf; for your own tooling |

> **Version-sensitive.** The compact log arrived in Bazel 7.1, and the converter's command-line syntax has changed since. Check `bazel help build | grep execution_log` for your version's flags, and the README next to the converter in the Bazel source for its arguments.

What the diff usually shows:

| Differing field | Cause | Fix |
|---|---|---|
| `environmentVariables` (`PATH`, `HOME`, `LANG`) | Action env inherited from the shell | `--incompatible_strict_action_env`; remove `--action_env=NAME` without a value |
| `args` contains `/home/USER/...` or `/usr/bin/...` | Rule or toolchain uses host paths | Hermetic toolchain; patch the rule to use runfiles paths |
| One input digest differs | A generated file is non-deterministic (timestamps, map ordering, absolute paths) | Fix the generator; stamp only under `--config=release` |
| `platform` properties differ | Different exec platform or `exec_properties` | Same `--host_platform` / `--extra_execution_platforms` on both |
| Different set of inputs | Different flags select different deps | Align `.bazelrc`; `--config=ci` should add, not change, output-affecting flags |

### Build Event Protocol and results UIs

The Build Event Protocol (BEP) is a stream of everything that happened in an invocation: options, targets, actions, test results, timings, cache statistics. Send it to a server for a UI, or write it to a file.

```bash
# to a server
build:bes --bes_backend=grpcs://bes.internal
build:bes --bes_results_url=https://bes.internal/invocation/
build:bes --bes_upload_mode=fully_async
build:bes --bes_timeout=60s

# metadata that makes invocations searchable
build:ci --build_metadata=ROLE=CI
build:ci --build_metadata=REPO_URL=https://gitlab.internal/acme/mono
build:ci --build_metadata=COMMIT_SHA=${CI_COMMIT_SHA}

# to files, kept as CI artifacts
bazel test //... --build_event_json_file=bep.json
bazel test //... --build_event_binary_file=bep.pb
```

> **Note.** `--build_metadata` with `${CI_COMMIT_SHA}` only expands if the shell expands it, so put it on the command line in the CI script, not in `.bazelrc`.

| UI | Reads | Hosting | Notes |
|---|---|---|---|
| BuildBuddy | BES, plus its own cache and RBE | SaaS or self-hosted; open-core | The most complete invocation view: timings, cache stats, test history, flaky tests |
| bb-browser (Buildbarn) | Action and CAS digests | Self-hosted, Apache-2.0 | Inspect individual actions and failures. Not an invocation dashboard |
| EngFlow UI | BES and its RBE | Commercial | Part of the EngFlow platform |
| Your own | `bep.json` | Anywhere | `jq` over the JSON is enough for hit-rate and slowest-target reports |

```bash
# targets that completed, and the action summary (executed vs cached) from a BEP file
jq -r 'select(.id.targetCompleted) | .id.targetCompleted.label' bep.json | head
jq 'select(.buildMetrics) | .buildMetrics.actionSummary' bep.json
```

### Credentials without rc files

`--remote_header=Authorization=Bearer TOKEN` works but puts the token in an rc file or on the command line. A credential helper is a program Bazel runs to get headers for a URL, so the token stays in a secret store.

```bash
# .bazelrc: one helper for every *.internal host
common --credential_helper=*.internal=%workspace%/tools/credential-helper.sh
```

```bash
#!/usr/bin/env bash
# tools/credential-helper.sh: reads {"uri": "..."} on stdin, prints headers as JSON
set -euo pipefail
[ "${1:-}" = "get" ] || exit 1
token="$(cat "${BAZEL_CACHE_TOKEN_FILE:-$HOME/.config/bazel/cache-token}")"
printf '{"headers":{"Authorization":["Bearer %s"]}}\n' "$token"
```

The helper also covers authenticated downloads of external repos and registries, not only the cache.

> **Gotcha.** Values with spaces inside `.bazelrc` need quoting: `build --remote_header="Authorization=Bearer abc"`. Unquoted, Bazel splits it into two arguments and the command fails with a confusing error about the second one.

### Backend comparison

| Backend | Cache | Remote exec | Results UI | Licence | Air-gap fitness |
|---|---|---|---|---|---|
| bazel-remote | yes | no | metrics only | Apache-2.0 | Excellent: one binary, local disk, no outbound calls |
| Buildbarn | yes | yes | bb-browser | Apache-2.0 | Good: self-hosted on Kubernetes, but many components to operate |
| NativeLink | yes | yes | limited | Check the current licence; it has changed over time | Good when self-hosted |
| BuildBuddy | yes | yes | yes | Open-core: open-source edition plus proprietary enterprise features | Self-hosted works; confirm the features you need are in the edition you can run offline |
| EngFlow | yes | yes | yes | Commercial | Ask the vendor; usually deployed in your cloud |
| BuildGrid | yes | yes | limited | Apache-2.0 | Self-hosted; smaller community |
| HTTP object store (nginx WebDAV, S3-compatible) | yes, HTTP only | no | no | Varies | Works anywhere, but no batching and no compression |

> **Field note.** For an air-gapped environment the sequence is: disk cache on every machine, then bazel-remote on one host near the runners, then Buildbarn only if profiles show that local execution, not cache misses, is what's slow.


## 11 · Performance and profiling

*Open the profile before guessing. Critical path, analysis cost, memory, sandboxing strategies and workers, and how to benchmark a change honestly.*

### Measure before you tune

Every Bazel command writes a trace profile. Open it before changing anything. Most slow builds come down to one of five causes, and the profile tells you which within a minute:

1. **Analysis is slow** on a build where nothing changed: flags changed, or loading and analysis are expensive.
2. **The critical path is long**: one chain of actions that nothing can parallelise.
3. **Actions miss the cache** that should hit: non-hermetic keys (chapter 10).
4. **Local execution is starved**: sandbox overhead, too few cores, too little memory.
5. **The network is the bottleneck**: cache round trips or downloads.

The rest of this chapter is how to tell them apart and what to do about each.

### The trace profile

```bash
# written automatically for every command (overwritten by the next one)
ls "$(bazel info output_base)"/command.profile.gz

# write to a path you choose, with richer detail
bazel build //app \
  --profile=/tmp/app.profile.gz \
  --experimental_profile_include_target_label \
  --noslim_profile

# a terminal summary: phase times and the critical path
bazel analyze-profile /tmp/app.profile.gz
```

Open the `.profile.gz` file in [Perfetto](https://ui.perfetto.dev) (drag and drop; it stays in your browser) or `chrome://tracing`. It is a Chrome trace-event JSON file, gzipped.

| Flag | Effect |
|---|---|
| `--profile=PATH` | Where to write the profile |
| `--generate_json_trace_profile` | On by default; set `--nogenerate_json_trace_profile` to disable |
| `--experimental_profile_include_target_label` | Adds the target label to each action event. Makes the timeline readable |
| `--experimental_profile_include_primary_output` | Adds each action's primary output path |
| `--noslim_profile` | Keeps short events that are merged away by default |
| `--starlark_cpu_profile=PATH` | Separate pprof CPU profile of Starlark evaluation (loading and analysis) |

#### Reading the timeline

| Lane or event | What it means |
|---|---|
| `Build phase marker` events | Boundaries between launch, init, loading/analysis, execution, finish |
| `Critical Path` lane | The longest dependency chain through the build. The build cannot be shorter than this |
| `skyframe evaluator` threads | Work during loading and analysis, often overlapping execution |
| Action events (by mnemonic: `GoCompilePkg`, `CppCompile`, `Javac`, `TestRunner`) | One bar per action. Width is wall time |
| `remote cache check`, `download outputs`, `upload outputs` | Time spent talking to the cache |
| `sandbox.createFileSystem`, `sandbox.delete` | Sandbox setup and teardown per action |
| `Garbage collection` or JVM events | Heap pressure in the Bazel server |
| `action counters`, `CPU usage`, `Memory usage` tracks | Machine utilisation over time; idle CPU during execution means parallelism is blocked |

#### What `analyze-profile` prints

```text
=== PHASE SUMMARY INFORMATION ===
Total launch phase time            0.03 s    0.12%
Total init phase time              0.21 s    0.81%
Total target pattern evaluation    0.11 s    0.42%
Total interleaved loading-and-analysis phase time  6.40 s   24.70%
Total preparation phase time       0.04 s    0.15%
Total execution phase time        19.08 s   73.62%
Total finish phase time            0.05 s    0.18%

Critical path (14.22 s):
  Time Percentage   Description
  2.11 s   14.84%   action 'GoCompilePkg //lib/proto:proto'
  9.87 s   69.41%   action 'GoLink //services/api:api'
  ...
```

Read it top-down. A large loading-and-analysis share on a no-change build is cause 1. A critical path close to the execution phase time is cause 2. Execution far longer than the critical path, with idle CPU in the timeline, is cause 4 or 5.

> **Note.** Execution overlaps with analysis in modern Bazel ("Skymeld"), so the phase lines don't sum the way they did in older releases. Use the timeline when the summary looks inconsistent.

### Analysis time

On a warm server with unchanged flags, a no-op `bazel build //...` should take seconds even on a large repo. If it takes much longer, look for these.

| Symptom | Cause | Fix |
|---|---|---|
| `WARNING: Build option --X has changed, discarding analysis cache` | Different flags between invocations | Same `.bazelrc` for IDE, scripts and terminal; separate `--output_base` for tools with different flags |
| Server restarts (`Starting local Bazel server...`) on every command | Startup options differ, or the server was killed for memory | Keep `startup` flags in `.bazelrc`; check heap |
| Loading takes seconds per package | Big `glob()`s, expensive macros, huge `.bzl` files | Generated `srcs` lists (Gazelle), simpler macros, a Starlark CPU profile |
| Analysis of one target is slow | A rule flattens depsets (`.to_list()`) deep in the graph | Fix the rule (chapter 15): pass depsets, use `ctx.actions.args()` |
| `//...` is slow but specific targets are fast | `//...` includes far more than you think (vendored code, generated packages) | `.bazelignore`, `manual` tags, narrower patterns in CI |

```bash
# where loading/analysis time goes in Starlark
bazel build //... --nobuild --starlark_cpu_profile=/tmp/starlark.pprof
go tool pprof -top /tmp/starlark.pprof | head -30

# analysis only, no execution: isolates analysis cost
bazel build //... --nobuild
```

#### `--watchfs`

Without it, Bazel stats every source file it knows about at the start of each command to find changes. With it, Bazel asks the OS (inotify on Linux, FSEvents on macOS) what changed.

```bash
common --watchfs
```

On a large repo this turns a multi-second "checking cached actions" pause into near zero. If file changes are missed (some network filesystems, some container bind mounts), turn it off for that environment.

### The critical path

The critical path is the floor. Adding cores, a faster cache or remote execution cannot make the build shorter than its longest chain.

| Critical path dominated by | Typical fix |
|---|---|
| One large link (`GoLink`, `CppLink`) | Split the binary; for C++, a faster linker (lld or mold through the toolchain); fewer static deps |
| One huge compile unit | Split the library into smaller packages so dependents start earlier |
| A code generator that runs before everything | Cache it (stable inputs), split its output per consumer, or prebuild the tool |
| A long chain of small libraries | Flatten layering where a library depends on another only for one helper |
| One big test | Shard it, split it, or move it to a separate job |

```bash
# how many actions, of which kinds, a target needs
bazel aquery 'deps(//services/api)' --output=summary

# which libraries sit on the path between two targets
bazel query 'allpaths(//services/api, //lib/proto:proto)' --output=label
```

### Memory and the server

The Bazel server is a JVM holding the full build graph in memory. Too little heap shows up as long GC pauses, then as OOM kills.

```bash
bazel info used-heap-size-after-gc   # what the graph really needs after a full GC
bazel info peak-heap-size
bazel info max-heap-size

# give it more, in .bazelrc or user.bazelrc
startup --host_jvm_args=-Xmx12g

# per-phase heap usage, to compare before and after a change
bazel build //... --memory_profile=/tmp/mem.txt

# write a heap dump when the server runs out
build --heap_dump_on_oom
```

| Flag | Effect | Use on |
|---|---|---|
| `--discard_analysis_cache` | Drops the analysis graph once execution starts | CI: lower peak memory; next command re-analyses |
| `--nokeep_state_after_build` | Drops incremental state after the command | CI runners that won't run another build |
| `--notrack_incremental_state` | Doesn't keep the dependency edges needed for incremental builds | One-shot builds only; every subsequent build is from scratch |
| `--skyframe_high_water_mark_threshold` and friends | Tune when Bazel drops cached state under pressure | Rarely; check `bazel help build | grep high_water` |

> **Gotcha.** The incremental-state flags make the next command on the same server much slower. They are for CI jobs that run one Bazel command and exit, not for laptops or long-lived runners that build many times.

### Local execution: sandboxes, workers, resources

#### Spawn strategies

Bazel decides per action how to execute it. The strategy list is tried in order; the first one that can run the action does.

| Strategy | What it does | Cost |
|---|---|---|
| `remote` | Execute on the remote executor | Network; needs RBE |
| `worker` | Send the request to a persistent worker process | Low per-action overhead; the rule must support workers |
| `linux-sandbox` | Run in a mount and PID namespace with only declared inputs visible | Symlink-forest setup per action |
| `darwin-sandbox` | macOS sandbox-exec equivalent | Notably slower than Linux |
| `processwrapper-sandbox` | Symlink forest in a temp dir, no namespaces | Portable fallback |
| `local` / `standalone` | Run directly in the execroot | Fastest, no isolation: undeclared inputs go unnoticed |
| `dynamic` | Race a local and a remote execution, take the first | More total work; for RBE setups with idle local cores |

```bash
# default order, set explicitly
build --spawn_strategy=remote,worker,linux-sandbox,local

# per mnemonic: Go compiles via workers, everything else as default
build --strategy=GoCompilePkg=worker

# dynamic execution: local workers race remote execution
build:rbe --spawn_strategy=dynamic
build:rbe --dynamic_local_strategy=worker,sandboxed
build:rbe --dynamic_remote_strategy=remote
```

#### Making the sandbox cheaper

Sandbox overhead is per action, so it dominates builds with many tiny actions (C++ with many headers, TypeScript with many files).

```bash
# put sandbox directories on tmpfs (Linux); fast, but uses RAM
build:linux --sandbox_base=/dev/shm

# give each action a private empty /tmp
build:linux --sandbox_tmpfs_path=/tmp
```

> **Version-sensitive.** Bazel can reuse sandbox directories between actions instead of rebuilding the symlink forest each time. The flag started as `--experimental_reuse_sandbox_directories` and was later renamed and enabled by default. Run `bazel help build | grep reuse_sandbox` to see the name and default on your release before setting it.

Check the cost before you change anything: in the profile, compare the width of `sandbox.createFileSystem` and `sandbox.delete` events to the actions themselves. If setup takes as long as the compile, the sandbox is your bottleneck.

#### Persistent workers

A worker is a long-lived process (a compiler server) that Bazel sends requests to, skipping JVM or interpreter start-up for each action. Javac, Kotlin, Scala, TypeScript and some Go and Rust rules support them.

```bash
build --strategy=Javac=worker
build --worker_max_instances=4                # per mnemonic
build --worker_sandboxing                     # sandbox each request (safer, slower)
build --worker_multiplex                      # one process handles many requests at once, if supported
```

> **Gotcha.** An unsandboxed worker can see files from earlier requests, so it can hide undeclared inputs exactly as `local` does. Turn on `--worker_sandboxing` in CI at least, so missing inputs fail there rather than on someone else's machine.

#### Resources and parallelism

```bash
# how much of this machine Bazel may schedule against
build --local_resources=cpu=HOST_CPUS*.75
build --local_resources=memory=HOST_RAM*.6

# how many actions in flight; defaults to auto (about the core count)
build --jobs=auto

# with remote execution, jobs counts parallel remote actions, not local cores
build:rbe --jobs=200

# tests have their own limit
test --local_test_jobs=8
```

> **Version-sensitive.** `--local_resources=cpu=…` and `--local_resources=memory=…` replaced `--local_cpu_resources` and `--local_ram_resources` in Bazel 7. Old blog posts and `.bazelrc` files still use the old names.

### Large-repo habits

| Habit | Why it is fast |
|---|---|
| Small packages, one library per directory | Changes invalidate fewer actions; more parallelism |
| Generated `srcs` lists instead of broad `glob()` | Globs are re-evaluated whenever the package changes and are slow over large trees |
| `.bazelignore` for `node_modules`, vendored trees, build outputs | Bazel never scans or loads them |
| Tight visibility | Prevents accidental deep dependency chains that lengthen the critical path |
| Header and interface hygiene (C++, Java) | Fewer inputs per compile; less invalidation |
| Prebuilt toolchains (hermetic downloads) | No building the compiler from source in every clean build |
| Keep macros cheap | Every package evaluation runs them; a macro that globs or loops over many files costs every build |
| Avoid `--experimental_*` flags you read about once | They change or disappear between releases and can cost more than they save; measure each one |

```bash
# how many targets //... really contains, by kind
bazel query 'kind(".*", //...)' --output=label_kind | awk '{print $1}' | sort | uniq -c | sort -rn | head -20

# packages with the most targets: candidates for splitting
bazel query '//...' --output=label | sed 's/:.*//' | sort | uniq -c | sort -rn | head -20
```

### Benchmarking a change properly

A single before-and-after timing is noise. Measure cold and warm separately, several times, with [hyperfine](https://github.com/sharkdp/hyperfine).

| Scenario | What it measures | How to set it up |
|---|---|---|
| Cold server, cold cache | First build on a fresh runner | `bazel shutdown`, disable disk and remote cache, clean |
| Cold server, warm cache | Fresh CI runner with a shared cache | `bazel shutdown` and `bazel clean`, caches on |
| Warm server, no change | The no-op build a developer runs constantly | Run twice; time the second |
| Warm server, one-file change | The edit-build loop | Touch or edit one file before each run |

```bash
# no-op build on a warm server
hyperfine --warmup 1 'bazel build //services/api'

# cold server, warm cache (CI-like)
hyperfine --runs 5 \
  --prepare 'bazel clean && bazel shutdown' \
  'bazel build //services/api --config=cache'

# fully cold: no caches at all
hyperfine --runs 3 \
  --prepare 'bazel clean --expunge' \
  'bazel build //services/api --disk_cache= --noremote_accept_cached'

# the edit loop: append a comment to a Go file before each run
hyperfine --runs 10 \
  --prepare 'echo "// $(date +%s%N)" >> lib/auth/token.go' \
  --cleanup 'git checkout lib/auth/token.go' \
  'bazel build //services/api'

# compare two branches
hyperfine --runs 5 --prepare 'bazel clean' \
  -n before 'git checkout -q before && bazel build //...' \
  -n after  'git checkout -q after  && bazel build //...'
```

> **Field note.** Record the process summary line (`N processes: X remote cache hit...`) beside each timing. A "speedup" that came from a warmer cache, not from your change, shows up immediately as a different hit count.

### Slow build decision table

| You see | Most likely | Check | Do |
|---|---|---|---|
| No-op build takes > 10 s | Analysis cache discarded or server restarting | Look for "discarding analysis cache" and "Starting local Bazel server" | Align flags and startup options; `--watchfs` |
| No-op build fast, one-file change slow | Long critical path from that file | `analyze-profile` critical path | Split the library or binary on the path |
| CI clean builds slow, cache configured | Low hit rate | Process summary; execution log diff (chapter 10) | Fix non-hermetic keys |
| Many small actions, CPUs half idle | Sandbox setup cost | `sandbox.*` events in the profile | `--sandbox_base=/dev/shm`, sandbox reuse, workers |
| Long gaps labelled cache check or download | Network to the cache | Profile lanes; ping the cache host | Move the cache closer, `--remote_cache_compression`, keep BwoB on |
| GC events, server OOM | Heap too small | `bazel info used-heap-size-after-gc` | Raise `-Xmx`; `--discard_analysis_cache` on CI |
| Tests dominate the time | Big or serial tests | Test lanes in the profile; `--test_summary=detailed` | Shard, split, move integration tests to their own job |
| Fetching external repos every CI run | No repository cache | `bazel info repository_cache`; timing of fetch events | Persistent `--repository_cache`, `bazel vendor`, or a warm CI image |
| Laptop fast, CI slow on the same commit | Different flags or resources | `--announce_rc` output in both | Same `.bazelrc`; size runners; persistent output base on long-lived runners |


## 12 · CI on GitLab

*Thin jobs, the same flags as laptops, a cache only trusted branches can write, affected targets on merge requests, and results in the MR widget.*

### What CI is for, in a Bazel repo

CI has three jobs in a Bazel repo, and each one drives a design decision:

1. **Fill the cache.** Main-branch builds write the results everyone else reuses. CI on main should build and test `//...` so the cache always holds the current tree.
2. **Enforce flag and dependency discipline.** CI is the only place every change runs with exactly the same flags, the same Bazel version and a lockfile that must match.
3. **Gate merges cheaply.** Merge-request pipelines should build and test only what the change can affect, and fail loudly when it breaks something.

Everything below serves one of those three.

### Runner shapes

| Shape | What survives between jobs | Speed comes from | Watch out for |
|---|---|---|---|
| Ephemeral (Kubernetes executor, autoscaled VMs) | Nothing | The remote cache, almost entirely | Server start and repository fetch on every job; keep the CI image warm |
| Long-lived with a persistent volume | Output user root: server state, repository cache, disk cache | The local output base plus the remote cache | Concurrent jobs on one volume need separate output bases |
| Long-lived shell runner | Everything on the host | Warm server between jobs | Hermeticity drift: host packages leak into builds without a strict action env |

#### Persistent state on long-lived runners

```bash
# /etc/bazel.bazelrc baked into the runner image (applies to every workspace)
startup --output_user_root=/cache/bazel-root
common  --repository_cache=/cache/bazel-repo
build   --disk_cache=/cache/bazel-disk
```

`--output_user_root` holds one output base per workspace path. GitLab's builds directory includes the runner and concurrency index (`/builds/<runner>/<n>/group/project`), so concurrent jobs naturally get separate output bases. If you override `GIT_CLONE_PATH`, keep a per-job component in it, or two jobs will block on the same server lock.

> **Gotcha.** Do not use GitLab's `cache:` keyword for Bazel state. Zipping an output base or disk cache, uploading it and restoring it takes longer than the build saves, the archive grows without bound, and parallel jobs race on the same key. Use a remote cache; on long-lived runners, add a persistent volume.

#### The CI image

Bake into one pinned image: Bazelisk (or the exact Bazel binary), `git`, `jq`, `target-determinator`, `crane` and `cosign` for release jobs, plus the system rc file above. Pin it by digest in `.gitlab-ci.yml` so a runner image change is a reviewed diff like any other.

```bash
# pre-download the Bazel version into the image so jobs never fetch it
USE_BAZEL_VERSION="$(cat .bazelversion)" bazel version
```

### A complete `.gitlab-ci.yml`

This is the same shape as the A→Z page, filled out with a release job and the variables that make it work.

```yaml
workflow:
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
    - if: $CI_COMMIT_TAG

variables:
  BAZELISK_BASE_URL: https://artifacts.internal/bazel   # drop if runners reach GitHub
  GIT_DEPTH: 0                                          # target-determinator needs the merge base

  image: harbor.internal/build/bazel-ci@sha256:REPLACE
  tags: [bazel]
  interruptible: true

  before_script:

  after_script:
    - mkdir -p reports

      junit: reports/**/test.xml

  extends: .bazel
  stage: lint
  script:
    - bazel run //:gazelle -- -mode=diff
    - bazel mod tidy && git diff --exit-code MODULE.bazel
    - bazel mod deps --lockfile_mode=error
    - bazel run @buildifier_prebuilt//:buildifier -- -mode=check -lint=warn -r .

test:mr:
  extends: .bazel
  stage: test
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
  script:
    - target-determinator "${CI_MERGE_REQUEST_DIFF_BASE_SHA}" > targets.txt
    - wc -l targets.txt
    - |
      if [ -s targets.txt ]; then
        bazel test --config=ci --build_event_json_file=bep.json --target_pattern_file=targets.txt
      else
        echo "no affected targets"
      fi

test:main:
  extends: .bazel
  stage: test
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
  interruptible: false        # let main finish so the cache stays complete
  script:
    - bazel test --config=ci --build_event_json_file=bep.json //...

release:
  extends: .bazel
  stage: release
  rules:

  interruptible: false
```

### Affected targets on merge requests

Running `//...` on every merge request is correct but wastes runner time on a large repo, even with good cache hits (each cache check still costs a round trip, and analysis of `//...` isn't free). Target determination computes what a change can affect.

#### target-determinator

[target-determinator](https://github.com/bazel-contrib/target-determinator) checks out the base commit, computes a hash for every configured target, does the same for the current commit, and prints the targets whose hash changed. Because it hashes the configured graph, it correctly catches changes to `.bazelrc`, `MODULE.bazel`, the lockfile, toolchains and macros, not just source files.

```bash
# print affected targets between the MR's base and HEAD
target-determinator "${CI_MERGE_REQUEST_DIFF_BASE_SHA}" > targets.txt

# feed them to Bazel; target_pattern_file avoids command-line length limits
bazel test --config=ci --target_pattern_file=targets.txt
```

Its repo also ships a `driver` binary that runs the build and tests for you. Check both tools' `--help` for flags such as which target pattern to consider and which Bazel binary to use.

> **Gotcha.** If `targets.txt` contains only non-test targets, `bazel test` still builds them and exits `4` ("no tests found") unless you handle it. Either accept `4` explicitly, or run `bazel build` and `bazel test` separately on the same list.

#### bazel-diff

[bazel-diff](https://github.com/Tinder/bazel-diff) does the same job in two steps: generate a hash file per commit, then compare. It is useful when you want to cache the base commit's hashes (for example, store them as an artifact of the main-branch pipeline) instead of recomputing them in every merge request.

```bash
# on the base commit (or fetch a stored hashes file)
bazel-diff generate-hashes -w "$PWD" -b "$(command -v bazel)" base.json
# on the MR head
bazel-diff generate-hashes -w "$PWD" -b "$(command -v bazel)" head.json
bazel-diff get-impacted-targets -sh base.json -fh head.json -o targets.txt
```

Flag spellings have changed between bazel-diff releases; check `bazel-diff --help` for the version in your image.

| | target-determinator | bazel-diff |
|---|---|---|
| Hashes | Configured targets | Targets, with optional file-level detail |
| Base commit | Checks it out and analyses it each run | Can reuse a stored hash file |
| Catches `.bazelrc` / toolchain changes | Yes | Mostly; verify for your setup |
| Simplest integration | One command | Three commands |

### Sharding CI across jobs

When the affected set is still large, split it across parallel jobs. GitLab's `parallel:` sets `CI_NODE_INDEX` (1-based) and `CI_NODE_TOTAL`.

```yaml
test:mr:
  extends: .bazel
  stage: test
  parallel: 4
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
  script:
    - target-determinator "${CI_MERGE_REQUEST_DIFF_BASE_SHA}" | sort > targets.txt
    - split -n "r/${CI_NODE_INDEX}/${CI_NODE_TOTAL}" targets.txt > shard.txt
    - test -s shard.txt || { echo "empty shard"; exit 0; }
    - bazel test --config=ci --target_pattern_file=shard.txt
```

Round-robin splitting (`r/K/N`) spreads large and small targets evenly enough in practice. If one package dominates, split by package prefix instead and give it its own job.

> **Note.** Every shard runs the same target determination. With target-determinator that means four analyses of the base commit. If that cost matters, compute `targets.txt` once in an earlier job and pass it as an artifact.

### Merge trains

GitLab merge trains run a pipeline on the merged result of each MR stacked on the ones ahead of it. The pipeline has `CI_PIPELINE_SOURCE == "merge_request_event"` and `CI_MERGE_REQUEST_EVENT_TYPE == "merge_train"`.

```yaml
test:train:
  extends: .bazel
  stage: test
  rules:
    - if: $CI_MERGE_REQUEST_EVENT_TYPE == "merge_train"
  script:
    - target-determinator "${CI_MERGE_REQUEST_TARGET_BRANCH_SHA}" > targets.txt
    - |
      if [ -s targets.txt ]; then
        bazel test --config=ci --target_pattern_file=targets.txt
      fi
```

Compare against the target branch's current tip, not the MR's original base, since the train has moved the base forward. Exclude the plain `test:mr` job from train pipelines so each train car runs once.

Train pipelines run approved code. Whether they may write to the cache is a trust decision: approved but not yet merged. Many teams allow it, because train results are exactly what main will contain moments later; keep it read-only if your threat model treats approval as insufficient.

### Exit codes

Never swallow Bazel's exit code. It distinguishes failures that need different responses.

| Code | Meaning | CI response |
|---|---|---|
| `0` | Success | Pass |
| `1` | Build failed | Fail; the error is a code problem |
| `2` | Command-line or option problem | Fail; usually a broken `.bazelrc` or a bad pattern |
| `3` | Build succeeded, some tests failed or timed out | Fail; read the JUnit report |
| `4` | Build succeeded, no tests found | Usually pass for affected-target runs with no tests |
| `8` | Interrupted | Retry or treat as cancelled |
| `9` | Server lock held and `--noblock_for_lock` was set | Infrastructure; another command on the same output base |
| `36` | Local environmental problem (disk, permissions) | Infrastructure; check the runner |
| `37` | Bazel internal error | Infrastructure; capture logs, report upstream |
| `38` | Transient error publishing build events (BES) | Retry |
| `39` | Remote cache evicted blobs Bazel needed | Retry; size the cache up |
| `45` | Persistent error publishing build events | Infrastructure; check the BES backend |

The full list is in Bazel's documentation on [exit codes](https://bazel.build/run/scripts#exit-codes).

```yaml
# retry only infrastructure-shaped failures, never test failures
test:main:
  retry:
    max: 2
    exit_codes: [8, 36, 37, 38, 39]
```

### Keeping CI and laptops on the same flags

A hit rate that is high on CI and poor on laptops (or the reverse) nearly always means the two run different flags.

- All output-affecting flags live in `.bazelrc`. `--config=ci` only **adds** behaviour that doesn't change outputs: `--keep_going`, `--lockfile_mode=error`, uploads, colour and progress settings, memory trimming.
- `common --announce_rc` in `.bazelrc`, so every job log shows exactly which rc lines applied. Diff that section between a CI log and your terminal.
- Same `.bazelversion`, same `MODULE.bazel.lock`, same hermetic toolchains. The CI image adds tools around Bazel, not inside the build.
- `--incompatible_strict_action_env` everywhere, so runner `PATH` differences don't enter action keys.
- Don't set `--action_env` or `--host_action_env` in `--config=ci` only.

```bash
# the first thing to compare when hit rates differ
bazel build //app --config=ci --announce_rc --nobuild 2>&1 | grep 'INFO: Reading rc options' -A50 | head -60
```

### Renovate for `MODULE.bazel`

Renovate has managers for both files that pin Bazel inputs: `bazel-module` for `bazel_dep(...)` lines in `MODULE.bazel`, and `bazelisk` for `.bazelversion`.

```json
{
  "extends": ["config:recommended"],
  "packageRules": [
    {
      "matchManagers": ["bazel-module"],
      "groupName": "bazel modules",
      "schedule": ["before 6am on monday"]
    },
    {
      "matchManagers": ["bazelisk"],
      "matchUpdateTypes": ["major"],
      "dependencyDashboardApproval": true
    }
  ]
}
```

> **Gotcha.** A bumped `bazel_dep` changes the resolution, so `MODULE.bazel.lock` must change too, and CI runs with `--lockfile_mode=error`. If your Renovate setup doesn't update the lockfile, every Renovate MR fails until someone runs `bazel mod deps --lockfile_mode=update` and pushes. Self-hosted Renovate can do this with `postUpgradeTasks` (the command must be in `allowedPostUpgradeCommands`); otherwise add a small CI job that updates and commits the lockfile on Renovate branches.

> **One-way door.** A Bazel major upgrade (`.bazelversion` 9 → 10) flips incompatible flags and can remove features. Treat it as a planned migration: run the new version in a separate CI job with `USE_BAZEL_VERSION` first, fix what breaks, then change the file. Moving back is possible, but anything you migrated forward for the new version may not work on the old one.

### BEP and profiles as artifacts

Keep the evidence for every slow or flaky job without rerunning it.

```yaml
artifacts:
  when: always
  expire_in: 14 days
  paths:
    - bep.json
    - profile.gz
```

```bash
bazel test --config=ci //... \
  --build_event_json_file=bep.json \
  --profile=profile.gz
```

With a BES backend (chapter 10), send events there as well and print the invocation URL in the job log; `--bes_results_url` makes Bazel print it automatically.

### Reproducing a CI failure locally

Because CI and laptops share flags and the cache, most CI failures reproduce with one command. Work through these in order.

```bash
# 1. same commit, same config, same targets
git fetch origin "$CI_COMMIT_SHA" && git checkout "$CI_COMMIT_SHA"
bazel test --config=ci //lib/auth:auth_test

# 2. still passes locally? rerun uncached to rule out a stale local result
bazel test --config=ci //lib/auth:auth_test --nocache_test_results

# 3. still passes? run it many times; CI runners are slower and busier than laptops
bazel test --config=ci //lib/auth:auth_test --runs_per_test=50 --jobs=4

# 4. still passes? run the CI image itself, with the repo mounted
docker run --rm -it -v "$PWD":/src -w /src harbor.internal/build/bazel-ci@sha256:REPLACE   bazel test --config=ci //lib/auth:auth_test
```

| Passes at step | Likely cause |
|---|---|
| 1 fails, as in CI | A real failure. Fix the code |
| 2 fails | Your local cached result was stale relative to an undeclared input. Find and declare it |
| 3 fails sometimes | A flake that load exposes (chapter 09) |
| 4 fails | Something on your laptop leaks into the build: a host tool, an env var, a file outside the repo. The CI image is the correct baseline |
| None fail | Compare `--announce_rc` output and the BEP options of the CI job against your run |

> **Field note.** The test log of a failed CI job is already in the job's artifacts (via the JUnit report) and in `bep.json`. Read it before reproducing anything; the failure message often names the missing file or the timed-out step directly.

### The "CI is slow" checklist

- [ ] Main-branch pipelines run `//...` and **write** to the remote cache, every commit.
- [ ] A no-change rerun of main shows nearly all processes as `remote cache hit`.
- [ ] Merge requests run only affected targets (target-determinator or bazel-diff).
- [ ] `GIT_DEPTH: 0` (or an explicit fetch of the base) on jobs that need the merge base.
- [ ] No GitLab `cache:` for Bazel directories.
- [ ] Bazel binary and repository cache are baked into the image or on a persistent volume, not downloaded per job.
- [ ] `--config=ci` adds flags without changing outputs; `--announce_rc` matches laptops.
- [ ] Remote cache is close to the runners and sized so blobs live for days.
- [ ] Integration and end-to-end suites run in their own jobs, not in the default `//...` gate.
- [ ] Runners have enough memory for the graph (`bazel info used-heap-size-after-gc` plus headroom), and `--discard_analysis_cache` is set on one-shot jobs.
- [ ] `bep.json` and a profile are kept for every job, so the next slow run can be diagnosed from artifacts.
- [ ] Exit codes are honoured; only infrastructure codes are retried.


## 13 · Images, releases and the air gap

*rules_oci from base digest to signed multi-arch index, stamping for releases only, SBOMs and scans, and building with no network at all.*

### The delivery chain at a glance

Everything a release ships is a Bazel target, so everything a release ships is cached, pinned and reproducible to the same degree as the code. The chain below is the one this chapter builds, end to end.

| Stage | Rule | Output | Pinned by |
|---|---|---|---|
| Base image | `oci.pull` (module extension) | `@distroless_static` and per-platform repos | digest in `MODULE.bazel` and `MODULE.bazel.lock` |
| Binary | `go_binary`, `py_binary`, `js_binary`, `cc_binary` | executable plus runfiles | source + toolchain hashes |
| Layer | `pkg_tar` or aspect_bazel_lib `tar` | `.tar` per layer | layer contents (mtime normalised) |
| Image | `oci_image` | OCI layout directory | base digest + layer digests + config |
| Multi-arch | `platform_transition_filegroup` + `oci_image_index` | OCI layout with an index | per-platform image digests |
| Local test | `oci_load` | `bazel run` loads into docker/podman | n/a |
| Publish | `oci_push` | pushes index and tags | tags from a stamped file |
| Evidence | `syft`, `grype`/`trivy`, `cosign` | SBOM, scan report, signature | image digest |
| Non-image artefacts | `pkg_tar`, `pkg_deb`, `pkg_rpm`, `pkg_zip` | archives and packages | contents |

The modules used throughout: `rules_oci` 2.3.0, `rules_pkg` 1.3.0, `aspect_bazel_lib` 2.22.5, `platforms` 1.1.0, plus `aspect_rules_py` 1.12.1 and `aspect_rules_js` 3.5.1 for the language-specific layer helpers.

### Base images with oci.pull

#### Pin by digest, always

```starlark
# MODULE.bazel
bazel_dep(name = "rules_oci", version = "2.3.0")

oci = use_extension("@rules_oci//oci:extensions.bzl", "oci")

oci.pull(
    name = "distroless_static",
    image = "gcr.io/distroless/static-debian12",
    digest = "sha256:REPLACE_WITH_INDEX_DIGEST",
    platforms = ["linux/amd64", "linux/arm64"],
)

oci.pull(
    name = "python_slim",
    image = "docker.io/library/python",
    digest = "sha256:REPLACE_WITH_INDEX_DIGEST",
    platforms = ["linux/amd64", "linux/arm64"],
)

use_repo(
    oci,
    "distroless_static",
    "distroless_static_linux_amd64",
    "distroless_static_linux_arm64",
    "python_slim",
    "python_slim_linux_amd64",
    "python_slim_linux_arm64",
)
```

- `digest` is the digest of the **index** when you list `platforms`. Get it with `crane digest gcr.io/distroless/static-debian12:nonroot` or `skopeo inspect --raw docker://IMAGE:TAG | sha256sum`.
- With `platforms`, the extension creates one repo per platform (`NAME_linux_amd64`) plus `NAME`, which selects the right one for the target platform. `bazel mod tidy` maintains the `use_repo` list for you.
- `tag = "nonroot"` instead of `digest` works, but the tag is resolved once and recorded in the lockfile with a warning. Treat that as a scaffolding step: copy the digest in and drop the tag.

> **Gotcha.** A digest from `docker images --digests` on your laptop is often the digest of the single-platform manifest your machine pulled, not the index. Pinning it with `platforms = [...]` fails, or worse, pins only one architecture. Always ask the registry (`crane digest`) for the index digest.

#### Updating base images

Renovate's `bazel-module` manager bumps `bazel_dep` versions, but digests inside `oci.pull` are not a standard Renovate pattern. Two workable options:

| Option | How | Trade-off |
|---|---|---|
| Renovate regex manager | `customManagers` entry matching `image = "..."` followed by `digest = "sha256:..."` | Automatic MRs; regex must track your formatting |
| Scheduled CI job | `crane digest IMAGE:TAG`, rewrite with `buildozer` or `sed`, open an MR with `glab mr create` | Explicit, easy to audit |

#### Private registries and auth

rules_oci reads credentials the same way the Docker CLI does: `~/.docker/config.json` (or `$DOCKER_CONFIG/config.json`), including `credHelpers` and `credsStore`. On a CI runner, write a minimal config before the build:

```bash
mkdir -p ~/.docker
cat > ~/.docker/config.json <<EOF
{"auths":{"harbor.internal":{"auth":"$(printf '%s:%s' "$HARBOR_USER" "$HARBOR_TOKEN" | base64 -w0)"}}}
EOF
```

> **Field note.** `oci.pull` runs at fetch time, outside the action sandbox, so credentials never enter action keys. Changing a token does not invalidate anything. Changing the digest does, which is exactly what you want.

#### Debian packages without apt-get in a Dockerfile

When a distroless base lacks a package (CA bundle variants, `tzdata`, a shared library), `rules_distroless` (0.9.4 on the BCR) resolves Debian packages from a lockfile and turns them into layers. It replaces the `RUN apt-get install` step that rules_oci deliberately cannot run. Use it sparingly: every package is a layer you now own the CVEs for.

### Layers

#### pkg_tar

```starlark
load("@rules_pkg//pkg:tar.bzl", "pkg_tar")

pkg_tar(
    name = "app_layer",
    srcs = [":api"],
    package_dir = "/app",
    mode = "0755",
    owner = "65532.65532",
)

pkg_tar(
    name = "config_layer",
    srcs = ["config/default.yaml"],
    package_dir = "/etc/api",
    mode = "0644",
)
```

`pkg_tar` normalises file modification times by default (`portable_mtime = True`), so the same inputs produce the same tar bytes and the same layer digest on any machine. Leave that default alone.

#### aspect_bazel_lib tar with an mtree

```starlark
load("@aspect_bazel_lib//lib:tar.bzl", "mtree_spec", "tar")

mtree_spec(name = "app_mtree", srcs = [":api"])

tar(
    name = "app_layer_bsdtar",
    srcs = [":api"],
    mtree = ":app_mtree",
)
```

The `tar` rule drives a hermetic bsdtar from an mtree specification, which gives exact control over paths, modes and ownership, and handles runfiles trees well. Prefer it for layers built from a binary plus its runfiles (Python, JavaScript); `pkg_tar` is simpler for a static binary and a few files.

#### Order layers by how often they change

Registries and runtimes deduplicate by layer digest. Put what changes least at the bottom:

| Layer | Changes when | Typical size |
|---|---|---|
| Base image | base digest bump | 2–50 MB |
| Interpreter / runtime | runtime version bump | 30–60 MB |
| Third-party packages | lockfile changes | 10–500 MB |
| First-party code | every commit | under 1 MB to a few MB |
| Config | config change | kilobytes |

A one-line code change then pushes a few hundred kilobytes, not the whole dependency tree.

### oci_image

```starlark
load("@rules_oci//oci:defs.bzl", "oci_image")

oci_image(
    name = "image",
    base = "@distroless_static",
    tars = [":app_layer", ":config_layer"],
    entrypoint = ["/app/api"],
    cmd = ["--config=/etc/api/default.yaml"],
    env = {"GOMEMLIMIT": "512MiB"},
    user = "65532:65532",
    workdir = "/app",
    exposed_ports = ["8080/tcp"],
    labels = {
        "org.opencontainers.image.source": "https://gitlab.internal/acme/mono",
        "org.opencontainers.image.title": "api",
    },
)
```

| Attribute | Meaning | Note |
|---|---|---|
| `base` | Base image (an `oci.pull` repo or another `oci_image`) | Omit only for `FROM scratch` images; then set `os` and `architecture` |
| `tars` | Layers, bottom to top | Order matters for cache reuse |
| `entrypoint`, `cmd` | Same meaning as in a Dockerfile | Exec form only; there is no shell |
| `env` | Dict, or a label to a file of `KEY=VALUE` lines | Values support `$VAR` expansion against the base env |
| `user`, `workdir` | Runtime user and directory | Use a numeric UID so `runAsNonRoot` can verify it |
| `exposed_ports` | Documentation in the config | Kubernetes ignores it |
| `labels`, `annotations` | Dict, or a label to a file | A file lets you stamp values at release time |
| `created` | Label to a file holding a timestamp | Leave unset for reproducible images |

> **Gotcha.** There is no `RUN`. Anything you would have done in a `RUN` step (create a user, `chmod`, install a package) has to happen in a layer you build with Bazel or come from the base image. That constraint is the reason the image is reproducible; it is not a missing feature.

### Multi-architecture images

```starlark
load("@aspect_bazel_lib//lib:transitions.bzl", "platform_transition_filegroup")
load("@rules_oci//oci:defs.bzl", "oci_image_index")

platform_transition_filegroup(
    name = "image_amd64",
    srcs = [":image"],
    target_platform = "//platforms:linux_amd64",
)

platform_transition_filegroup(
    name = "image_arm64",
    srcs = [":image"],
    target_platform = "//platforms:linux_arm64",
)

oci_image_index(
    name = "index",
    images = [":image_amd64", ":image_arm64"],
)
```

The transition rebuilds the whole subgraph (binary, layers, base selection) for each platform. With a hermetic toolchain (rules_go, toolchains_llvm, rules_python's downloaded interpreters) this works from any host, and the arm64 build gets cache hits from whichever machine built it first.

```bash
bazel build //services/api:index
cat "$(bazel cquery //services/api:index --output=files)/index.json" | jq '.manifests[] | {digest, platform}'
```

> **Gotcha.** A Python or C++ image that needs native wheels or shared libraries for arm64 needs those artefacts resolved for arm64 too. rules_python resolves wheels per target platform when the lockfile carries them; a lockfile generated only on x86_64 will quietly lack arm64 wheels. Check with `bazel cquery 'deps(//svc:image_arm64)' | grep -i aarch64`.

### Load, push and tag

#### Load locally

```starlark
load("@rules_oci//oci:defs.bzl", "oci_load")

oci_load(
    name = "load",
    image = ":image",
    repo_tags = ["api:dev"],

```

```bash
bazel run //services/api:load
docker run --rm -p 8080:8080 api:dev
# no docker daemon? build the tarball output group and load it with podman
bazel build //services/api:load --output_groups=+tarball   # check the oci_load docs for your version

```

`oci_load` loads a single-platform image. To try the arm64 variant locally, load `:image_arm64` through its own `oci_load`, or pass `--platforms`.

#### Push with stamped tags

`oci_push` takes `repository` (no tag, no digest), and `remote_tags` as either a list of strings or a label to a file with one tag per line. The file form is how you get release-specific tags from stamping.

```starlark
load("@aspect_bazel_lib//lib:expand_template.bzl", "expand_template")
load("@rules_oci//oci:defs.bzl", "oci_push")

expand_template(
    name = "release_tags",
    out = "_release_tags.txt",
    template = [
        "0.0.0",
        "sha-dev",
    ],
    stamp_substitutions = {
        "0.0.0": "{{STABLE_VERSION}}",
        "sha-dev": "sha-{{STABLE_GIT_COMMIT}}",
    },
)

oci_push(
    name = "push",
    image = ":index",
    repository = "harbor.internal/acme/api",
    remote_tags = ":release_tags",
)
```

```bash
bazel run --config=release //services/api:push          # tags: 1.4.2 and sha-<commit>
bazel run //services/api:push                            # unstamped: tags 0.0.0 and sha-dev
bazel run //services/api:push -- --repository harbor.internal/scratch/api   # override target repo
```

Without `--stamp`, `stamp_substitutions` are not applied and the template's literal values are used. That makes accidental pushes from a laptop obviously wrong (`0.0.0`) instead of plausibly right.

> **Field note.** Use `repository_file` instead of `repository` when the destination itself varies per environment. It takes a label to a file, which can come from another `expand_template`.

#### Python with aspect_rules_py

#### JavaScript with aspect_rules_js

`js_image_layer` from `aspect_rules_js` does the same for a `js_binary`: `node_modules` in one layer, application code in another.


#### Go and C++

A static Go binary (`pure = "on"`) or a fully static C++ binary needs one `pkg_tar` and `distroless/static`. A dynamically linked binary needs `distroless/cc` (glibc and libstdc++) as its base, and its shared libraries must match the base's glibc.

### Digests, signing, SBOMs and scanning

#### The digest is the release

```bash
LAYOUT="$(bazel cquery //services/api:index --output=files)"
DIGEST="$(jq -r '.manifests[0].digest' "$LAYOUT/index.json")"
echo "$DIGEST"
```

Deploy, sign, scan and record **that** digest. A tag is a pointer you will move; the digest is what was tested.

#### SBOM and scan from the layout

```bash
IMG="$(bazel cquery //services/api:image --output=files)"
syft "oci-dir:$IMG" -o spdx-json > sbom.spdx.json
syft "oci-dir:$IMG" -o cyclonedx-json > sbom.cdx.json
grype "oci-dir:$IMG" --fail-on high
trivy image --input "$IMG" --severity HIGH,CRITICAL --ignore-unfixed --exit-code 1
```

Scanning the layout before pushing means a failed gate never leaves an image in the registry. Scan the per-platform `:image` target, not the index, unless your scanner version handles indexes; when in doubt, scan each platform.

#### Sign by digest

```bash
bazel run --config=release //services/api:push
cosign sign --yes --key cosign.key "harbor.internal/acme/api@${DIGEST}"
cosign attest --yes --key cosign.key --type spdxjson \
  --predicate sbom.spdx.json "harbor.internal/acme/api@${DIGEST}"
cosign verify --key cosign.pub "harbor.internal/acme/api@${DIGEST}"
```

> **One-way door.** Choosing keyless (Sigstore OIDC plus Rekor) or key-pair signing shapes every verifier you deploy afterwards. An air-gapped cluster cannot reach a public transparency log, so key-pair signing with a key held in OpenBao (or an HSM) is the practical default for anything that ships to a disconnected site. Switching later means re-signing and redeploying every verifier policy.

rules_oci 1.x had a `cosign_sign` rule; 2.x removed it. Signing is a release-pipeline step after the push, not a build action, which is correct: a signature needs a secret, and secrets do not belong in action keys.

### Reproducibility: what Bazel gives you and what it does not

| Property | Bazel guarantees it? | What you still have to do |
|---|---|---|
| Every input is declared | Yes, enforced by the sandbox | Keep `no-sandbox` and `local` tags rare |
| Same inputs give the same action key | Yes | Keep env and flags out of actions (`--incompatible_strict_action_env`) |
| Same action key gives bit-identical output | **No** | Use tools that are deterministic: `-trimpath` (rules_go does this), fixed mtimes (`pkg_tar` does this), no embedded timestamps |
| Toolchains are the same everywhere | Only if hermetic | Download toolchains through modules; never `/usr/bin/gcc` |
| Image timestamps are fixed | Yes, unless you set `created` | Set `created` only from a stamped file on release builds, if at all |
| Build metadata (commit, version) | Only with `--stamp` | Stamp release builds only, so dev and CI keep cache hits |

Check bit-for-bit reproducibility directly:

```bash
bazel build //services/api:image --disk_cache= --remote_cache= && cp -rL "$(bazel cquery //services/api:image --output=files)" /tmp/a
bazel clean && bazel build //services/api:image --disk_cache= --remote_cache= && cp -rL "$(bazel cquery //services/api:image --output=files)" /tmp/b
diff -r /tmp/a /tmp/b && echo reproducible
```

If the two layouts differ, `diffoscope /tmp/a /tmp/b` names the file and the bytes. Typical culprits: a code generator writing the current date, a zip without fixed timestamps, a compiler embedding absolute paths.

### Stamping, carefully

```bash
#!/usr/bin/env bash
# tools/workspace_status.sh
set -euo pipefail
echo "STABLE_GIT_COMMIT $(git rev-parse HEAD)"
echo "STABLE_VERSION $(git describe --tags --always --dirty | sed 's/^v//')"
echo "BUILD_TIMESTAMP $(date +%s)"
```

| Key prefix | Written to | Invalidates stamped actions when it changes? |
|---|---|---|
| `STABLE_` | `bazel-out/stable-status.txt` | Yes |
| anything else | `bazel-out/volatile-status.txt` | No; picked up only when the action reruns for another reason |
| `BUILD_EMBED_LABEL` | from `--embed_label=VALUE` | Yes (stable) |

```text
# .bazelrc
build:release --stamp
build:release --workspace_status_command=tools/workspace_status.sh
```

> **Gotcha.** `--stamp` on every build makes every stamped binary rebuild on every commit, because `STABLE_GIT_COMMIT` changed. That silently destroys cache hit rates for anything downstream of a stamped binary, images included. Stamp only in the release job.

```starlark
load("@rules_pkg//pkg:deb.bzl", "pkg_deb")
```

### Helm charts next to the images

Two patterns work; pick by how much of the chart lifecycle you want inside Bazel.

| Pattern | How | Fits |
|---|---|---|
| Chart outside Bazel, digests inside | Bazel builds and pushes images; a release job writes the digests into `values.yaml` with `yq` and runs `helm package` / `helm push` | Charts maintained by a platform team in a separate repo |
| Chart as a Bazel target | `rules_helm` (0.34.0 on the BCR) provides chart packaging, linting and push rules with a hermetic Helm toolchain | Monorepos where chart and code version together |

The values file must reference images by digest. A pattern that works with either approach:

```bash
DIGEST="$(jq -r '.manifests[0].digest' "$(bazel cquery //services/api:index --output=files)/index.json")"
yq -i ".image.repository = \"harbor.internal/acme/api\" | .image.digest = \"$DIGEST\"" charts/api/values.yaml
helm package charts/api --version "$VERSION" --app-version "$VERSION"
helm push "api-$VERSION.tgz" oci://harbor.internal/acme/charts
```

> **Note.** rules_helm's rule names and attributes are documented at `periareon.github.io/rules_helm`. Read the reference for your pinned version; this chapter does not reproduce it.

### Offline and air-gapped builds

#### What a build downloads

| Download | When | Offline answer |
|---|---|---|
| Bazel binary | first `bazel` call (Bazelisk) | `BAZELISK_BASE_URL` mirror, or binary baked into the builder image |
| Registry metadata (`MODULE.bazel`, `source.json` per module version) | module resolution | mirror of the BCR, `--registry` |
| Module source archives | fetch | `bazel vendor`, repository cache, or URL rewriting |
| Toolchains (Go SDK, Python, LLVM, Node) | fetch, when first needed | same as above; they are just archives |
| Language packages (Go modules, wheels, npm tarballs) | fetch, via extensions | same, plus language-specific mirrors |
| Base images | fetch (`oci.pull`) | internal registry mirror |
| Anything an action downloads | execution | must not exist; the sandbox blocks network by default |

#### The Bazel binary

Bazelisk builds the URL as `$BAZELISK_BASE_URL/<version>/<file>`, matching the GitHub release layout. Set it in the environment or commit a `.bazeliskrc`:

```text
# .bazeliskrc
BAZELISK_BASE_URL=https://artifacts.internal/bazel-releases
```

```bash
# populate the mirror on the connected side
V=9.3.0
for f in bazel-$V-linux-x86_64 bazel-$V-linux-arm64 bazel-$V-darwin-arm64; do
  curl -fsSLO "https://github.com/bazelbuild/bazel/releases/download/$V/$f"
  curl -fsSLO "https://github.com/bazelbuild/bazel/releases/download/$V/$f.sha256"
done
```

#### A registry mirror

The BCR is a Git repository of JSON metadata, `MODULE.bazel` files and patches. A mirror is a clone served over HTTPS or read from disk:

```bash
git clone --depth 1 https://github.com/bazelbuild/bazel-central-registry /opt/bcr
```

```text
# .bazelrc: first registry that has a module wins, so list internal ones first
common --registry=https://registry.internal/acme-modules
common --registry=file:///opt/bcr
```

The registry tells Bazel *where* to download sources; the archives themselves still point at GitHub. Pair the mirror with vendoring, a pre-filled repository cache or a downloader config that rewrites those URLs. A registry's `bazel_registry.json` can also list `mirrors` that Bazel tries for every module source.

> **Gotcha.** Once you pass any `--registry`, the default BCR is no longer used. Forgetting to list the BCR mirror makes every public module "not found" in a way that looks like a typo in `MODULE.bazel`.

#### bazel vendor

```bash
# on the connected side: vendor every repo the targets need
bazel vendor //... --vendor_dir=vendor_src

# or everything the module graph declares
bazel vendor --vendor_dir=vendor_src

# one repo, after a dependency bump
bazel vendor --vendor_dir=vendor_src --repo=@rules_go
```

```text
# .bazelrc on the disconnected side
common --vendor_dir=vendor_src
```

`vendor_src/VENDOR.bazel` controls what is vendored: `ignore("@@repo+")` leaves a repo out, `pin("@@repo+")` stops Bazel refreshing it on the next `bazel vendor`. Local repositories (`local_path_override`, `local_repository`) are never vendored.

| Choice | Size | Review story | Fits |
|---|---|---|---|
| Commit `vendor_src` to Git | Large (hundreds of MB with toolchains) | Every dependency change is a diff | Small dependency graphs, strict audit |
| Ship `vendor_src` as a tarball per release | Large, but outside Git | Checksum the tarball, record it in the release | Air-gap media handoff |
| Shared repository cache instead | Similar | Content-addressed by SHA-256 | Internal CI with a persistent volume |

#### Repository cache and distdir

```text
common --repository_cache=/srv/bazel-repo-cache
build  --distdir=/srv/bazel-distdir
```

- `--repository_cache` is content-addressed by SHA-256. Bazel uses an entry only when it already knows the expected checksum, which every BCR module and every lockfile-pinned package provides. Copy a populated cache across the gap and builds stop downloading.
- `--distdir` is a flat directory checked by file name before downloading. Useful for a handful of archives you place by hand; the repository cache is the better general mechanism.

#### Downloader config

```text
# tools/bazel_downloader.cfg
# directives apply in the order rewrite, then allow, then block
rewrite github.com/(.*) artifacts.internal/github/$1
rewrite (dl\.google\.com/go/.*) artifacts.internal/golang/$1
rewrite (files\.pythonhosted\.org/.*) artifacts.internal/pypi/$1
rewrite (registry\.npmjs\.org/.*) artifacts.internal/npm/$1
allow artifacts.internal
block *
all_blocked_message Not mirrored: add a rewrite to tools/bazel_downloader.cfg
```

```text
# .bazelrc
common --downloader_config=tools/bazel_downloader.cfg
```

Rules for the file, read from Bazel's own source:

- `rewrite PATTERN REPLACEMENT` matches the URL without its scheme; back references are `$1`, `$2`.
- `allow HOST` and `block HOST` include subdomains; `block *` blocks every host not allowed.
- `all_blocked_message` may appear once and is shown when every URL for a download was blocked.
- Comments must be on their own line, starting with `#`. A trailing comment on a directive line breaks it.

> **Field note.** Running with the rewrite plus `block *` while still connected is the cheapest air-gap rehearsal there is. Every download that would fail on site fails now, with your `all_blocked_message`, naming the URL to mirror.

#### Language package mirrors

| Ecosystem | Lockfile | Mirror route |
|---|---|---|
| Go | `go.sum` | URL rewrite of the module proxy, or a vendored `go_deps` repo set; check the gazelle `go_deps` docs for proxy settings in your version |
| Python | `requirements_lock.txt` with hashes | rewrite `files.pythonhosted.org`, or point `pip.parse` at an internal index (see rules_python docs for the index attributes) |
| npm | `pnpm-lock.yaml` | rewrite `registry.npmjs.org`, or an `.npmrc` passed to `npm_translate_lock` |
| Containers | digests in `oci.pull` | change the `image` host to the internal registry; the digest stays valid |

Every one of these is pinned by a hash, so a mirror cannot substitute content without the build failing. That is the strongest supply-chain property Bazel gives you; protect it by refusing lockfile changes that drop hashes.

#### Prove the build is offline

Reading configuration proves nothing. Run the build where the network does not exist:

```bash
# connected side: warm everything
bazel fetch //...
bazel vendor //... --vendor_dir=vendor_src

# offline rehearsal: no network at all
podman run --rm --network=none \
  -v "$PWD":/src:Z -w /src \
  -e BAZELISK_SKIP_WRAPPER=1 \
  harbor.internal/build/bazel-ci@sha256:REPLACE \
  bazel build --vendor_dir=vendor_src --config=ci //...
```

If the build passes with `--network=none`, it passes on site. If it fails, the error names the repository or URL that is missing.

> **Gotcha.** A test tagged `requires-network` passes on a connected CI runner and fails at the customer site. Before a disconnected release, run `bazel query 'attr(tags, "requires-network", //...)'` and decide what each one actually needs.

### Release checklist

- [ ] `.bazelversion` and `MODULE.bazel.lock` are committed; CI ran with `--lockfile_mode=error`.
- [ ] Every `oci.pull` uses a `digest`, not only a `tag`.
- [ ] No `pkg_rpm`, `no-sandbox` or `local` target is in the release path without a recorded reason.
- [ ] The release job uses `--config=release` (and only it uses `--stamp`).
- [ ] Images were scanned from the OCI layout and the gate passed before the push.
- [ ] The pushed digest was signed (key pair for disconnected sites) and the SBOM attested.
- [ ] Helm values reference images by digest.
- [ ] The offline rehearsal (`--network=none`, vendored repos) passed for this exact commit.
- [ ] `vendor_src` tarball, image layouts and charts are checksummed in the release record.
- [ ] Release notes list the Bazel version, the base image digests and any module overrides.


## 14 · Writing rules, macros and aspects

*When a macro is enough and when you need a rule, providers and depsets done right, aspects, toolchain-aware rules, testing them, and publishing a module.*

### Macro, rule or aspect

Starlark gives you three extension points. They run in different phases and they are not interchangeable.

| Tool | Runs in | Can see | Produces | Reach for it when |
|---|---|---|---|---|
| Legacy macro (`def`) | loading | its own arguments | more targets | quick wrappers in one repo |
| Symbolic macro (`macro()`, Bazel 8+) | loading | its declared attributes | more targets, namespaced | a reusable "service = binary + image + test" bundle |
| Rule (`rule()`) | analysis | providers of its deps | actions and providers | a new kind of build step with its own inputs and outputs |
| Aspect (`aspect()`) | analysis | providers and attributes of every target it visits | extra actions and providers alongside existing targets | collecting information across a graph you do not own (lint, IDE info, licences) |
| Repository rule / module extension | fetch | the network and filesystem | external repos | bringing third-party code or tools in |

The rule of thumb: if the thing you want can be expressed as "these existing rules, wired together", it is a macro. If it needs a command Bazel does not already run, it is a rule. If it needs to walk someone else's targets, it is an aspect.

> **Gotcha.** A `genrule` is a rule with a shell string for an implementation. It has no providers, no toolchain resolution and runs under `bash` on whatever executes it. One line of `sed` is fine. A `genrule` that grows past a few lines, or that calls a tool you also build, should become a rule.

### Macros

#### Legacy macros

```starlark
# tools/legacy.bzl
load("@rules_go//go:def.bzl", "go_binary", "go_test")

def go_service(name, srcs, deps = [], **kwargs):
    go_binary(name = name, srcs = srcs, deps = deps, **kwargs)
    go_test(name = name + "_test", srcs = native.glob(["*_test.go"]), embed = [":" + name])
```

A legacy macro is a plain function. It can create targets with any name, read `native.package_name()`, call `native.glob()`, and pass `**kwargs` through untouched. That flexibility is the problem: nothing stops it creating `//pkg:foo` that collides with a hand-written target, and `bazel query --output=build` is the only way to see what it did.

#### Symbolic macros

```starlark
# tools/service.bzl
load("@rules_go//go:def.bzl", "go_binary", "go_test")
load("@rules_oci//oci:defs.bzl", "oci_image")
load("@rules_pkg//pkg:tar.bzl", "pkg_tar")

def _service_impl(name, visibility, embed, base, test_srcs):
    go_binary(
        name = name,
        embed = embed,
        pure = "on",
        visibility = visibility,
    )
    pkg_tar(
        name = name + "_layer",
        srcs = [":" + name],
        package_dir = "/app",
    )
    oci_image(
        name = name + "_image",
        base = base,
        tars = [":" + name + "_layer"],
        entrypoint = ["/app/" + name],
        visibility = visibility,
    )
    if test_srcs:
        go_test(
            name = name + "_test",
            srcs = test_srcs,
            embed = embed,
        )

service = macro(
    doc = "A Go binary, its distroless image and its tests.",
    implementation = _service_impl,
    attrs = {
        "embed": attr.label_list(mandatory = True, doc = "go_library targets to embed"),
        "base": attr.label(default = "@distroless_static", configurable = False),
        "test_srcs": attr.label_list(allow_files = [".go"], default = [], configurable = False),
    },
)
```

```starlark
# services/api/BUILD.bazel
load("//tools:service.bzl", "service")

service(
    name = "api",
    embed = [":api_lib"],
    test_srcs = glob(["*_test.go"]),
    visibility = ["//deploy:__subpackages__"],
)
```

What a symbolic macro enforces:

| Rule | Effect |
|---|---|
| Naming | Every target it creates is `name` or starts with `name` followed by `_`, `-` or `.` (`api`, `api_image`, `api-config`). Anything else is an error. |
| Visibility | Targets inside are visible to the macro's own definition package. The caller sees them only through the `visibility` it passes, which the implementation must forward. |
| Typed attributes | Attributes are declared with `attr.*` like a rule's. Unknown arguments are an error, not a silent `**kwargs` pass-through. |
| Configurability | Attributes are `select()`-able by default. Mark ones you branch on in Starlark with `configurable = False`, since a `select` value cannot be inspected at loading time. |
| No `native.glob()` on the caller's behalf | Pass file lists in as attributes, as `test_srcs` above. |

`inherit_attrs` lets a wrapper macro accept all of a rule's attributes without listing them: `inherit_attrs = go_binary` (or the string `"common"` for the attributes every rule has). Inherited attributes arrive as arguments to the implementation; forward them with `**kwargs` and declare `**kwargs` in the signature.

> **Version-sensitive.** Symbolic macros arrived in Bazel 8 and gained features (`inherit_attrs`, finalizers) across 8.x. On Bazel 9.x everything in this section works; on older versions check the macro documentation for your release.

#### Finalizers

A finalizer is a symbolic macro declared with `finalizer = True`. It runs after every other target in the package is defined and can call `native.existing_rules()` to see them. Use it for "generate a `test_suite` of every test in this package" style jobs; do not use it to modify targets, which it cannot do.

### Rule anatomy

#### The shape every rule has

```starlark
# tools/render.bzl
RenderedManifestInfo = provider(
    doc = "A Kubernetes manifest rendered from templates.",
    fields = {
        "manifest": "File: the rendered YAML",
        "images": "depset of image digest files this manifest references",
    },
)

def _render_impl(ctx):
    out = ctx.actions.declare_file(ctx.label.name + ".yaml")

    args = ctx.actions.args()
    args.add("--values", ctx.file.values)
    args.add_all(ctx.files.templates, before_each = "--template")
    args.add("--out", out)

    ctx.actions.run(
        executable = ctx.executable._renderer,
        arguments = [args],
        inputs = depset(ctx.files.templates + [ctx.file.values]),
        outputs = [out],
        mnemonic = "RenderManifest",
        progress_message = "Rendering %{label}",
        env = {"TZ": "UTC"},
    )

    images = depset(
        direct = ctx.files.image_digests,
        transitive = [d[RenderedManifestInfo].images for d in ctx.attr.deps],
    )

    return [
        DefaultInfo(files = depset([out])),
        RenderedManifestInfo(manifest = out, images = images),
    ]

render_manifest = rule(
    implementation = _render_impl,
    doc = "Renders templates with a values file into one manifest.",
    attrs = {
        "templates": attr.label_list(allow_files = [".tpl"], mandatory = True),
        "values": attr.label(allow_single_file = [".yaml"], mandatory = True),
        "image_digests": attr.label_list(allow_files = True),
        "deps": attr.label_list(providers = [RenderedManifestInfo]),
        "_renderer": attr.label(
            default = "//tools/renderer",
            executable = True,
            cfg = "exec",
        ),
    },
    provides = [RenderedManifestInfo],
)
```

#### Attributes

| Type | Use | Common options |
|---|---|---|
| `attr.label` | one dependency | `allow_single_file`, `executable`, `cfg`, `providers`, `default` |
| `attr.label_list` | many dependencies | `allow_files`, `providers`, `allow_empty` |
| `attr.string`, `attr.int`, `attr.bool` | scalars | `values` (allowed list), `default`, `mandatory` |
| `attr.string_list`, `attr.string_dict` | lists, maps | `default` |
| `attr.label_keyed_string_dict` | label → string (e.g. file → install path) | `allow_files` |
| `attr.output`, `attr.output_list` | outputs named by the caller | prefer `declare_file` instead |

- Attributes whose name starts with `_` are private: callers cannot set them. Use them for tools and implicit dependencies.
- `cfg = "exec"` builds the dependency for the execution platform. Every tool an action runs needs it, or cross-compilation builds the tool for the target and then fails to run it.
- `providers = [FooInfo]` makes analysis fail early, with a clear message, when someone passes a target that does not provide `FooInfo`.

#### Actions

| Call | Does | Note |
|---|---|---|
| `ctx.actions.declare_file(name)` | declares an output file in the package's output directory | every declared output must be produced by exactly one action |
| `ctx.actions.declare_directory(name)` | declares a tree artefact | use only when the file list is unknown at analysis time |
| `ctx.actions.run(...)` | runs an executable with `arguments` | the default; no shell |
| `ctx.actions.run_shell(...)` | runs a shell command string | avoid; needs `bash` on every executor |
| `ctx.actions.write(output, content, is_executable)` | writes a file at execution time from a string or `Args` | cheap; good for wrapper scripts |
| `ctx.actions.expand_template(template, output, substitutions)` | template substitution | no tool needed |
| `ctx.actions.symlink(output, target_file)` | symlink action | for executable aliases |
| `ctx.actions.args()` | lazily expanded command line | always use it for file lists |

```starlark
args = ctx.actions.args()
args.add_all(srcs_depset, format_each = "--src=%s")
args.use_param_file("@%s", use_always = False)   # spill to a params file if the line is too long
args.set_param_file_format("multiline")
```

> **Gotcha.** `ctx.actions.run` with `env = {...}` sets only those variables. If your tool needs `PATH`, set `use_default_shell_env = True` (which brings in `--action_env` and, with `--incompatible_strict_action_env`, a fixed `PATH`) or, better, call tools by their declared path from `ctx.executable`.

#### Providers and depsets

A provider is a typed record passed from a target to whatever depends on it. A depset is how you pass a growing collection up a deep graph without copying it at each level.

```starlark
# good: linear in the size of the graph
files = depset(
    direct = ctx.files.srcs,
    transitive = [d[MyInfo].files for d in ctx.attr.deps],
)

# bad: quadratic; flattens at every level of the graph
files = ctx.files.srcs + [f for d in ctx.attr.deps for f in d[MyInfo].files.to_list()]
```

Built-in providers you will return or read:

| Provider | Carries |
|---|---|
| `DefaultInfo` | `files` (what `bazel build` shows), `runfiles`, `executable` |
| `OutputGroupInfo` | named groups of extra outputs (`--output_groups=report`) |
| `RunEnvironmentInfo` | environment variables for `bazel run` and `bazel test` |
| `InstrumentedFilesInfo` | which files coverage should instrument |
| Language providers (`CcInfo`, `PyInfo`, `JavaInfo`, `GoInfo`) | what the language rules need to depend on your outputs |

#### Executable and test rules

```starlark
def _smoke_test_impl(ctx):
    script = ctx.actions.declare_file(ctx.label.name + ".sh")
    ctx.actions.expand_template(
        template = ctx.file._template,
        output = script,
        substitutions = {"%BINARY%": ctx.executable.binary.short_path},
        is_executable = True,
    )
    runfiles = ctx.runfiles(files = [ctx.executable.binary] + ctx.files.data)
    runfiles = runfiles.merge(ctx.attr.binary[DefaultInfo].default_runfiles)
    return [
        DefaultInfo(executable = script, runfiles = runfiles),
        RunEnvironmentInfo(environment = {"SMOKE_TIMEOUT": "30"}),
    ]

smoke_test = rule(
    implementation = _smoke_test_impl,
    test = True,
    attrs = {
        "binary": attr.label(executable = True, cfg = "target", mandatory = True),
        "data": attr.label_list(allow_files = True),
        "_template": attr.label(default = "//tools:smoke_test.sh.tpl", allow_single_file = True),
    },
)
```

- `test = True` requires the rule name to end in `_test` and the implementation to return an executable. `executable = True` is the same for `bazel run` targets.
- Everything the executable reads at runtime must be in `runfiles`. Merge the runfiles of executables you call, or they will find their own data missing.
- `cfg = "target"` for the binary under test: it runs on the test's platform, unlike a build tool.

### Toolchain-aware rules

Use a toolchain when the tool a rule runs depends on the platform (a compiler, a code generator with native binaries, a linter downloaded per OS).

```starlark
# tools/fmt/toolchain.bzl
FmtInfo = provider(fields = {"binary": "File: the formatter"})

def _fmt_toolchain_impl(ctx):
    return [platform_common.ToolchainInfo(fmt = FmtInfo(binary = ctx.executable.binary))]

fmt_toolchain = rule(
    implementation = _fmt_toolchain_impl,
    attrs = {"binary": attr.label(executable = True, cfg = "exec", mandatory = True)},
)
```

```starlark
# tools/fmt/BUILD.bazel
load(":toolchain.bzl", "fmt_toolchain")

toolchain_type(name = "toolchain_type")

fmt_toolchain(name = "fmt_linux_amd64_impl", binary = "@fmt_linux_amd64//:fmt")

toolchain(
    name = "fmt_linux_amd64",
    toolchain = ":fmt_linux_amd64_impl",
    toolchain_type = ":toolchain_type",
    exec_compatible_with = ["@platforms//os:linux", "@platforms//cpu:x86_64"],
)
```

```starlark
# a rule that uses it
def _fmt_check_impl(ctx):
    fmt = ctx.toolchains["//tools/fmt:toolchain_type"].fmt
    out = ctx.actions.declare_file(ctx.label.name + ".ok")
    ctx.actions.run(
        executable = fmt.binary,
        arguments = ["--check", "--stamp-file", out.path] + [f.path for f in ctx.files.srcs],
        inputs = ctx.files.srcs,
        outputs = [out],
        mnemonic = "FmtCheck",
    )
    return [DefaultInfo(files = depset([out]))]

fmt_check = rule(
    implementation = _fmt_check_impl,
    attrs = {"srcs": attr.label_list(allow_files = True)},
    toolchains = ["//tools/fmt:toolchain_type"],
)
```

```starlark
# MODULE.bazel
register_toolchains("//tools/fmt:all")
```

- `exec_compatible_with` says where the tool can run; `target_compatible_with` says what platform its output is for. A formatter only needs the first.
- For a toolchain the rule can work without, declare it optional: `toolchains = [config_common.toolchain_type("//tools/fmt:toolchain_type", mandatory = False)]`, then check `ctx.toolchains[...]` for `None`.
- Debug selection with `--toolchain_resolution_debug='//tools/fmt:toolchain_type'`.

### Aspects

An aspect visits targets along attribute edges and attaches extra actions and providers to them, without the targets knowing. This one collects the licence files of every third-party dependency of a binary.

```starlark
# tools/licences.bzl
LicenceInfo = provider(fields = {"files": "depset of licence files"})

def _licences_aspect_impl(target, ctx):
    direct = []
    if hasattr(ctx.rule.attr, "data"):
        for d in ctx.rule.attr.data:
            for f in d.files.to_list():
                if f.basename.upper().startswith(("LICENSE", "LICENCE", "COPYING")):
                    direct.append(f)

    transitive = [
        dep[LicenceInfo].files
        for attr_name in ("deps", "data", "embed")
        if hasattr(ctx.rule.attr, attr_name)
        for dep in getattr(ctx.rule.attr, attr_name)
        if LicenceInfo in dep
    ]
    files = depset(direct, transitive = transitive)
    return [
        LicenceInfo(files = files),
        OutputGroupInfo(licences = files),
    ]

licences_aspect = aspect(
    implementation = _licences_aspect_impl,
    attr_aspects = ["deps", "data", "embed"],
)
```

```bash
bazel build //services/api \
  --aspects=//tools:licences.bzl%licences_aspect \
  --output_groups=licences
```

- `attr_aspects` names the edges the aspect follows. `["*"]` follows every attribute, which is rarely what you want and often slow.
- The `to_list()` on a single target's `data` files is acceptable; flattening the transitive depset would not be.
- An aspect can also be attached from a rule attribute (`attr.label_list(aspects = [licences_aspect])`), which makes it part of a normal target instead of a command-line flag.

> **Field note.** IDE plugins, rules_lint and most "collect X across the repo" tools are aspects. If you are tempted to write a script that runs `bazel query` and then parses BUILD files, an aspect is almost always the better tool: it sees the configured graph, `select()` already resolved.

### Testing rules and macros

#### Analysis tests with bazel_skylib

```starlark
# tools/render_test.bzl
load("@bazel_skylib//lib:unittest.bzl", "analysistest", "asserts")
load(":render.bzl", "RenderedManifestInfo", "render_manifest")

def _manifest_is_yaml_impl(ctx):
    env = analysistest.begin(ctx)
    target = analysistest.target_under_test(env)
    asserts.true(env, target[RenderedManifestInfo].manifest.basename.endswith(".yaml"))
    actions = analysistest.target_actions(env)
    asserts.equals(env, 1, len([a for a in actions if a.mnemonic == "RenderManifest"]))
    return analysistest.end(env)

manifest_is_yaml_test = analysistest.make(_manifest_is_yaml_impl)

def _fails_without_values_impl(ctx):
    env = analysistest.begin(ctx)
    asserts.expect_failure(env, "values")
    return analysistest.end(env)

fails_without_values_test = analysistest.make(_fails_without_values_impl, expect_failure = True)

def render_test_suite(name):
    render_manifest(name = "fixture", templates = ["testdata/a.tpl"], values = "testdata/v.yaml", tags = ["manual"])
    manifest_is_yaml_test(name = "manifest_is_yaml_test", target_under_test = ":fixture")
    native.test_suite(name = name, tests = [":manifest_is_yaml_test"])
```

- Mark fixtures `manual` so `bazel build //...` does not build them on their own.
- `analysistest.make(..., config_settings = {"//command_line_option:platforms": "//platforms:linux_arm64"})` runs the analysis under a different configuration, which is how you test platform-dependent behaviour.
- `unittest.make` tests pure Starlark functions with no targets involved.

#### rules_testing

`rules_testing` (0.9.0 on the BCR) offers a fluent, truth-style API for analysis tests (`env.expect.that_target(target)...`) with better failure messages than skylib's `asserts`. New rule sets increasingly use it; skylib's `analysistest` remains fine and has no extra dependency.

#### End-to-end

Analysis tests prove the action graph is right. They do not prove the tool works. Add one ordinary test per rule that builds a small fixture and checks the output, for example a `sh_test` (from `rules_shell`) that diffs the rendered manifest against a golden file.

### Starlark performance rules

| Rule | Why |
|---|---|
| Never call `to_list()` on a transitive depset in a rule implementation | Quadratic time and memory across the graph |
| Build command lines with `ctx.actions.args()` | Expansion happens at execution, not analysis, and can spill to a params file |
| Keep providers small | Every provider is retained in memory for the life of the analysis cache |
| Avoid `glob()` in macros on behalf of callers | Globs re-evaluate on every file change in the package |
| Do not compute in loading what you can declare | Loading runs on every BUILD file evaluation; analysis is cached per configuration |
| One action per output is cheaper than one giant action | Smaller actions cache and parallelise better |

Measure before tuning: `bazel build //... --profile=/tmp/p.gz --experimental_profile_include_target_label` and look at the analysis-phase lanes in Perfetto. `bazel dump --skylark_memory=/tmp/mem.pb` writes a memory profile of Starlark allocations you can read with `pprof`.

```starlark
# MODULE.bazel
module(
    name = "rules_acme",
    version = "0.0.0",          # replaced by the release tooling

bazel_dep(name = "bazel_skylib", version = "1.9.2")
```

> **One-way door.** A public `load()` path and a provider's field names are an API. Once other repos depend on them, renaming either is a breaking release for every consumer. Decide the public surface (`defs.bzl`, provider names) before the first release, and keep the rest private.

## 15 · When it breaks

*Find the family first: graph, action, cache or environment. Then symptom to cause to command to fix, for every failure you will actually meet.*

### The method: find the family first

Every Bazel failure belongs to one of four families, and each family has its own tool. Spend the first minute working out which family you are in; the rest goes quickly after that.

| Family | Question | Phase | Tool |
|---|---|---|---|
| **Graph** | Is the dependency graph what I think it is? | loading, analysis | `bazel query`, `bazel cquery`, `bazel mod` |
| **Action** | Does this command have everything it needs, and only that? | execution | `-s`, `--sandbox_debug`, `bazel aquery` |
| **Cache** | Why did this rerun, or why didn't it? | execution | `--explain`, execution log, `aquery` diff |
| **Environment** | Is Bazel itself healthy: server, memory, network, flags? | all | `bazel info`, `--announce_rc`, profile, `dmesg` |

How to tell them apart from the first error line:

| Error starts with or contains | Family |
|---|---|
| `no such package`, `no such target`, `not visible from`, `is not defined`, `cycle in dependency graph` | Graph |
| `does not have mandatory providers`, `No matching toolchains found`, `Error in fail:` from a rule | Graph (analysis) |
| `Executing genrule`, `Compiling`, `Linking ... failed: (Exit 1)`, `not all outputs were created`, `missing input file` | Action |
| Everything rebuilds, or a test shows `(cached) PASSED` when it should not | Cache |
| `Another command is running`, `Server terminated abruptly`, `OutOfMemoryError`, `Error downloading`, `Checksum was` | Environment |

### The first five commands, always

```bash
bazel build //X --verbose_failures -s                 # -s prints every command Bazel runs (SUBCOMMAND lines)
bazel build //X --sandbox_debug                       # keep the sandbox; the error shows its path and the wrapper command
bazel build //X --explain=/tmp/explain.txt --verbose_explanations   # why each action re-executed
bazel aquery //X --output=text                        # exact argv, env, inputs, outputs per action
bazel info release && bazel build //X --announce_rc 2>&1 | grep -E '^INFO: (Reading|Found)'   # version and flags in play
```

`-s` is `--subcommands`; `--subcommands=pretty_print` puts one argument per line. `--announce_rc` prints every `.bazelrc` line that applied, with the file it came from, which answers half of all "but it works on my machine" questions in one go.

### Loading errors

| Symptom / message | Cause | Command | Fix |
|---|---|---|---|
| `no such package 'foo/bar': BUILD file not found in any of the following directories` | Directory has no `BUILD.bazel`, or it is excluded by `.bazelignore` | `ls foo/bar; grep -n foo .bazelignore` | Add a BUILD file or fix the label |
| `no such target '//foo:bar': target 'bar' not declared in package 'foo'` | Typo, or the target is created by a macro under another name | `bazel query 'foo:*'` | Use the real name; check macro naming |
| `Label '//foo:sub/x.go' is invalid because 'foo/sub' is a subpackage` | The file belongs to a subpackage | `ls foo/sub/BUILD*` | Use `//foo/sub:x.go`, or depend on the subpackage's target |
| `name 'cc_library' is not defined` (or `java_library`, `py_binary`, `sh_test`, `proto_library`) | Bazel 9 removed autoloading of language rules | `buildifier -r -lint=warn .` | Add the `load()`; `buildifier -r -lint=fix .` adds most of them |
| `glob pattern 'x/**' didn't match anything, but allow_empty is set to False` | Empty globs are an error by default since Bazel 8 | `ls` the pattern | Fix the pattern, or `glob([...], allow_empty = True)` deliberately |
| `cannot load '//tools:defs.bzl': no such file` | Path wrong, or the `.bzl` is outside any package | `ls tools/BUILD*` | Add a BUILD file in `tools/` (it can be empty) |
| `file '//tools:defs.bzl' does not contain symbol 'foo'` | Renamed or private (leading `_`) symbol | `grep -n "^def \|^foo" tools/defs.bzl` | Load the right name; private symbols cannot be loaded |
| `cycle in dependency graph` with a printed path | Two targets depend on each other, often through a macro | the printed cycle; `bazel query 'somepath(//a, //b)'` | Split the shared code into a third target |
| `No repository visible as '@foo' from main repository` | Missing `bazel_dep`, or not in `use_repo()` | `bazel mod show_repo @foo`; `bazel mod tidy` | Add the dep; let `bazel mod tidy` fix `use_repo` |
| `Repository '@@foo+' is not visible from repository '@@bar+'` | A module uses a repo it did not declare | `bazel mod graph`, `bazel mod explain foo` | Add the `bazel_dep` in that module, or patch it with `single_version_override(patches = ...)` |
| `MODULE.bazel.lock is no longer up-to-date` under `--lockfile_mode=error` | Someone changed deps or extension inputs without updating the lockfile | `git diff MODULE.bazel` | `bazel mod deps --lockfile_mode=update`, commit the lockfile |
| Module resolution picks an unexpected version | Minimal version selection took the highest request | `bazel mod explain rules_go` | Bump your own request, or `single_version_override` with a comment |

> **Gotcha.** Canonical repository names (`@@rules_go+`) are an implementation detail. They changed from `~` to `+` in Bazel 8 and may change again. Anything that hard-codes them (scripts reading `bazel-out/../external/rules_go~`, runfiles paths in tests) breaks on upgrades. Use apparent names in labels and the runfiles libraries in code.

### Analysis errors

| Symptom / message | Cause | Command | Fix |
|---|---|---|---|
| `target '//a' is not visible from target '//b'. Check the visibility declaration of the former target` | Visibility working as designed | `bazel query --output=build //a` | Widen `visibility` on `//a` deliberately, or depend on its public target |
| `in deps attribute of go_library rule //b: '//a' does not have mandatory providers: 'GoInfo'` | Wrong kind of target in an attribute | `bazel query --output=label_kind //a` | Depend on the library target, not a filegroup or binary |
| `While resolving toolchains for target //x: No matching toolchains found for types @@bazel_tools//tools/cpp:toolchain_type` | No toolchain registered for this exec/target platform pair | `bazel build //x --toolchain_resolution_debug='@bazel_tools//tools/cpp:toolchain_type'` | Register a toolchain (`register_toolchains`), fix `--platforms`, or add constraints |
| `Dependency chain ... is incompatible with the target platform` / target skipped | `target_compatible_with` excludes the platform | `bazel cquery //x --platforms=P` | Expected for platform-specific targets in `//...`; otherwise fix constraints |
| `Configurable attribute "srcs" doesn't match this configuration` | `select()` without `//conditions:default` and no branch matched | `bazel config`; check `--platforms` and flags | Add `//conditions:default` or the missing branch |
| `Error in fail: ...` from a `.bzl` | A rule or macro rejected its inputs on purpose | read the message; `bazel query --output=build //x` | Fix the attribute values it names |
| `Illegal ambiguous match on configurable attribute` | Two `select()` branches match and neither specialises the other | `bazel config` | Make the `config_setting`s mutually exclusive |
| `in ... attribute of ... rule: source file '//x:y' is misplaced here (expected no files)` | A file passed where only rule targets are allowed | the attribute definition | Wrap in `filegroup`, or pass the generating target |
| Analysis takes minutes on a no-op build | Flags changed, so the analysis cache was dropped | look for `discarding analysis cache` in the output | Same flags everywhere (chapter 04); separate `--output_base` for tools that need different flags |

### Execution and sandbox errors

| Symptom / message | Cause | Command | Fix |
|---|---|---|---|
| `missing input file '//pkg:file.txt'` | Declared input does not exist (deleted, or generated by nothing) | `ls pkg/file.txt`; `bazel query 'kind(rule, rdeps(//..., //pkg:file.txt, 1))'` | Restore the file or fix the label |
| Compiler: `fatal error: foo.h: No such file or directory` only in the sandbox | Header not declared in `hdrs`/`deps` | `--sandbox_debug`, then list the sandbox dir | Add the header to the right `cc_library` |
| `undeclared inclusion(s) in rule '//x'` | C++ includes a header it does not declare | the listed paths | Add the owning `cc_library` to `deps` |
| `bash: foo: command not found` or exit 127 in a `genrule` | Tool assumed on `PATH`; strict action env hides it | `bazel aquery //x --output=text \| grep -A3 Environment` | Depend on the tool via `tools = [...]` and use `$(execpath ...)` |
| `output 'pkg/out.txt' was not created` / `not all outputs were created or valid` | Action wrote to a different path, or failed silently | `-s` to see the command; run it by hand in the sandbox dir | Write exactly to the declared output path (`$@`, `$(OUTS)`, `out.path`) |
| Works with `--spawn_strategy=local`, fails sandboxed | Undeclared input or reliance on the source tree | `bazel build //x --sandbox_debug` | Declare the input; `local` is a diagnostic, never a fix |
| `linux-sandbox` errors inside a container (`Operation not permitted` around namespaces) | The container forbids user namespaces | `bazel info` on the runner; check the CI container's security options | Allow unprivileged user namespaces, or accept Bazel's fallback to `processwrapper-sandbox` on that runner |
| Action hangs | Tool waiting on stdin, network or a lock | `bazel build //x -s`, then `ps -ef --forest` | Give the tool non-interactive flags; tag network use `requires-network` |
| Action produces different output each run | Timestamps, random IDs, absolute paths in the output | build twice with `--disk_cache= --remote_cache=` and `diffoscope` the outputs | Make the tool deterministic (chapter 13) |

#### Reading a sandbox

```bash
bazel build //pkg:target --sandbox_debug 2>&1 | tee /tmp/build.log
# the error now shows the sandbox path and the exact linux-sandbox command line
SANDBOX="$(grep -o '/[^ ]*/sandbox/linux-sandbox/[0-9]*/execroot/[^ ]*' /tmp/build.log | head -1)"
ls -la "$SANDBOX"                       # what the action could see
cd "$SANDBOX" && ls bazel-out/          # what it had produced before failing
```

Run the failing command by hand inside that directory, with the `env` Bazel printed. What is missing there is what is missing from your BUILD file.

### Test failures

| Symptom | Cause | Command | Fix |
|---|---|---|---|
| `ERROR: No test targets were found, yet testing was requested` (exit code 4) | Pattern matched no tests, or tag/size filters excluded them all | `bazel query 'tests(//pattern)'` | Fix the pattern or filters |
| `TIMEOUT` | Test exceeded its size's timeout | `bazel test //t --test_output=streamed` | Fix the slow part; raise `size` or `timeout` only if the test really is that big |
| `NO STATUS` | Bazel did not get a result (interrupted, crashed runner) | rerun with `--test_output=all` | Usually environmental; rerun and check memory |
| `FLAKY` | Passed only on retry | `bazel test //t --runs_per_test=200 --nocache_test_results` | Fix the race; then remove `flaky = True` |
| `(cached) PASSED` after you changed code | The changed file is not in the test's deps | `bazel query 'somepath(//t, //changed:file)'` | If empty, the test never depended on it; that is the answer |
| Test reads a file and gets `No such file` | File not in `data`, or path computed relative to the source tree | check `data`; print `$TEST_SRCDIR` in the test | Add to `data` and resolve with the runfiles library |
| Test passes alone, fails in `bazel test //...` | Shared state: ports, `/tmp`, a database | `--test_strategy=exclusive` to confirm | Use `$TEST_TMPDIR`, random ports, or tag `exclusive` |
| Test passes locally, fails in CI | Different env, flags or resources | compare `--announce_rc`; CI `test.log` | Pass env with `--test_env`; set `size` honestly |
| Sharded test runs everything N times | The test framework ignores `TEST_SHARD_INDEX` | look for `TEST_SHARD_STATUS_FILE` support | Use a framework that supports sharding, or drop `shard_count` |

Environment variables a test can rely on: `TEST_TMPDIR` (private writable directory), `TEST_UNDECLARED_OUTPUTS_DIR` (files kept in `test.outputs/`), `TEST_SRCDIR` and `RUNFILES_DIR` (runfiles root), `TEST_SHARD_INDEX` and `TEST_TOTAL_SHARDS`, and `TESTBRIDGE_TEST_ONLY` (set from `--test_filter`).

### Cache misses

| Symptom | Cause | Command | Fix |
|---|---|---|---|
| Everything rebuilds after switching terminal or IDE | Different flags or env; analysis cache discarded, action keys differ | `--announce_rc` in both; look for `discarding analysis cache` | One `.bazelrc`; `--incompatible_strict_action_env` |
| Rebuilds after `git checkout` back to the same commit | Generated files in the source tree, or tools writing into it | `bazel build //x --explain=/tmp/e.txt --verbose_explanations` | Keep generated files out of the source tree |
| Remote cache hit rate low across machines | Action keys differ between machines | execution log diff (below) | Remove host-dependent inputs |
| Remote cache hits on CI but not on laptops | Laptops use different flags or toolchains | diff `--announce_rc` output | `--config=ci` should add flags, not change output-affecting ones |
| A single action never caches | `no-cache`, `no-remote` or `local` tag, or a volatile input | `bazel aquery //x --output=text \| grep -i -A2 execution_info` | Remove the tag, or find the volatile input |
| Stamped binaries rebuild every commit | `--stamp` with `STABLE_` keys | check for `--stamp` outside `--config=release` | Stamp only in release builds |

#### Diffing two executions

```bash
# same commit, two machines (or two clean output bases)
bazel build //x --execution_log_json_file=/tmp/exec_a.json
bazel build //x --execution_log_json_file=/tmp/exec_b.json   # on the other machine

# compare what each action saw
diff <(jq -S . /tmp/exec_a.json) <(jq -S . /tmp/exec_b.json) | head -80
```

The first difference is nearly always one of: an environment variable, an absolute path, a different toolchain digest, or a different flag on the command line. For large builds, `--execution_log_compact_file` is much cheaper to write; convert it to JSON with the execlog converter in Bazel's source tree before diffing.

#### Diffing action graphs

```bash
git stash; bazel aquery 'deps(//x)' --output=text > /tmp/before.txt
git stash pop; bazel aquery 'deps(//x)' --output=text > /tmp/after.txt
diff /tmp/before.txt /tmp/after.txt | head -80
```

This tells you whether a change altered command lines (and so cache keys) without running a build. Bazel's source repository also has an `aquery_differ` tool for structured comparisons.

### Remote execution and remote cache failures

| Symptom / message | Cause | Command | Fix |
|---|---|---|---|
| `Failed to query remote execution capabilities: UNAVAILABLE` | Endpoint unreachable, TLS or DNS wrong | `grpcurl HOST:443 list`; check `--remote_executor` | Fix the URL or certificates; `--remote_local_fallback` keeps local builds going |
| `UNAUTHENTICATED` / `PERMISSION_DENIED` | Missing or wrong header/credentials | `--announce_rc` (is `user.bazelrc` imported?) | Fix the token; keep it out of the committed rc |
| `DEADLINE_EXCEEDED` on uploads or long actions | `--remote_timeout` too short, or a slow link | profile: look at upload lanes | Raise `--remote_timeout`; enable `--remote_cache_compression` |
| Builds fail mid-way with lost inputs or missing digests | Build without the Bytes: the cache evicted blobs Bazel expected to fetch later | check cache size and eviction | Larger cache or longer retention; `--rewind_lost_inputs` (default on in 10.0) |
| Passes locally, fails remotely with `command not found` or missing shared libs | Worker image lacks a host tool the action assumed | `bazel aquery //x --output=text` for `/usr/` paths | Hermetic toolchain, or add the tool to the worker image deliberately |
| `INVALID_ARGUMENT` about platform properties, or actions queue forever | No worker matches the `exec_properties` | check `//platforms:rbe` against the cluster's worker pools | Align `exec_properties` with what the workers advertise |
| Results differ between local and remote | Non-hermetic action | execution log diff | As for cache misses |

### Fetch and download failures

| Symptom / message | Cause | Command | Fix |
|---|---|---|---|
| `Error downloading [https://...]: ... GET returned 404 Not Found` | URL moved, or the mirror lacks the file | `curl -I URL` | Mirror it; or bump the module version |
| `Checksum was X but wanted Y` | Archive content changed upstream, or a proxy returned an error page | `curl -sL URL \| sha256sum` | Never just update the hash; find out why it changed |
| Downloads hang behind a corporate proxy | Bazel honours `HTTPS_PROXY`/`HTTP_PROXY`/`NO_PROXY` from the environment of the client | `env \| grep -i proxy` | Export the proxy variables before starting the server; `bazel shutdown` to apply |
| Every URL for a resource is blocked | `--downloader_config` has no rewrite for it | the error shows `all_blocked_message` | Add a `rewrite` line and mirror the file |
| Module "not found" after adding `--registry` | The default BCR is no longer consulted once any `--registry` is set | `--announce_rc` | List the BCR (or its mirror) explicitly after internal registries |
| `bazel vendor` output is used but a repo still downloads | Repo not vendored (local repo, ignored in `VENDOR.bazel`, or vendored before a dep change) | `ls vendor_src`; `cat vendor_src/VENDOR.bazel` | Re-run `bazel vendor` after dependency changes |
| Extension fails fetching packages (pip, npm, Go) | The language package host is unreachable | the extension's error names the URL | Mirror or rewrite that host (chapter 13) |

### Server and memory problems

| Symptom / message | Cause | Command | Fix |
|---|---|---|---|
| `Another command (pid=N) is running. Waiting for it to complete on the server` | One server per output base; another client holds the lock | `ps -fp N` | Wait; or give the second tool its own `--output_base` |
| `WARNING: Running Bazel server needs to be killed, because the startup options are different` | Startup flags differ between invocations (e.g. `--host_jvm_args`) | `--announce_rc` | Keep startup options identical across tools |
| `java.lang.OutOfMemoryError: Java heap space`, or `Server terminated abruptly` | Heap too small for the graph, or the kernel OOM killer | `dmesg \| tail`; `bazel info used-heap-size-after-gc` | `startup --host_jvm_args=-Xmx...`; lower `--jobs`; `--discard_analysis_cache` on CI |
| Bazel hangs with no output | Deadlocked server, filesystem stall, waiting on a lock | `jcmd "$(bazel info server_pid)" Thread.print > /tmp/threads.txt` | Attach the thread dump to the bug; `bazel shutdown` to recover |
| Disk full under `~/.cache/bazel` | Output bases and disk cache grow without bound | `du -sh ~/.cache/bazel/_bazel_$USER/*` | Disk cache GC flags (chapter 04); delete old output bases |
| `bazel clean` seems needed to fix a build | Something non-hermetic, or a corrupted output base after a crash | try `bazel clean` once; if it helps, find the cause | `bazel clean --expunge` only as a last resort, then investigate |

> **One-way door.** `bazel clean --expunge` deletes the entire output base: every external repository, the local action cache and the server's state. On a large repo the next build re-fetches and re-analyses everything, which can take a long time and, in an air-gap without a populated repository cache or vendor directory, may not be possible at all. Make sure the vendor directory or repository cache is in place before you run it on a disconnected machine.

### Bazel 8 and 9 migration errors

| Symptom | Cause | Fix |
|---|---|---|
| `WORKSPACE` file ignored, external repos missing (Bazel 8) | `--enable_workspace` defaults to false in 8; WORKSPACE is removed in 9 | Move to `MODULE.bazel` (chapter 05); use `--enable_workspace` on 8 only as a bridge |
| `name 'X' is not defined` for language rules (Bazel 9) | Autoloading of rules removed | `buildifier -r -lint=fix .`; add `bazel_dep`s for `rules_cc`, `rules_java`, `rules_python`, `rules_shell`, `protobuf` as needed |
| Empty glob errors (Bazel 8) | `--incompatible_disallow_empty_glob` flipped | Fix patterns or `allow_empty = True` |
| Runfiles paths changed for external repos (Bazel 8) | `--legacy_external_runfiles` defaults to false | Use the runfiles library (`rlocation`) instead of hard-coded paths |
| Paths containing `~` in canonical repo names stopped matching (Bazel 8) | Separator changed to `+` | Remove hard-coded canonical names |
| A third-party module fails on 9 but works on 8 | The module still relies on autoloads or WORKSPACE | Upgrade it; if no release exists, patch it with `single_version_override(patches = [...])` |

To find autoload breakage before upgrading, run on Bazel 8 with autoloading disabled. The flag that controls it is `--incompatible_autoload_externally`; check `bazel help build | grep -A3 autoload` on your 8.x for its exact behaviour, then try `USE_BAZEL_VERSION=9.3.0 bazel build //...` on a branch.

> **Version-sensitive.** Bazel 10.0 (rc1 at the time of writing) flips another set of flags, including `--incompatible_no_implicit_file_export`, `--incompatible_check_testonly_for_output_files` and `--rewind_lost_inputs`. Run a branch build with `USE_BAZEL_VERSION=10.0.0rc1` before the release lands, and read the release notes' list of flipped flags.

### IDE problems

| Symptom | Cause | Fix |
|---|---|---|
| Every IDE sync triggers a full re-analysis in the terminal | IDE and terminal use different flags on the same output base | Make the IDE use the repo `.bazelrc`; or give it its own `--output_base` |
| gopls: `could not import` for Bazel-only or generated packages | gopls uses `go list`, which cannot see Bazel's graph | Set `GOPACKAGESDRIVER` to a wrapper around `@rules_go//go/tools/gopackagesdriver` |
| clangd: no completions, wrong flags | No `compile_commands.json` | Generate one with a compile-commands extractor (an aspect-based tool) and refresh after BUILD changes |
| Python IDE cannot resolve `@pypi` imports | The IDE knows nothing about the hub repo | Point the IDE at a local venv built from `requirements_lock.txt`, or use the IDE plugin's Bazel integration |
| JetBrains Bazel plugin sync fails | A target in the project view does not build, or the plugin's aspect fails on a rule | Build the project view's targets in the terminal first; narrow the project view |
| Editor shows stale errors after a BUILD change | IDE caches the old graph | Re-sync; for VS Code, reload the window after `bazel run //:gazelle` |

### Filing a good upstream bug

Upstream maintainers (Bazel itself, or a rule set) fix what they can reproduce. Make that cheap:

```bash
bazel version > bug/bazel-version.txt
bazel info > bug/bazel-info.txt              # review before sharing: contains paths
bazel build //repro --announce_rc --verbose_failures -s 2>&1 | tee bug/build.log
bazel build //repro --build_event_json_file=bug/bep.json
# for hangs
jcmd "$(bazel info server_pid)" Thread.print > bug/threads.txt
```

- **Minimal repro.** A new directory with `MODULE.bazel`, one BUILD file and the smallest input that fails. If it only fails in your monorepo, keep deleting until it stops failing; the last thing you deleted is the bug.
- **Version range.** Try the previous and next Bazel versions with `USE_BAZEL_VERSION=...`. "Works on 8.8.1, fails on 9.3.0" is half the diagnosis.
- **Flags.** Paste the `--announce_rc` output. A surprising number of bugs turn out to be a flag from `/etc/bazel.bazelrc` nobody knew about.
- **Where.** Bazel core: `github.com/bazelbuild/bazel/issues`. Rule sets have their own trackers; each module's page on `registry.bazel.build` links to its repository. If you cannot tell which layer is at fault, the rule set's tracker is usually the right first stop.
- **Redact.** `bazel info` and logs contain usernames, paths and sometimes internal hostnames. Strip them before posting to a public tracker.


## 16 · Adopting Bazel, and leaving it

*The fit test, what it costs, a migration that never breaks the build, the numbers that say it is working, and how to keep the exit cheap.*

Bazel is a large commitment with a large payoff in the right repo and a steady tax in the wrong one. This chapter is the fit test, a migration plan that keeps a working build at every step, the numbers that tell you whether it is paying off, and how to leave cheaply if it isn't.

### The fit test

Score each line. Three or more in the left column and Bazel is probably worth a pilot. Mostly right-hand answers and the native tools will serve you better.

| Question | Points toward Bazel | Points away from Bazel |
|---|---|---|
| How much of CI time rebuilds things that didn't change? | Most of it | Little; builds are already incremental |
| How many languages share code? | Three or more, with generated code crossing between them (protos, clients) | One or two, each with a mature native build |
| How big is the repo? | Hundreds of packages, many services | A handful of services |
| Do you need offline, hash-pinned, reproducible builds? | Yes, and the current tools don't give it | Lockfiles plus a mirror already do |
| Who will own the build? | A named person or team, with time for rule upgrades, the cache and CI | Nobody in particular |
| How often do developers onboard? | Rarely, and they stay for years | Often, including contractors for short engagements |
| How much custom tooling do you need? | Codegen, cross-compilation, many target platforms | Standard library and service builds |

> **Note.** The answer can differ between repos in the same company. A monorepo with a moon (or Nx/Turborepo) task graph plus a docker-bake image graph, and a repo with compose-per-service Dockerfiles, can both fit their shape well enough that neither should adopt Bazel. Re-run this test when the shape of a repo changes, not when a new tool is fashionable.

### What it costs

| Cost | Size | How to keep it down |
|---|---|---|
| Initial migration | Weeks for a mid-sized polyglot repo, mostly BUILD files, toolchains and CI | Gazelle for every language it supports; migrate leaves first |
| Rule set upgrades | A few hours per quarter, more around a Bazel major | Renovate on `MODULE.bazel`; upgrade one rule set per MR |
| Bazel major upgrades | A day or two per major, every couple of years | Stay on LTS; test the next major on a branch with `USE_BAZEL_VERSION` |
| Cache and RBE operations | Small for bazel-remote; real for Buildbarn | Start with the cache only; buy RBE if nobody can own it |
| Onboarding | Every new developer learns labels, queries and the sandbox | Keep native tools working; link this manual; pair on the first BUILD change |
| IDE friction | Some language servers need extra setup | `GOPACKAGESDRIVER`, compile_commands extraction, the JetBrains/VS Code plugins |

### A migration that never breaks the build

The rule: at every step, the old build still works and CI still runs it. Bazel runs beside it until it has earned the right to replace it.

#### Phase 1 — pilot one leaf

1. Pick a leaf library with good tests and no generated code.
2. Add `MODULE.bazel`, `.bazelversion`, `.bazelrc` and a root `BUILD.bazel` with Gazelle.
3. `bazel run //:gazelle -- update lib/leaf` and get `bazel test //lib/leaf/...` green.
4. Add an allow-failure CI job that runs it.

Exit criterion: the leaf builds and tests under Bazel on a laptop and in CI, with no host toolchains.

#### Phase 2 — the shared cache

1. Stand up bazel-remote (chapter 10).
2. CI writes on protected branches; laptops read.
3. Measure the hit rate on a no-change rerun from a second machine.

Exit criterion: above 90% cross-machine hits on the pilot. If not, fix hermeticity now; it only gets harder.

#### Phase 3 — expand by dependency order

1. Move libraries bottom-up, so every package you migrate depends only on packages already migrated.
2. Generated code (protos, OpenAPI clients) moves early, because everything above it needs it.
3. Services and images last.
4. Turn the CI job from allow-failure to required once a directory is fully migrated.

Exit criterion: `bazel test //...` covers everything the old CI covered.

#### Phase 4 — switch over

1. CI runs Bazel as the gate; the old build runs nightly for two weeks as a cross-check.
2. Release jobs move to `--config=release` with stamping and rules_oci push.
3. Remove the old build from CI. Keep the native tools working for developers.

> **One-way door.** Phase 4 step 3 is where leaving gets expensive. Before you delete the old CI path, make sure `go build ./...`, `uv run pytest` and `pnpm test` (or your equivalents) still work locally. Those are your exit route.

### The numbers that say it's working

| Metric | Where to get it | Healthy |
|---|---|---|
| CI p50 / p90 for MRs | GitLab pipeline analytics | Falling quarter over quarter; p90 under 15 minutes |
| Remote cache hit rate on main | Last line of every build, or BES | Above 95% on reruns, above 80% on typical MRs |
| No-op build time | `time bazel build //...` twice in a row | Seconds, not minutes |
| Analysis time | `bazel analyze-profile` | Stable as the repo grows |
| BUILD drift | Gazelle `-mode=diff` failures per week | Near zero |
| Flaky test count | BES results or JUnit retries | Falling; every flaky test has an owner |
| Time to first green build for a new developer | Ask them | Under an hour |

### Leaving Bazel cheaply

You can leave without much pain if you kept to two rules:

- **The native lockfiles stayed the source of truth.** `go.mod`, `requirements_lock.txt`, `pnpm-lock.yaml` and `Cargo.lock` drove Bazel through module extensions, not the other way round.
- **The native tools kept working.** Developers could still run the language's own build and test commands.

Then leaving is: replace the CI jobs with native ones, move image builds to buildx or bake (your Docker field manual covers it), delete `MODULE.bazel`, `.bazelrc`, `.bazelversion` and every `BUILD.bazel`, and keep the cache server for a while in case you change your mind.

If you broke those rules, generated code that only Bazel can produce and tests that only run under Bazel are the two things to unwind first.

| `release` | Running Bazel version |
| `used-heap-size-after-gc` | Real memory the graph needs |

### Tags

| Tag | Effect |
|---|---|
| `manual` | Excluded from `//...` and `:all` |
| `exclusive` | Test runs alone |
| `requires-network` | Sandbox allows network |
| `no-sandbox` | Runs without the sandbox (avoid) |
| `no-remote` | Never executed or cached remotely |
| `no-remote-exec` | Cached remotely, executed locally |
| `no-cache` | Never cached anywhere |
| `local` | Local, unsandboxed, uncached |
| `external` | Test is never cached |

### Exit codes

| Code | Meaning |
|---|---|
| `0` | Success |
| `1` | Build failed |
| `2` | Bad command line or environment |
| `3` | Build OK, tests failed or timed out |
| `4` | Build OK, no tests found |
| `8` | Interrupted |
| `36` | Local environmental error |
| `37` | Unhandled Bazel internal error |
